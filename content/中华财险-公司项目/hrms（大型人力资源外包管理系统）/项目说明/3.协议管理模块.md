## 1. 这模块到底管什么

HRMS 不保存完整协议正文。

- `data`：前端传来的完整协议 JSON，原样交给**合约域**保存、修改、查询。
- `bizData`：HRMS 自己保存的管理信息，用于列表、审批、终止、恢复和业务线权限。
- 本地表：`agreement`（当前协议）、`agreement_history`（旧版本）、`agreement_business_line_ref`（协议与业务线）。

所以写业务代码时可以这样理解：**协议内容找合约域；协议在 HRMS 的状态、审批和管理信息找本地库。**

## 2. 入口和最简调用链

接口都从 `AgreementController` 进入，最终调用 `AgreementServiceImpl`。

| 业务 | HTTP 路径 | 核心方法 |
|---|---|---|
| 暂存 | `staging-agreement` | `stagingAgreement` |
| 提交审批 | `submit-approval` | `submitApproval` |
| 查询详情 | `get-agreement` | `getAgreementDetail` |
| 查询列表 | `query-agreement-page` | `queryAgreementPage` |
| 手动终止 | `manual-terminate-agreement` | `manualTerminateAgreement` |
| 手动恢复 | `manual-recovery-agreement` | `manualRecoveryAgreement` |
| 续延 | `extension-agreement` | `extensionAgreement` |
| 删除 | `delete-agreement` | `deleteAgreement` |

最常用链路：

```text
前端请求
  → AgreementServiceImpl
  → 合约域（保存/更新完整协议 data）
  → 流程中心（发起审批）
  → AgreementRepository（保存 HRMS 管理数据）
```

查询详情时相反：

```text
本地 agreement 查管理信息
  + 合约域按 agreementInstanceId 查完整协议内容
  → 拼成详情返回
```

## 3. 数据从哪来、落到哪里

### 3.1 新建、暂存、变更

| HRMS 字段 | 数据来源 | 说明 |
|---|---|---|
| `id` | HRMS 生成 | 本地协议主键，后续终止/恢复/详情都传它 |
| `agreementNo` | 合约域 `save/update` 返回 | 业务协议编号 |
| `agreementInstanceId` | 合约域 `save/update` 返回 | 查询、删除合约域协议时使用 |
| `name` | `bizData.agreementName` | 本地列表名称 |
| `startDate` / `endDate` | `bizData.agreementStartTime` / `agreementEndTime` | 协议起止时间 |
| `belongOperationOrgCode` | `bizData.belongOrgCode` | 协议归属机构 |
| `partA` / `partB` | `bizData.partASignOrg` / `partBSignId` | 签约双方 |
| 银行账户字段 | `bizData.bankAccountReqDTO` | 收款方式、户名、账号、开户行、省市等 |
| 主/子业务线 | `bizData.businessLineDTO` | 落到 `agreement_business_line_ref` |
| `status` | 代码赋值 | 暂存为 `INIT`；提交后为 `APPROVING` |
| `actionType` | 代码赋值 | 新建 `NEW`；编辑已有记录提交时为 `CHANGE` |
| `flowInstanceId` | 流程中心 `start` 返回 | 审批 MQ 回调靠它定位本地记录 |

`data` 内的完整协议字段不在 HRMS 做字段映射；它直接传给 `agreementIntegration.saveAgreement(data)` 或 `updateAgreement(data)`。

### 3.2 协议和供应商的关系

协议的**乙方就是供应商**：`bizData.partBSignId` 保存到 `agreement.partB`，值为供应商 `id`。查询协议列表或详情时，代码再用 `agreement.partB` 查询供应商并补齐 `partBName`（供应商名称）。

即：一个供应商可关联多份协议；当前代码未看到数据库外键，属于按供应商 ID 的业务关联。

### 3.3 手动终止、手动恢复

这两个接口不让前端重新传完整协议。

1. 用请求 `id` 查询本地 `agreement`。
2. 从查到的记录复制名称、日期、签约方、银行账户、业务线。
3. 新建一条本地记录，沿用原 `agreementNo`、`agreementInstanceId`。
4. 再补本次操作字段：

| 业务 | 新增字段 |
|---|---|
| 手动终止 | `actionType=MANUAL_TERMINATE`、`actionRemark=terminationReason`、`manualTerminateDate=terminationDate`、`originId=原协议id` |
| 手动恢复 | `actionType=MANUAL_RECOVERY`、`actionRemark=remark`、`originId=原协议id` |

两者的新记录初始状态都是 `APPROVING`，并各自发起审批。

### 3.4 续延

1. 从 `data.agreement.agreementNo` 取本次续延协议编号。
2. 调合约域 `save(data)`，获取新的 `agreementNo` 和 `agreementInstanceId`。
3. 从 `data.agreement.relationships[0].fromAgreementNo` 取原协议编号，并查询原协议是否存在。
4. 按 `bizData` 生成新的本地记录：`actionType=EXTENSION`、`status=APPROVING`、`originId=原agreementNo`。
5. 发起审批并保存 `flowInstanceId`。

## 4. 各业务的最简逻辑

### 暂存

- 传了 `id`：更新合约域 `data`，更新本地记录，状态设为 `INIT`。
- 没传 `id`：保存合约域 `data`，插入本地记录，状态设为 `INIT`。
- 如果传入的是已生效协议的 `id`：代码会清空该 `id`，按新增草稿处理，不直接覆盖已生效记录。

### 提交审批

1. 检查同一个 `agreementNo` 是否已有 `APPROVING` 记录；有则拒绝。
2. 无 `id` 调合约域保存；有 `id` 调合约域更新。
3. 取 `bizData` 组装 HRMS 本地记录。
4. 用 `permissionOrgCode` 查询审批所属组织；用业务线生成审批变量。
5. 调流程中心发起审批，拿到 `flowInstanceId`。
6. 保存本地记录：新建插入；已有 `id` 更新并标记为 `CHANGE`。

### 审批回调

流程 MQ 只按 `flowInstanceId` 找本地协议：

- 审批通过：更新为生效状态，必要时归档旧版本到 `agreement_history`。
- 审批驳回：普通新建/变更回到 `INIT`；手动终止、手动恢复变为 `REJECTED`。

### 删除

1. 用本地 `id` 查询协议。
2. 用查到的 `agreementInstanceId` 删除合约域协议。
3. 删除本地协议和业务线关联。

## 5. 写代码时只需记住的标识

| 字段 | 该用在什么地方 |
|---|---|
| `id` | HRMS 本地详情、终止、恢复、删除、流程变量 |
| `agreementNo` | 同一协议的业务编号、查审批中记录、查历史版本 |
| `agreementInstanceId` | 调合约域详情、更新、删除 |
| `flowInstanceId` | 流程审批结果回调 |
