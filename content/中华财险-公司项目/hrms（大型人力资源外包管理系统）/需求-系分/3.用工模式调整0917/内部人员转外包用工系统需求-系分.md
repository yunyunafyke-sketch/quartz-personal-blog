# 内部人员转外包用工系统分析设计

## 1. 目标、边界与模型结论

### 1.1 目标

当 HR 系统将内部人员的用工类型调整为“6-新劳务规则”时，HRMS 通过运营支撑域广播维护一套**内部转外包人员模型**。该模型仅服务用工统计、项目/协议关联、提醒与审计；保留 HR 工号，账号和既有权限不发生切换。

### 1.2 本次关键结论

内部转外包人员**不写入现有 `outsourced_staff`（staff）表，也不复用 `OutsourcedStaffEntity`**。

现有 `outsourced_staff` 是 HRMS 原生外包员工的生命周期模型，创建、入离场审批、账号生命周期、项目和协议均与其强耦合。内部转外包人员仍由 HR 系统管理，人事身份和账号权限不能被现有外包人员链路改变；混表会使自动同步误触发既有审批、账号失效、手机号/证件校验及项目续延处理。因此本次应新建独立模型、独立数据表、独立 Repository/Service 和页面接口，只在项目、协议统计处做受控汇总。

### 1.3 系统边界

- HRMS：消费人员广播，维护内部转外包人员、关联项目/协议、查询导出、任职记录、提醒及统计联动。
- HR 系统/运营支撑域：用工类型码表、类型变更轨迹、半小时人员同步、广播生产与失败补偿。
- 账号中心、权限中心：不在本次改造范围。HRMS 自动入、离场不得创建、修改或失效账号和权限。

## 2. 现状与改造结论

| 对象 | 现有实现 | 本次改造 |
| --- | --- | --- |
| 原生外包人员 | `OutsourcedStaffEntity` 对应 `outsourced_staff`；支持创建、入离场审批、账号处理、任职异动 | 沿用现有能力，不写入内部转外包人员，不调整其审批和账号流程 |
| 内部转外包人员 | 当前无对应模型；现有 `create-staff` 要求协议、项目等完整外包信息，不能承接该场景 | 新建独立模型、数据表和广播同步服务；可先不关联项目、协议 |
| 项目/协议关联 | 原生外包人员的项目、协议变更和续延由现有仓储处理 | 新模型独立维护关联；关联后计入项目人数、人员列表和协议报销凭证 |
| 任职记录 | `outsourced_staff_movement` 是原生外包人员的异动快照 | 新建内部转外包人员任职记录，不复用该表，确保两类人员审计边界清晰 |
| 提醒 | 已有项目/协议到期任务，项目在 12 月 1 日、20 日触发通知 | 新增未关联提醒；调整本次人员的项目/协议到期、续延联动及接收人规则 |

## 3. 新模型与数据设计

### 3.1 模型关系

```text
运营支撑域人员广播
        ↓
内部转外包人员主模型（新表，物理表名待确认）
        ├── 项目关联（项目编码、业务条线）
        ├── 协议关联（协议编号）
        └── 内部转外包人员任职记录（新表）

项目 / 协议统计、人员清单、报销凭证
        ↑
原生外包人员（outsourced_staff） + 内部转外包人员（新模型）
```

### 3.2 内部转外包人员主模型

物理表名、主键策略和审计字段沿用项目现有表规范，待数据库设计确认。主模型至少包含以下字段：

| 字段类别 | 字段 | 说明 |
| --- | --- | --- |
| 唯一标识 | 10 位工号 | 该模型的业务唯一键；同一工号仅保留一条当前人员档案 |
| HR 广播信息 | 姓名、手机号、用工类型、HR 人员状态、归属组织、经营组织、入司/离司日期、岗位信息 | 由广播新增或更新；用工类型原样保存 code |
| HRMS 管理信息 | 在职状态、入场日期、离场日期 | 仅记录本模型在 HRMS 的统计状态，不等同于 HR 人事状态 |
| 关联信息 | 项目编码、协议编号、业务条线编码 | 初始可为空；项目关联后由项目带出业务条线 |
| 审计信息 | 创建人、创建时间、最后操作人、最后操作时间、来源 | 广播同步和人工关联均须可追溯；来源用于区分系统同步与人工操作 |

唯一索引为“10 位工号”；建议在项目编码、协议编号、经营组织编码、在职状态上建立组合或单列索引，服务项目统计、未关联提醒和列表分页。索引具体组合以现网数据量和查询计划确认后落 DDL。

### 3.3 任职记录模型

新建内部转外包人员任职记录表，按人员主模型主键关联。每次自动入场、自动离场、项目关联/变更、协议关联/变更、项目/协议续延均保存一条快照或关闭当前有效记录。

快照至少保留：工号、人员名称、用工类型、在职状态、入/离场日期、项目、协议、业务条线、归属组织、岗位信息、操作来源和操作时间。离场时保留离场前关联信息，满足统计追溯与审计。

## 4. 核心业务规则

### 4.1 广播消费与自动入离场

以 10 位工号查询新人员主表；不查询、不新增、不更新 `outsourced_staff`。

| 广播条件 | 新模型处理 |
| --- | --- |
| 用工类型为“6-新劳务规则”，人员不存在 | 新增内部转外包人员；HR 在岗则标记“已入场”，HR 离职则标记“已离场”；项目、协议、业务条线为空。 |
| 用工类型为“6-新劳务规则”，人员已存在且已入场 | 更新广播覆盖的基础信息，保持已入场；重复消息不得重复创建任职记录或占用项目额度。 |
| 用工类型为“6-新劳务规则”，人员已存在且已离场 | 更新基础信息，默认保持已离场；是否允许后续 HR 在岗消息自动返场待确认。 |
| 用工类型变为其他类型，或仍为新劳务规则但 HR 离职 | 已入场人员自动离场，离场日期取消息接收日期，关闭当前任职记录并释放已关联项目额度；已离场人员仅更新基础信息。 |

自动入离场不生成原生外包人员审批单，不调用 `AccountIntegration.invalidExternalAccount`，不修改账号或权限。

### 4.2 项目、协议关联与权限

- 新模型人员可未关联项目、协议。单人编辑和批量关联均要求项目、协议同时必填；项目有效，协议状态为有效或到期未终止。
- 项目实际剩余数量大于等于关联人数才能提交；批量操作任一人员或额度校验失败时整批回滚。
- 关联成功后写入新人员主表、占用项目额度，并新建任职记录；业务条线由项目带出。
- 同层级业务部门经办人：未关联时可查看所有业务条线并关联；关联后仅可查看、操作本人归属业务条线。人力部门经办人可查看、操作全部业务条线数据。
- 所选人员须为同一机构或同一机构及其下级机构；包含已离场人员时由前端二次确认，后端仍执行组织与额度校验。

### 4.3 续延、到期与统计

- 项目或协议存在续延对象时，将新模型中已入场且关联旧对象的人员自动转至续延对象，并写任职记录；该能力不能直接调用仅面向 `outsourced_staff` 的现有仓储实现，应由新模型服务实现。
- 项目/协议到期但无续延或未人工重新关联时，人员保持已入场，账号、权限不变，并持续提醒机构业务经办人；缺经办人时提醒负责人。
- 项目人员数量、人员列表弹窗、协议报销凭证查询需汇总原生外包人员和新模型的已入场、已关联人员；未关联人员不计入项目或协议统计。

## 5. 接口、消息与任务改造

### 5.1 上游广播

新增运营支撑域人员广播消费者，按现有 SOFAMQ 监听方式实现。消息消费完成后，在本地事务内更新新人员主表、任职记录及项目额度。Topic、Tag、消费组、正式字段名和重试策略沿用上游正式契约，当前需求未提供，不在本设计中假定。

最小消息内容：10 位工号、用工类型 code、HR 在岗/离职状态、姓名、手机号、归属组织、经营组织、消息唯一标识或版本时间；入司/离司日期和岗位信息待确认。

### 5.2 页面接口

页面使用**新模型专属**查询、详情、编辑、批量关联和导出接口；不得复用 `OutsourcedStaffController` 的 `create-staff`、`update-staff`、入离场申请接口，避免现有 DTO 的强制校验和副作用。

| 能力 | 变化 |
| --- | --- |
| 查询列表 | 支持工号、姓名、手机号、组织（含下级）、业务条线、项目、协议、在职状态，以及“无关联项目/无关联协议”筛选；按需求原型展示组织简称、业务条线、关联信息、状态、最后操作人和时间。 |
| 详情 | 展示广播同步的基本/岗位信息、关联工作信息及新模型任职记录。 |
| 单人编辑 | 仅允许维护项目、协议；基本信息、用工类型和组织信息由广播管理，不允许人工改写。 |
| 批量关联 | 校验人员组织范围、项目/协议可选范围、项目实际剩余数量，成功后原子更新。 |
| 导出与导出记录 | 导出当前查询结果，记录操作人、时间、成功/失败状态；可复用现有通用导出设施，但数据查询来自新模型。 |

### 5.3 定时提醒

- 每日 16:00：按机构统计新模型中未关联项目、未关联协议人数，提醒业务部门与人力部门经办人；缺经办人时提醒负责人。
- 项目到期：按需求在项目结束年度 12 月 1 日提醒；到期后仍未续延或未重新关联时继续提醒。现有 `ProjectRelationNoticeHandler` 的 12 月 20 日触发与需求不一致，需调整或拆分新模型任务。
- 协议到期：到期前 30 天提醒；协议到期未续延时沿用协议“到期未终止”30 天宽限规则，并对未重新关联人员继续提醒。

钉钉消息的 `channelCode`、模板编号与“经办人/负责人”查询规则待确认。

## 6. 最小代码改造范围与测试

| 分层 | 主要改造 |
| --- | --- |
| `service/listener` | 新增人员广播消费者与消息 DTO 适配。 |
| `domain` | 新增内部转外包人员领域服务、项目/协议关联、自动入离场、续延、统计查询服务。 |
| `infrastructure/repository` | 新增主模型及任职记录 Entity、Mapper、Repository 和 DDL；禁止复用 `outsourced_staff`、`outsourced_staff_movement` 的写库逻辑。 |
| `web`、`service`、`bootstrap` | 新增新模型专属接口、命令与返回 DTO；不改动现有原生外包人员接口语义。 |
| `scheduler` | 新增未关联提醒、补充项目/协议到期与续延任务。 |

测试至少覆盖：广播新增与重复投递、自动离场及项目额度释放、不触发审批和账号失效、单人/批量关联的额度和组织校验、未关联/关联后的数据权限、续延自动迁移、两类人员汇总统计、提醒接收人降级。

## 7. 待确认项

1. 新模型、两张新表及新页面接口的正式命名；本文不预设物理表名、Java 类名或 API 路径。
2. “6-新劳务规则”的正式码值，及广播 Topic/Tag/消费组、完整字段、消息唯一标识/版本时间。
3. HR 在岗人员的广播是否保证姓名、手机号、组织、岗位等新模型必要信息完整；不足时的落库策略。
4. 已离场人员再次收到“新劳务规则 + 在岗”广播时，是否自动返场及入场日期口径。
5. 新模型人员关联项目后，项目额度的占用、自动离场后的释放、离场人员再次关联时是否重新占用的具体规则。
6. 项目人数、项目人员列表和协议报销凭证的现有查询位置及最终汇总口径；是否仅汇总已入场人员。
