## 人员手机号检验规则

创建外包人员时，`phone` 字段会经过以下校验：

1. **必填校验**：手机号不能为空；为空时返回“手机号不能为空”。
2. **格式校验**：必须是 11 位中国大陆手机号，格式为 `^1[3-9]\\d{9}$`：以 `1` 开头，第二位为 `3` 至 `9`，其余为 9 位数字；不符合时返回“手机号格式错误”。
3. **唯一性校验**：保存时由数据库唯一索引 `uk_contact_number` 兜底限制，手机号重复时返回“手机号已存在”。

校验位置

- 请求字段的必填与格式：`CreateStaffCmd.phone`。
- 请求参数校验：`OutsourcedStaffWebValidator.validateCreateStaff` 调用统一参数校验。
- 手机号唯一性：新增员工插入数据库时捕获唯一索引冲突并转换为业务提示。

## 人员批量导入提示“批次号不存在有效记录”

点击“批量保存员工”时，系统会按批次号查询导入明细中状态为 `1` 的记录；查询结果为空时，即提示“批量导入员工信息批次号不存在有效记录”。

常见触发情况：

1. 该批次没有成功写入导入明细，例如文件导入未完成或未插入任何记录。
2. 导入明细已被全部删除或清空。
3. 导入的所有员工均校验失败，明细状态均为 `0`。
4. 原本有效的明细在后续保存处理中因手机号与已有员工冲突等原因被标记为失败。

导入明细可能因机构或岗位不存在、无机构权限、手机号重复、证件类型或号码不合法、码值校验失败、线客必填项缺失，以及员工状态不允许关联当前项目等原因而变为失败。应先在批次明细页查看各条记录的失败原因，修正后重新导入。

校验代码：`OutsourcedStaffBatchSaveHandler.getValidBatchRecords`，查询条件为 `batch_id = 当前批次号` 且 `status = 1`。

## 人员批量导入提示“无此机构权限”

导入单条人员信息时，系统会使用本次上传携带的权限机构编码 `permissionOrgCode` 计算可操作的机构范围，再与 Excel 中该行的“归属部门/团队”机构编码比较。

只有同时满足以下条件时，明细会提示“无此机构权限”：

1. Excel 中填写的机构编码存在；不存在时会提示“机构编码: xxx对应的经营组织不存在”。
2. `permissionOrgCode` 计算出的可操作机构范围不为空；空范围在当前代码中表示不限制机构权限。
3. 当前行填写的归属部门机构编码不在该可操作范围内。

示例：当前权限机构仅覆盖 A 支公司及其下属机构，而 Excel 填写的是 B 支公司的电融团队，则该行导入失败并标记为无效记录（`status=0`）。如果一个批次所有行都因该原因失败，后续点击“导入”保存时会进一步提示“批次号不存在有效记录”。

校验代码：`OutsourcedStaffBatchImportHandler.validateRecord`；权限范围由 `AgreementService.buildPermissionScope(permissionOrgCode)` 计算。

### `permissionOrgCode` 的来源与排查

`permissionOrgCode` 不是 Excel 中的员工归属机构编码，也不是当前后端自动根据登录人生成的值。它由前端在调用批量导入接口 `POST /import-batch-staff-file` 时，作为请求体字段传入：

```json
{
  "batchId": "批次号",
  "permissionOrgCode": "机构编码",
  "fileId": "文件ID"
}
```

该字段用于确定“本次操作按哪个机构计算权限”，可理解为当前操作的权限机构或管理机构。其对应的可操作范围规则如下：

- 总公司编码 `210000000000`：不限制机构范围。
- 一级机构：可操作本机构及下属二、三级机构。
- 二级机构：可操作本机构及下属三级机构。
- 三级机构：可操作本机构及其上级二级机构。

后端仅校验该字段非空，然后将其透传至权限范围计算逻辑；当前项目未包含前端实现，无法从后端代码确认页面实际取的是“当前选中机构”还是“登录人默认机构”。排查具体问题时，可在浏览器开发者工具的 Network 请求详情中查看此次 `import-batch-staff-file` 请求体实际传入的 `permissionOrgCode`，再与 Excel 中“归属部门/团队”的机构编码比较。

### Excel 中归属部门机构编码的查看位置

权限校验实际比较的是 Excel 模板中的“人员归属部门/团队编码”列，对应字段 `branchOrgCode`，而不是页面展示的“归属部门/团队”名称。导入明细页当前只展示机构名称，不能据此确认实际参与校验的编码。

排查“无此机构权限”时：

1. 打开本次上传的 Excel，查找报错人员所在行的“人员归属部门/团队编码”。
2. 在浏览器 Network 中查看导入请求的 `permissionOrgCode`。
3. 按机构层级规则确认该 Excel 编码是否属于 `permissionOrgCode` 的可操作范围。

即使 Excel 中的机构名称显示正确，只要名称对应的机构编码不在权限范围内，仍会报“无此机构权限”。

### 如何判断 `permissionOrgCode` 的机构层级

HRMS 不通过机构名称判断层级，而是调用组织服务查询 `permissionOrgCode` 对应的组织详情，读取 `orgOperationDetailDTO.branchOrgLevel` 字段。当前批量导入权限逻辑识别的取值如下：

| `branchOrgLevel` | 实际机构类型 | 权限逻辑中的层级 |
| --- | --- | --- |
| `0` | 总公司 | 一级机构 |
| `1` | 分公司 | 二级机构 |
| `2` | 中心支公司 | 三级机构 |

如果 `permissionOrgCode` 传入的是团队等非经营组织编码，后端会沿组织路径向上查找最近的经营组织，再以该经营组织的 `branchOrgLevel` 计算权限范围。因此，团队编码通常会按其所属的中心支公司或其他最近经营组织的层级处理。

实际排查时，可在组织中心/组织管理中按 `permissionOrgCode` 查询机构详情并查看“机构层级”；若通过接口排查，关注响应字段 `orgOperationDetailDTO.branchOrgLevel`。

## 申请单不存在、任务实例为空或流程不存在
![](image/Pasted%20image%2020260828164626.png)
![](image/Pasted%20image%2020260828164618.png)

出现“申请单不存在”“无法获取到任务实例：null”或“流程不存在”时，先区分两种情况：真正缺少申请/流程数据，或列表接口没有把已存在的关联信息返回给页面。不能仅凭页面中的 `null` 判断数据库数据已丢失。

### 数据关联关系

入离场审批涉及以下三张 HRMS 表及流程中心：

```text
outsourced_staff（人员表）
  id
   └─ outsourced_staff_onoffboard_application_record.account_id（申请单明细）
        └─ application_batch_id
             └─ outsourced_staff_onoffboard_application.id（申请单）
                  └─ flow_req_id / flow_instance_id（流程中心实例 ID）
```

注意：申请明细表的 `account_id` 在本功能中存储的是人员表 `outsourced_staff.id`，即接口返回的 `staffId`，而不是人员登录账号 `accountId`。

### 排查顺序

1. 从人员列表接口获取 `staffId`、`staffStatus`、`requestId` 与 `flowInstanceId`。`staffStatus=2` 表示“离场审批中”。
2. 不要因为接口中 `requestId` 或 `flowInstanceId` 为 `null` 就直接认定数据不存在；按人员 `staffId` 查询申请明细，再经 `application_batch_id` 查询申请单。
3. 核对申请单中的 `flow_req_id`、`flow_instance_id`，拿到真实流程实例 ID 后再到流程中心查询实例是否存在。
4. 对比人员状态、申请单状态和申请明细状态：人员显示“审批中”而申请单已经是 `success` 时，需重点检查列表查询的状态过滤条件和后续人员状态更新是否一致。
5. 只有申请单中的流程实例 ID 为空，或流程中心按真实流程实例 ID 查询不到记录时，才进一步排查发起流程失败、流程配置下线或流程实例被清理。

### 本次问题的定位示例

人员孟晓悦的数据如下：

| 项目 | 值 | 含义 |
| --- | --- | --- |
| 人员 ID | `7483405542666027008` | 人员表主键，也是申请明细关联值 |
| 登录账号 | `zhex08330100094` | 人员账号，不用于关联申请明细 |
| 人员状态 | `2` | 离场审批中 |
| 申请单 ID | `7483407043979395072` | 申请单存在 |
| 申请单状态 | `success` | 申请处理成功 |
| 申请明细状态 | `1` | 明细处理成功 |
| 流程实例 ID | `PS2026077483407241472118784` | 流程关联字段已有值 |

该案例中，申请单和流程实例 ID 均未丢失。人员列表接口仍返回 `requestId=null`、`flowInstanceId=null` 的原因是查询申请单时只筛选了 `approving`、`approved`、`fail` 三种申请单状态，遗漏了 `success`。因此状态为 `success` 的申请单不会被列表接口查出，页面点击详情时将空的申请单 ID 传入，最终报“申请单不存在”或“无法获取到任务实例：null”。

相关代码：`OutsourcedStaffQueryRepositoryImpl.fetchApplicationMap`；申请单状态过滤调用 `selectMapByRecordAccountIdsAndStatuses` 时未包含 `SUCCESS`。

### 提供给研发/运维的处理结论

1. 列表查询的申请单状态过滤需补充 `success`，使页面能够获得正确的 `requestId` 和 `flowInstanceId`。
2. 修复后复核人员状态：申请单和明细均为成功，但人员仍为“离场审批中（2）”，需确认是否还应进入正式离场状态。
3. 如页面带到正确的流程实例 ID 后仍提示“流程不存在”，再由流程中心按 `PS2026077483407241472118784` 查询实例是否已被清理或是否跨环境访问。

### 只读查询示例

```sql
SELECT
    s.id AS staff_id,
    s.account_id AS login_account_id,
    s.staff_status,
    r.id AS record_id,
    r.application_batch_id,
    r.status AS record_status,
    a.id AS request_id,
    a.status AS request_status,
    a.flow_req_id,
    a.flow_instance_id
FROM outsourced_staff s
LEFT JOIN outsourced_staff_onoffboard_application_record r
    ON r.account_id = s.id
LEFT JOIN outsourced_staff_onoffboard_application a
    ON a.id = r.application_batch_id
WHERE s.id = '7483405542666027008';
```
