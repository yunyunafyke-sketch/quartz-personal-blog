## 一、💡 一句话理解

> [!tip] 核心结论
> 多个事务同时操作数据时，数据库必须决定“谁能看到哪份数据”和“谁需要等待”。隔离级别负责制定规则，InnoDB 主要通过历史版本和锁来执行这些规则。

先不着急背术语，只记住这条主线：

```text
多个事务同时操作同一批数据
→ 可能产生脏读、不可重复读、幻读或丢失更新
→ 隔离级别规定要防住哪些问题
→ InnoDB 再使用历史版本和锁实现这些规则
```

## 二、🧭 理论：先认识并发、锁和 MVCC

### 2.1 为什么学完事务还要学隔离和锁

事务的原子性只能保证“多条操作一起成功或一起失败”。它并不自动保证多个事务同时执行时不会互相干扰。

假设账户余额是 `1000`，两个用户几乎同时扣款：

```text
事务 A：读到 1000，准备扣 100
事务 B：也读到 1000，准备扣 200
```

如果没有并发控制，两个事务都可能根据同一个旧值计算，造成结果被覆盖。所以学完“事务是什么”以后，还必须学习事务之间如何相处。

```text
事务       = 划定一组操作的开始和结束
隔离级别 = 规定并发事务之间能看到什么
锁           = 让冲突的操作按顺序执行
MVCC         = 让普通查询可以读取合适的历史版本
```

### 2.2 数据库锁是什么

先把锁理解成一个非常简单的规则：

> [!tip] 锁的最小定义
> 当一个事务正在使用或修改某份数据时，数据库会限制其他事务对这份数据执行冲突操作。得不到锁的事务通常需要等待，或者返回失败。

可以把一行数据想成一间只有一块白板的会议室：

```text
事务 A 正在修改白板内容
→ 数据库给这份数据加上合适的锁
→ 事务 B 也想修改同一份数据
→ B 先等待
→ A 提交或回滚，锁被释放
→ B 才能继续
```

这个类比只用来理解“冲突操作需要排队”。真实的 InnoDB 锁有不同类型和范围，后文再逐步展开。

### 2.3 为什么不能所有读取都靠锁

如果普通查询一遇到正在修改的数据就必须等待，读写会经常互相堵住，并发性会很差。

假设余额原来是 `1000`，事务 A 正在把它修改为 `900`，但还没提交。此时事务 B 进行普通查询，有三种可能：

| 做法 | 问题 |
| --- | --- |
| 让 B 一直等 A | 安全，但普通读取容易被写操作堵住 |
| 让 B 直接读未提交的 `900` | 可能读到以后会被回滚的脏数据 |
| 让 B 读取对自己可见的旧版本 `1000` | 既不必等待，也不会看到未提交数据 |

第三种做法就是理解 MVCC 的起点。

### 2.4 MVCC 是什么

MVCC 的全称是 Multi-Version Concurrency Control，即“多版本并发控制”。此时只需要记住：

> [!tip] MVCC 的最小定义
> 同一行数据被修改后，InnoDB 仍能根据修改记录找到较旧的版本。普通查询可以按照当前事务的读取视角，选择自己应该看到的版本。

```text
最新版本：900，正在被事务 A 修改
历史版本：1000，对事务 B 仍然可见

事务 B 执行普通 SELECT
→ 不必去读 A 未提交的 900
→ 也不一定要等 A 结束
→ 可以返回对自己可见的 1000
```

这里先理解目的就够了。历史版本保存在哪里、Read View 怎么判断可见性，会在第五章详细说明。

### 2.5 本篇的学习顺序

```text
先看并发事务会造成什么问题
→ 再看四种隔离级别分别允许什么
→ 再理解 MVCC 如何为普通查询选择版本
→ 然后理解 MVCC 和锁的正式分工
→ 最后深入具体锁类型、加锁范围和死锁
```

> [!warning] 暂时不要死背细节
> 刚开始只要能说出“锁让冲突操作排队，MVCC 让普通查询可以选择合适的历史版本”就够了。

## 三、⚠️ 理论：并发事务会产生什么问题

| 问题 | 现象 |
| --- | --- |
| 脏读 | 读到了其他事务尚未提交的数据，之后对方可能回滚 |
| 不可重复读 | 同一事务两次读取同一行，值发生了变化 |
| 幻读 | 同一事务两次按相同条件查询，结果行数发生了变化 |
| 丢失更新 | 两个事务都根据同一个旧值计算新值，后写入的结果覆盖先写入的结果 |

下面的事务 A 和事务 B 表示两个独立的数据库连接。SQL 只用于解释执行顺序，假设示例表和数据已经存在；如需动手验证，只能在个人测试库中进行。

### 3.1 脏读是怎么产生的

先用生活例子理解：同事正在修改一份共享表格，还没有点击“保存”，你却看到了他的临时数字，并拿这个数字去做决定。后来同事发现写错了，撤销了修改。你刚才看到的数字从来没有正式生效，这就是“读到了脏数据”。

假设账户 A 的余额原来是 `1000` 元：

| 时间 | 事务 A | 事务 B |
| --- | --- | --- |
| ① | 开始事务 |  |
| ② | 把余额从 `1000` 改成 `900`，但是**没有提交** |  |
| ③ |  | 读取余额，竟然读到尚未提交的 `900` |
| ④ | 发现操作有误，执行 `ROLLBACK`，余额恢复为 `1000` |  |
| ⑤ |  | 此时才发现刚才读到的 `900` 从未真正生效 |

对应的执行顺序可以简化为：

```sql
-- 事务 A
START TRANSACTION;
UPDATE account SET balance = 900 WHERE id = 1;
-- 暂时不提交
```

```sql
-- 事务 B：只有允许读取未提交数据时，才可能看到这种结果。
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
START TRANSACTION;
SELECT balance FROM account WHERE id = 1;
-- 读到 900，但事务 A 还没有提交。
```

```sql
-- 事务 A 后来撤销修改。
ROLLBACK;
-- 数据库中的余额重新变成 1000。
```

问题在于：事务 B 可能已经根据不存在的 `900` 拒绝付款、发送通知或执行其他业务操作。

> [!tip] 判断关键词
> 脏读的关键不是“两次读取结果不同”，而是**读到了其他事务尚未提交、以后还可能被回滚的数据**。

### 3.2 不可重复读是怎么产生的

生活中可以理解为：你在同一张商品详情页里先看到价格是 100 元；工作人员正式修改并保存价格后，你刷新页面看到 120 元。同一个商品还在，但同一字段前后两次读到的值不同。

仍然假设账户余额原来是 `1000` 元：

| 时间 | 事务 A | 事务 B |
| --- | --- | --- |
| ① |  | 开始事务，第一次读取余额，得到 `1000` |
| ② | 开始事务，把余额改成 `900` |  |
| ③ | 执行 `COMMIT`，修改正式生效 |  |
| ④ |  | 在同一个事务里再次读取同一账户，得到 `900` |

```sql
-- 事务 B：READ COMMITTED 下，每次普通查询会读取新的已提交版本。
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT balance FROM account WHERE id = 1;
-- 第一次得到 1000。
```

```sql
-- 事务 A 在两次查询之间提交修改。
START TRANSACTION;
UPDATE account SET balance = 900 WHERE id = 1;
COMMIT;
```

```sql
-- 事务 B 仍处于原来的事务中，再查一次同一行。
SELECT balance FROM account WHERE id = 1;
-- 第二次得到 900。
COMMIT;
```

这不是脏读，因为事务 B 第二次读到的 `900` 已经由事务 A 提交。问题是：**事务 B 在同一个事务中重复读取同一行，结果却不能保持一致。**

> [!tip] 判断关键词
> 不可重复读关注的是**同一行数据的内容发生变化**，例如同一个账户的余额从 `1000` 变成 `900`。

### 3.3 幻读是怎么产生的

生活中可以理解为：你第一次统计“教室里穿红衣服的人”，数出 2 人；统计过程中又进来一个穿红衣服的人；你按照相同条件再数一次，变成了 3 人。原来的两个人没有变，但符合条件的结果集合中凭空多出了一行，好像出现了“幻影”。

假设订单表中原来只有 1 条待支付订单：

| 时间 | 事务 A | 事务 B |
| --- | --- | --- |
| ① |  | 开始事务，查询待支付订单，得到 1 条 |
| ② | 插入一条新的待支付订单 |  |
| ③ | 执行 `COMMIT`，新订单正式生效 |  |
| ④ |  | 使用完全相同的条件再次查询，得到 2 条 |

```sql
-- 事务 B 第一次按条件查询。
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT * FROM orders WHERE status = 'PENDING';
-- 第一次返回 1 行。
```

```sql
-- 事务 A 插入一条也符合 status = 'PENDING' 的记录并提交。
START TRANSACTION;
INSERT INTO orders(id, status) VALUES (2, 'PENDING');
COMMIT;
```

```sql
-- 事务 B 使用完全相同的条件再次查询。
SELECT * FROM orders WHERE status = 'PENDING';
-- 第二次返回 2 行。
COMMIT;
```

两次查询条件没有变化，但符合条件的记录集合发生了变化。新插入的记录像“幻影”一样出现在第二次结果中，所以叫幻读。其他事务删除符合条件的记录，也可能让第二次查询少一行。

> [!tip] 判断关键词
> 幻读关注的是**相同查询条件得到的记录集合发生变化**，常见表现是多了一行或少了一行；不可重复读关注的是同一行的字段值发生变化。

### 3.4 丢失更新是怎么产生的

假设账户余额是 `1000` 元，事务 A 支付 `100` 元，事务 B 支付 `200` 元。两个事务都采用“先查询，再由程序计算，最后把结果写回”的方式：

```text
事务 A 读取余额 1000
事务 B 也读取余额 1000

事务 A 计算 1000 - 100 = 900，并写入 900
事务 B 计算 1000 - 200 = 800，并写入 800
```

最终余额是 `800`，但正确结果应该是：

```text
1000 - 100 - 200 = 700
```

事务 B 写入的 `800` 覆盖了事务 A 已经写入的 `900`，导致事务 A 的扣款效果消失，这就是**丢失更新**。

常见解决办法：

- 直接执行原子更新：`UPDATE account SET balance = balance - 100 WHERE id = 1 AND balance >= 100;`
- 在事务中先用 `SELECT ... FOR UPDATE` 锁定目标行，再读取和修改。
- 使用版本号做乐观锁，更新时检查数据有没有被其他事务改过。

> [!warning] 不要混淆
> `UPDATE account SET balance = balance - 100` 由数据库基于当前值直接计算，与应用先读出 `1000`、计算出 `900`，再执行 `UPDATE account SET balance = 900` 不同。后者更容易覆盖其他事务的修改。

四种问题可以这样快速区分：

| 问题 | 最关键的判断点 |
| --- | --- |
| 脏读 | 读到了别人**还没提交**的数据，这个数据之后可能被回滚 |
| 不可重复读 | 同一事务重复读取**同一行**，已经提交的字段值发生了变化 |
| 幻读 | 同一事务使用相同条件重复查询，符合条件的**记录集合**多了或少了 |
| 丢失更新 | 两个事务根据同一个旧值计算，后写入的结果覆盖了先写入的结果 |

> [!tip] 大白话记忆
> **脏读**：偷看了别人还没保存的草稿，别人后来又撤销了。
>
> **不可重复读**：第一次看的是正式版本，别人保存了新版本，第二次再看时，同一条内容变了。
>
> **幻读**：第一次按条件点名有 2 个人，别人又正式加入了一个符合条件的人，第二次用相同条件点名变成 3 个人，像凭空冒出来一个“幻影”。
>
> **丢失更新**：两个人都拿同一个旧版本进行修改，后保存的人覆盖了先保存的人，导致前一个人的修改白做了。

隔离越强，并发事务越不容易互相影响，但等待和锁冲突通常也越多。因此数据库通过**隔离级别**在一致性和并发性能之间取舍。

## 四、🧱 理论：四种隔离级别

InnoDB 支持四种隔离级别，默认是 `REPEATABLE READ`。

先看面试最常用的结论：

| 隔离级别 | 能防止什么 | 仍可能发生什么 | 为什么 |
| --- | --- | --- | --- |
| `READ UNCOMMITTED` | 基本没有防住三种读异常 | 脏读、不可重复读、幻读 | 连其他事务尚未提交的数据都允许读取 |
| `READ COMMITTED` | 脏读 | 不可重复读、幻读 | 只读已提交数据，但每次查询都会读取当时最新的已提交版本 |
| `REPEATABLE READ` | 脏读、不可重复读；InnoDB 还能处理常见幻读问题 | 普通快照读通常不会出现前三种读异常，但当前读要结合锁理解 | 同一事务的普通一致性读通常复用同一快照；范围锁定操作还会使用 next-key lock |
| `SERIALIZABLE` | 脏读、不可重复读、幻读 | 三种经典读异常通常都不会发生 | 通过更严格的锁和等待，让事务尽量像排队一样执行 |

### 4.1 READ UNCOMMITTED：别人没提交也能读

这个级别几乎不限制普通读取。事务 A 把余额从 `1000` 改成 `900`，即使尚未提交，事务 B 也可能读到 `900`。

```text
事务 A：写入 900，但没有提交
事务 B：直接读到 900                 ← 脏读
事务 A：ROLLBACK，余额恢复成 1000
```

既然连未提交数据都能看到，就更无法保证同一行重复读取不变，也无法保证相同条件查询的记录集合不变。因此三个问题都可能发生。

> [!tip] 大白话
> `READ UNCOMMITTED` 相当于别人草稿还没保存，你就能偷看。

### 4.2 READ COMMITTED：解决脏读，但不能解决不可重复读

这个级别规定：**只能读取已经提交的数据。**

如果事务 A 把余额改成 `900` 但没有提交，事务 B 仍然只能读到之前已经提交的 `1000`，所以不会脏读。

```text
事务 A：写入 900，但没有提交
事务 B：只能读到已提交的 1000         ← 防止脏读
```

但是，`READ COMMITTED` 下每条普通查询都会读取执行这一刻最新的已提交版本：

```text
事务 B：第一次查询余额，得到 1000
事务 A：把余额改成 900，并且 COMMIT
事务 B：第二次查询余额，得到 900       ← 不可重复读
```

事务 B 第二次读到的 `900` 是合法的已提交数据，所以不属于脏读；但同一事务两次读取同一行的结果不同，因此属于不可重复读。

同样，如果事务 A 在两次查询之间提交了一条符合条件的新记录，事务 B 第二次查询时就会看到它，所以也可能发生幻读。

> [!tip] 为什么能防脏读，却防不了不可重复读
> 它只承诺“不给你看未提交的数据”，没有承诺“整个事务始终看同一个版本”。

### 4.3 REPEATABLE READ：同一事务通常看同一个快照

这是 InnoDB 的默认隔离级别。对于普通一致性读，事务第一次查询时会建立 Read View，后续普通查询通常继续使用同一个快照。

```text
事务 B：第一次查询余额，得到 1000，并建立快照
事务 A：把余额改成 900，并且 COMMIT
事务 B：第二次普通查询仍然得到 1000   ← 保持可重复读
```

事务 A 已经提交了 `900`，但它是在事务 B 的快照建立之后提交的，所以事务 B 的普通查询暂时看不到它。这样就避免了不可重复读。

如果事务 A 后来插入一条符合条件的新记录，事务 B 的普通快照读通常也看不到这条新记录，因此两次查询的结果集合能够保持一致。

不过要区分两种读取：

- 普通 `SELECT` 是**快照读**，主要使用 MVCC 和 Read View。
- `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 是**当前读或锁定操作**，要读取较新的数据并加锁。

InnoDB 对索引范围执行锁定读或修改时，还可能使用 next-key lock 锁住索引记录及其间隙，阻止其他事务在相关范围插入新记录，从而处理常见的幻读问题。

> [!warning] 面试容易混淆的地方
> 按 SQL 标准的常见隔离级别表格，`REPEATABLE READ` 仍可能出现幻读；但 MySQL InnoDB 结合 MVCC 和 next-key lock，能够处理常见的幻读场景。回答时最好明确说“MySQL InnoDB 的实现”。

### 4.4 SERIALIZABLE：让事务尽量排队执行

这是隔离程度最高的级别。可以把它理解为：多个事务对同一批数据的操作尽量排队，不让它们随意交叉执行。

```text
事务 A：读取或修改目标数据，并持有相关锁
事务 B：也想操作冲突的数据，只能等待
事务 A：COMMIT 或 ROLLBACK，释放锁
事务 B：继续执行
```

在关闭自动提交的事务中，InnoDB 会把普通 `SELECT` 隐式转换为共享锁定读。这样能避免三种经典读异常，但也会带来更多锁等待、降低并发能力，所以普通业务通常不会默认使用。

### 4.5 四个级别到底逐步增加了什么

```text
READ UNCOMMITTED
    什么版本都可能读
        ↓ 增加“只能读已提交数据”
READ COMMITTED
    防止脏读，但每次查询可能看到新版本
        ↓ 增加“同一事务复用快照”
REPEATABLE READ
    普通查询前后结果更稳定
        ↓ 增加更严格的锁和串行等待
SERIALIZABLE
    隔离最强，但并发性能最低
```

> [!tip] 最简单的记忆方法
> `READ COMMITTED` 只保证“读到的是真的”；`REPEATABLE READ` 进一步保证“这次事务里反复读，看到的版本尽量不变”；`SERIALIZABLE` 则让有冲突的事务尽量排队。

> [!info] 丢失更新要单独理解
> 上面的隔离级别对比主要讨论脏读、不可重复读和幻读三种经典读异常。业务代码如果采用“先读旧值、在程序中计算、再把绝对值写回”的方式，仍要注意丢失更新；通常使用原子 `UPDATE`、`SELECT ... FOR UPDATE` 或版本号乐观锁解决。

### 4.6 四种隔离级别的实际场景与选择

先用一句话记住最常比较的两个级别：

```text
READ COMMITTED  = 实时直播
REPEATABLE READ = 某个时间点的截图
```

直播不断更新，但前后看到的内容可能不同；截图可能不是最新的，但分析截图时内容不会突然变化。

| 隔离级别 | 典型定位 | 普通业务是否常用 |
| --- | --- | --- |
| `READ UNCOMMITTED` | 可以接受脏数据的临时观察或实验 | 几乎不用 |
| `READ COMMITTED` | 关注最新已提交结果的高并发短事务 | 常用 |
| `REPEATABLE READ` | 一个事务内需要稳定数据视角 | MySQL 默认，常用 |
| `SERIALIZABLE` | 正确性和严格顺序远比吞吐量重要 | 极少使用 |

#### 4.6.1 READ UNCOMMITTED：只适合允许结果失真的临时场景

它允许读取其他事务尚未提交的数据，查询结果可能随后被回滚。

可以勉强考虑的场景：

- 个人测试环境中演示脏读；
- 临时观察一个大事务进行到了哪里，并且结果只供参考；
- 对准确性完全没有要求的粗略估算。

例如事务 A 正在导入 100 万条数据但尚未提交，事务 B 可能看到已经导入 80 万条；如果事务 A 最终回滚，真实数量又会变成 0。

```text
临时看到：80 万条
导入事务：发生错误并回滚
最终真实结果：0 条
```

余额、支付、订单、库存、权限、报表和审计等业务不能使用它。

> [!tip] 场景关键词
> 可以接受“刚才读到的数据可能从未正式存在”，才可能考虑 `READ UNCOMMITTED`；普通业务基本不用。

#### 4.6.2 READ COMMITTED：适合查询最新状态和高并发短事务

它只读取已经提交的数据，并且每条普通查询都会读取执行当时最新的已提交版本。

适合的场景：

- 客服查询订单当前状态；
- 后台管理页面刷新最新数据；
- 用户查询最新物流进度；
- 高并发、执行时间很短的增删改查接口；
- 业务能够接受同一事务中前后两次查询结果发生变化。

例如客服查询订单：

```text
10:00 第一次查询 → 待支付
10:01 用户支付并提交
10:02 第二次查询 → 已支付
```

这里前后结果不同反而符合需求，因为客服关心的是当前最新状态，而不是保持第一次查询的旧视角。

它不适合一个事务执行多条统计 SQL，并要求所有结果使用同一个数据时间点的场景。

> [!tip] 场景关键词
> “每次刷新都想看到最新提交结果”，优先考虑 `READ COMMITTED`。

#### 4.6.3 REPEATABLE READ：适合需要稳定快照的多次查询

它让同一事务中的普通一致性读通常复用同一个快照，适合多次查询必须保持统一观察口径的场景。

例如生成财务报表需要依次查询：

```text
订单总数
订单总金额
退款总金额
最终收入
```

如果使用 `READ COMMITTED`，其他事务在查询过程中不断提交订单，不同指标可能来自不同时间点：

```text
订单总数   → 基于 10:00 的数据
订单总金额 → 基于 10:01 的数据
退款总金额 → 基于 10:02 的数据
```

每个结果单独看都是真的，但整份报表可能对不上。使用 `REPEATABLE READ` 时，这些普通查询通常基于同一个快照，统计口径能够保持一致。

其他适合的场景：

- 对账时多次读取并比较同一批数据；
- 库存盘点需要固定一个观察时间点；
- 批量计算要求输入来自同一个数据版本；
- 分页导出希望本次看到的数据集合保持稳定；
- 没有明确理由修改隔离级别时，沿用 InnoDB 默认设置。

分页导出示例：

```sql
SELECT * FROM user ORDER BY id LIMIT 0, 100;
SELECT * FROM user ORDER BY id LIMIT 100, 100;
SELECT * FROM user ORDER BY id LIMIT 200, 100;
```

稳定快照可以减少导出期间因数据集合变化产生的统计口径问题，但事务不能保持太久。长事务会占用连接和资源，还会让旧版本及 undo log 长时间无法清理；大量导出还应考虑主键游标分页、只读副本或专门的导出方案。

> [!tip] 场景关键词
> “这次分析必须始终基于同一个时间点”，优先考虑 `REPEATABLE READ`。

#### 4.6.4 SERIALIZABLE：适合低并发但要求严格顺序的特殊流程

它通过更严格的锁和等待，让冲突事务尽量排队执行，正确性直观，但并发性能最低。

可以考虑的场景：

- 数据量小、频率低，但必须严格顺序完成的结算流程；
- 系统维护期间执行关键配置或数据迁移校验；
- 复现并发异常时，临时使用最高隔离级别做对比；
- 业务吞吐量很低，愿意用等待换取简单性。

例如每天执行一次的小规模结算：

```text
结算事务开始
→ 读取待结算记录并持有相关锁
→ 其他冲突事务等待
→ 完成计算并提交
→ 释放锁，其他事务继续
```

它不适合秒杀、抢购、高频支付和大量用户同时修改订单等高并发业务，否则容易出现大量锁等待、超时和死锁。这些业务通常应该用唯一约束、条件更新、合理索引、悲观锁或乐观锁解决具体冲突。

> [!tip] 场景关键词
> “数据量小、并发低、必须严格排队，而且可以接受等待”，才考虑 `SERIALIZABLE`。

#### 4.6.5 最终怎么选择

| 业务目标 | 更适合的选择 | 原因 |
| --- | --- | --- |
| 允许读取尚未提交的临时数据 | `READ UNCOMMITTED` | 准确性最低，普通业务基本不用 |
| 每次查询尽量看到最新提交结果 | `READ COMMITTED` | 每条普通查询获取新的已提交版本 |
| 多次查询需要统一统计口径 | `REPEATABLE READ` | 同一事务的普通一致性读通常复用同一快照 |
| 低并发流程必须严格排队 | `SERIALIZABLE` | 用更多锁和等待换取最高隔离程度 |
| 余额、库存等并发修改 | 不能只靠隔离级别 | 还要使用原子更新、悲观锁或乐观锁 |

面试时可以这样回答：

1. `READ UNCOMMITTED` 会产生脏读，普通业务基本不用。
2. 查询最新状态或高并发短事务，可以考虑 `READ COMMITTED`。
3. 报表、对账和多次查询需要稳定快照，使用 `REPEATABLE READ`。
4. 只有低并发、严格顺序比性能更重要时，才考虑 `SERIALIZABLE`。
5. 隔离级别不能代替业务并发控制，余额、库存和幂等仍要依赖条件更新、锁、版本号与数据库约束。

## 五、🔄 理论：用“支付账单”看懂 MVCC

先别背 `Read View` 和 `DB_ROLL_PTR`。把场景放进真实系统：**用户刚付完款，客服正在查询账单，财务同时在生成对账报表。**

三个人想看的其实不是同一份数据：

| 角色 | 真正想看到什么 |
| --- | --- |
| 支付服务 | 必须修改当前最新余额和订单状态 |
| 客服 | 每次刷新都想看到最新已提交状态 |
| 财务报表 | 整份报表必须基于同一个时间点，不能算到一半口径变了 |

MVCC 的作用，就是让不同事务在不互相堵死的情况下，拿到**对自己可见的版本**。

> [!tip] 一句话理解
> MVCC 很像文档的“历史版本”：写操作继续编辑最新版，普通查询根据自己的快照，查看最新版或某个旧版本。

### 5.1 真实场景：支付正在改余额，客服此时查询

账户余额原来是 `1000` 元。支付事务 A 正在扣款 `100` 元，但还没有提交：

```text
10:00:00  已提交版本：余额 1000
10:00:01  事务 A 把最新版改成 900，但尚未提交
10:00:02  事务 B（客服查询）执行普通 SELECT
```

如果没有历史版本，事务 B 只有两个糟糕选择：

- 等事务 A 提交，客服页面一直转圈；
- 直接显示 `900`，但事务 A 之后可能回滚，这就是脏读。

MVCC 给了第三个选择：

```text
支付事务 A → 继续处理尚未提交的 900
客服事务 B → 先看到已经提交、对自己可见的 1000
```

两边都能继续工作。这里的 `1000` 不是缓存中的假数据，而是 InnoDB 根据 undo log 重建出的旧版本。

### 5.2 版本链：数据库怎样找回旧余额

InnoDB 在聚簇索引记录里维护事务信息。初学时只记两个隐藏字段：

| 隐藏字段 | 正式作用 | 放进支付场景怎么理解 |
| --- | --- | --- |
| `DB_TRX_ID` | 记录最后插入或修改该行的事务 ID | “这一版余额是谁改的” |
| `DB_ROLL_PTR` | 指向相关 undo log 记录 | “上一版余额去哪里找” |

假设这笔账户余额经历过几次变化：

```text
余额 900，事务 120 修改       ← 当前记录，支付尚未提交
    │ DB_ROLL_PTR
    ▼
余额 1000，事务 105 修改      ← undo log 可重建的上一版
    │ DB_ROLL_PTR
    ▼
余额 1200，事务 90 修改       ← 更早的一版
```

这就是**版本链**。它不是把整张 `account` 表复制三遍，而是用当前记录配合 undo log，按需还原旧内容。

> [!info] `DB_ROW_ID` 先放一边
> InnoDB 还可能维护隐藏的 `DB_ROW_ID`，用于缺少合适主键或唯一非空索引时构建聚簇索引。它不是这次判断版本可见性的重点。

### 5.3 Read View：客服到底能看哪一版

版本链解决了“旧数据在哪里”，还缺一个问题：**当前事务有资格看哪一版？**

Read View 可以理解为查询拍下的一张“事务合影”。它会记住拍照时：

- 哪些事务仍在处理中，还没有提交；
- 哪些事务已经在拍照前完成；
- 哪些事务是在拍照后才出现的；
- 当前版本是不是查询事务自己改出来的。

真正做判断时，可以把 Read View 简化成四份信息：

| 教学名称 | 记录什么 | 白话理解 |
| --- | --- | --- |
| `creator_trx_id` | 创建 Read View 的事务 ID | “是不是我自己改的” |
| `m_ids` | 创建 Read View 时仍然活跃的事务 ID 集合 | “拍照时这些事务还没交卷” |
| `min_trx_id` | `m_ids` 中最小的事务 ID | “比它还早的事务通常已经交卷” |
| `max_trx_id` | 创建 Read View 时尚未分配的下一个事务 ID | “从这里开始的事务都是拍照后才来的” |

拿到一个行版本后，InnoDB 检查这个版本的 `DB_TRX_ID`，按下面的顺序判断：

```text
1. DB_TRX_ID == creator_trx_id
   → 是当前事务自己改出的版本
   → 可见

2. DB_TRX_ID < min_trx_id
   → 修改者在快照创建前通常已经提交
   → 可见

3. DB_TRX_ID >= max_trx_id
   → 修改者在快照创建后才出现
   → 不可见

4. min_trx_id <= DB_TRX_ID < max_trx_id
   → 再检查 DB_TRX_ID 是否在 m_ids 中
   → 在：拍照时仍未提交，不可见
   → 不在：拍照时已经提交，可见
```

> [!tip] 其实只问两个问题
> 这个版本是**快照建立前已经提交**的吗？或者是**我自己改的**吗？是，就能看；否则先跳过，沿版本链继续往前找。

回到刚才的支付场景。客服创建 Read View 时，支付事务 120 仍未提交：

```text
最新版：余额 900，来自事务 120
→ 拍照时事务 120 仍在处理中
→ 这一版对客服不可见
→ 沿 DB_ROLL_PTR 往前找

上一版：余额 1000，来自事务 105
→ 事务 105 在拍照前已经提交
→ 这一版可见
→ 返回 1000
```

再看一次完整演算。假设 Read View 中记录：

```text
creator_trx_id = 108
m_ids          = [100, 107]
min_trx_id     = 100
max_trx_id     = 110
```

某行从新到旧有三个版本：

```text
版本一：DB_TRX_ID = 112，余额 700
版本二：DB_TRX_ID = 107，余额 800
版本三：DB_TRX_ID = 105，余额 900
```

InnoDB 会这样找：

```text
先看版本一：112 >= 110
→ 事务 112 在快照建立后才出现
→ 不可见，沿 DB_ROLL_PTR 找上一版

再看版本二：107 位于 [100, 110)，而且在 m_ids 中
→ 拍照时事务 107 还没有提交
→ 不可见，继续找上一版

再看版本三：105 位于 [100, 110)，但不在 m_ids 中
→ 拍照时事务 105 已经提交
→ 可见，最终返回余额 900
```

所以 MVCC 不是先算出“应该读第几个版本”，而是从最新版本开始逐个验票：**可见就返回，不可见就沿 `DB_ROLL_PTR` 继续找，直到找到可见版本或确认该行对当前快照不存在。**

所以一次普通查询的实际思路是：

```text
执行普通 SELECT
→ 创建或复用 Read View
→ 先检查最新记录
→ 最新版不可见，就沿 DB_ROLL_PTR 找 undo log
→ 找到第一个可见版本
→ 返回结果
```

> [!tip] 面试不用背成数学题
> 常见资料会列出 `m_ids`、`min_trx_id`、`max_trx_id`、`creator_trx_id`。理解重点不是背变量名，而是能解释：Read View 记录创建时的活跃事务，并用这些信息决定行版本是否可见。

### 5.4 客服查询与财务报表：为什么需要两种快照策略

现在换成两个真实需求：

#### 5.4.1 客服查询：每次刷新都要最新状态

客服查订单时，希望用户付款后立刻能看到 `PAID`：

```text
10:00 第一次查询 → PENDING
10:01 支付事务提交 → PAID
10:02 第二次查询 → PAID
```

这适合 `READ COMMITTED`：每次普通一致性读通常创建新的 Read View，所以第二次查询能看到刚提交的数据。

#### 5.4.2 财务报表：整份报表必须使用同一口径

财务任务要依次计算订单数、支付金额和退款金额：

```text
10:00 查订单数
10:01 查支付金额
10:02 查退款金额
```

如果三条 SQL 各看各的最新数据，计算期间又有订单提交，三项指标可能来自三个时间点。每项单独都没错，合在一起却对不上。

这适合 `REPEATABLE READ`：事务第一次普通一致性读建立快照，后续普通一致性读通常复用它，让整份报表像基于同一张截图计算。

| 隔离级别 | Read View 策略 | 更像什么 | 典型场景 |
| --- | --- | --- | --- |
| `READ COMMITTED` | 每次普通一致性读通常创建新的 Read View | 不断刷新的直播 | 客服查订单、后台看物流 |
| `REPEATABLE READ` | 同一事务后续普通一致性读通常复用快照 | 固定时间点的截图 | 对账、报表、批量分析 |

> [!warning] 准确说法
> `REPEATABLE READ` 的一致性快照通常在事务中的第一次普通一致性读时建立，不一定在 `START TRANSACTION` 那一刻建立。需要立刻建立快照时，可以了解 `START TRANSACTION WITH CONSISTENT SNAPSHOT`。

### 5.5 快照读和当前读：看账单与扣款不是一回事

如果只是展示余额，读一个符合当前事务视角的版本即可：

```sql
-- 快照读：适合“只查看”。
SELECT balance FROM account WHERE id = 1;
```

但如果接下来要扣款，就不能拿历史余额做决定：

```sql
-- 锁定读：读取当前记录并锁住，适合“查完还要改”。
SELECT balance FROM account WHERE id = 1 FOR UPDATE;

-- UPDATE、DELETE 也要围绕当前数据执行并处理锁冲突。
UPDATE account
SET balance = balance - 100
WHERE id = 1 AND balance >= 100;
```

| 问题 | 快照读 | 当前读或锁定操作 |
| --- | --- | --- |
| 典型语句 | 普通 `SELECT` | `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` |
| 想解决什么 | 快速查看合适版本 | 基于当前数据安全地修改 |
| 主要机制 | Read View、undo 版本链 | 当前记录、行锁和范围锁 |
| 会不会读历史版本 | 可能 | 通常需要读取较新的当前版本 |

最实用的判断方法：

```text
只是展示数据？
→ 普通 SELECT，让 MVCC 处理

查完要根据结果修改？
→ 原子 UPDATE，或在事务中 SELECT ... FOR UPDATE
```

### 5.6 MVCC 解决不了哪些真实问题

#### 5.6.1 秒杀库存：两个人都想买最后一件

商品只剩 1 件。两个请求都用普通 `SELECT` 读到库存为 1，MVCC 完全可以让两边都拿到可见版本，但它不会自动决定谁购买成功。

安全做法之一是直接条件更新：

```sql
UPDATE product
SET stock = stock - 1
WHERE id = 1001
  AND stock > 0;
```

只有影响行数为 `1` 才表示抢购成功；影响行数为 `0` 表示库存不足。

#### 5.6.2 长报表事务：旧版本一直不能清理

如果财务报表开着一个事务跑几小时，InnoDB 可能必须保留它仍可能看到的旧版本。结果是 undo log 无法及时清理、历史链变长，存储和查询压力都可能增加。

所以即使是只读事务，也应该及时提交；大规模导出还要考虑只读副本、分批处理或专门的离线方案。

#### 5.6.3 写写冲突：两个人同时改同一行

MVCC 擅长减少“普通读与写”之间的阻塞，但两个事务同时写同一行时，仍然必须靠锁排队。

> [!tip] 第五章只记这一条
> **MVCC 负责“我应该看哪一版”，锁负责“谁可以先改当前版”。**

### 5.7 MVCC 的完整心智模型

```text
业务执行普通 SELECT
→ InnoDB 创建或复用 Read View
→ 先查看记录的最新版本
→ 用事务信息判断最新版是否可见
→ 不可见就沿 DB_ROLL_PTR 查找 undo log
→ 返回第一个可见版本

业务要修改数据
→ 不能只依赖历史版本
→ 读取并修改当前数据
→ 使用锁协调写入顺序
```

面试时可以这样回答：

> InnoDB 通过记录中的 `DB_TRX_ID`、`DB_ROLL_PTR` 和 undo log 形成版本链，再用 Read View 判断版本可见性。普通 `SELECT` 可以沿版本链读取合适的历史版本，因此常常不必等待写事务；`READ COMMITTED` 通常每次一致性读创建新 Read View，`REPEATABLE READ` 通常复用同一事务的快照。MVCC 主要优化普通读写并发，当前读和写写冲突仍然需要锁。

## 六、🔒 理论：用“秒杀和转账”看懂 InnoDB 锁

锁最容易学枯燥，是因为只看 S 锁、X 锁、Gap Lock，像在背缩写。换成业务问题就简单了：

```text
秒杀最后一件商品 → 谁先扣库存？
后台领取待处理订单 → 领取后别人还能不能同时处理？
范围扫描待支付订单 → 扫描期间能不能插入新订单？
两人互相转账 → 为什么会死锁？
```

锁就是数据库对这些问题给出的“排队规则”。

### 6.1 场景一：秒杀最后一件商品

商品库存只剩 `1`，请求 A 和请求 B 同时到达。下面这种写法有风险：

```text
A 普通 SELECT → stock = 1
B 普通 SELECT → stock = 1
A 在程序里计算 1 - 1，写回 0
B 也在程序里计算 1 - 1，写回 0
```

两个请求都可能告诉用户“购买成功”。问题不在于有没有读到历史版本，而在于**两个写操作必须竞争同一份当前库存**。

#### 6.1.1 首选：一条原子条件更新

```sql
UPDATE product
SET stock = stock - 1
WHERE id = 1001
  AND stock > 0;
```

执行后检查影响行数：

| 影响行数 | 业务含义 |
| --- | --- |
| `1` | 成功扣减库存 |
| `0` | 商品不存在或库存已经不足 |

InnoDB 会对实际修改的索引记录加排他锁。先拿到锁的请求完成修改；另一个请求等待后会基于最新库存重新判断条件，不会凭旧的 `stock = 1` 再扣一次。

#### 6.1.2 复杂判断：先锁定，再处理

如果购买前还要检查会员资格、限购次数等多个数据库条件，可以在一个短事务里锁住商品行：

```sql
START TRANSACTION;

SELECT stock
FROM product
WHERE id = 1001
FOR UPDATE;

-- 在同一事务内完成必要判断和更新。
UPDATE product
SET stock = stock - 1
WHERE id = 1001
  AND stock > 0;

COMMIT;
```

请求 A 持有锁时，请求 B 的冲突锁定读或更新会等待。普通 `SELECT` 通常仍可借助 MVCC 读取合适快照，这说明“锁了一行”不等于“所有人都不能看”。

> [!warning] 别把远程调用放在锁里面
> 获取 `FOR UPDATE` 锁之后，不要再调用支付网关、发送短信或等待用户输入。远程调用越久，锁持有越久，后面的请求排队越严重。

### 6.2 普通 SELECT 与 FOR UPDATE：看库存和占库存

```sql
-- 商品详情页展示库存：只看，不承诺接下来由我修改。
SELECT stock FROM product WHERE id = 1001;

-- 下单流程准备修改库存：读当前记录并加排他锁。
SELECT stock FROM product WHERE id = 1001 FOR UPDATE;
```

可以用一句话区分：

```text
普通 SELECT     = 我看一眼库存
SELECT FOR UPDATE = 这条库存我马上要改，冲突操作先排队
```

锁定读只有放在事务中才有实际意义。如果开启自动提交、语句执行完立即提交，锁也会立即释放，无法保护后续多条语句。

### 6.3 共享锁和排他锁：审核人员与处理人员

假设风控人员要审核一笔订单，处理人员要修改这笔订单：

| 锁 | SQL | 业务含义 | 谁会被挡住 |
| --- | --- | --- | --- |
| 共享锁（S Lock） | `FOR SHARE` | 我正在审核，请暂时别改 | 冲突的排他锁 |
| 排他锁（X Lock） | `FOR UPDATE` 或写操作 | 这条记录我要修改 | 冲突的共享锁和排他锁 |

```sql
-- 多个审核者可以同时持有兼容的共享锁。
SELECT * FROM orders WHERE id = 5001 FOR SHARE;

-- 处理者准备修改订单，获取排他锁。
SELECT * FROM orders WHERE id = 5001 FOR UPDATE;
```

大白话理解：共享锁像“大家可以同时看，但暂时不准改”；排他锁像“我正在改，冲突操作先等我完成”。

### 6.4 意向锁：商场门口的状态牌

假设一张表是商场，每一行是一家店。某事务要锁住第 101 号店，不需要封锁整个商场，但会先在商场门口挂一块状态牌：

```text
IS：里面有店铺正在加共享锁
IX：里面有店铺正在加排他锁
```

这块牌子就是表级的**意向锁**。它不是把整张表的数据锁住，而是帮助另一个想加表锁的事务快速判断：表内是否已经存在可能冲突的行锁，不必逐行检查。

| 意向锁 | 表达的意思 |
| --- | --- |
| IS（意向共享锁） | 准备在表中的某些记录上加共享锁 |
| IX（意向排他锁） | 准备在表中的某些记录上加排他锁 |

> [!tip] 面试够用
> 意向锁是表级锁，用来协调表锁和行锁；它表达“表内某些记录将持有什么锁”，不等于直接锁住整张表的全部数据。

### 6.5 场景二：为什么只锁现有订单还不够

运营任务准备处理所有金额在 `100` 到 `500` 元之间的待支付订单：

```sql
SELECT *
FROM orders
WHERE amount BETWEEN 100 AND 500
  AND status = 'PENDING'
FOR UPDATE;
```

假设金额索引中目前只有：

```text
100、300、500
```

如果只锁住这三条已有记录，另一个事务仍可插入金额 `200` 的待支付订单。运营任务再次按相同范围查询时，就会突然多出一条。这就是范围操作为什么还要关心“空隙”。

| 锁类型 | 锁住什么 | 放进订单场景 |
| --- | --- | --- |
| Record Lock | 已存在的索引记录 | 锁住金额 `300` 的订单 |
| Gap Lock | 索引记录之间的间隙 | 锁住 `100` 与 `300` 之间可插入的位置 |
| Next-Key Lock | 记录及其前面的间隙 | 同时保护已有订单和相邻插入范围 |

```text
索引值：100 -------- 300 -------- 500
             ↑
      想插入 amount = 200

如果相关间隙被锁住，这次插入就需要等待。
```

在 InnoDB 默认的 `REPEATABLE READ` 下，范围锁定读或范围修改可能使用 next-key lock，防止其他事务向扫描范围插入新记录，从而处理常见幻读问题。

> [!warning] 图只是心智模型
> 真实加锁范围由隔离级别、索引结构、查询条件和执行计划共同决定。不能只看 `WHERE` 条件，就断言一定锁住哪一段。

### 6.6 场景三：为什么没索引会让锁冲突变严重

InnoDB 的行锁实际加在**索引记录**上。索引决定数据库为了找到目标数据要扫描多少记录，也会影响可能触及的加锁范围。

```sql
-- 主键精确定位，通常很快找到目标记录。
SELECT * FROM orders WHERE id = 5001 FOR UPDATE;

-- status 没有合适索引时，可能需要扫描大量记录。
SELECT * FROM orders WHERE status = 'PENDING' FOR UPDATE;
```

假设订单表有 100 万行，但待支付订单只有 20 行：

```text
有合适索引
→ 沿索引定位 20 条待支付订单
→ 扫描和锁定目标更集中

没有合适索引
→ 为找 20 条记录扫描大量索引记录
→ 锁持有时间和冲突风险都可能上升
```

所以线上出现锁等待时，不要只盯着事务代码，还要检查 [[MySQL 索引]] 和实际执行计划。

### 6.7 悲观锁、乐观锁和原子更新怎么选

还是用抢库存来比较：

| 方案 | 思路 | 适合场景 | 代价 |
| --- | --- | --- | --- |
| 原子条件更新 | 一条 SQL 同时判断并扣减 | 规则能写进 `WHERE` 的库存、余额更新 | 复杂业务判断不一定能塞进一条 SQL |
| 悲观锁 | 先 `FOR UPDATE` 锁住，再判断和修改 | 冲突多、步骤必须串行 | 会产生等待，事务必须短 |
| 乐观锁 | 更新时检查版本号 | 冲突较少、可以重试 | 冲突后本次更新失败，需要重试或提示 |

乐观锁示例：

```sql
UPDATE product
SET stock = stock - 1,
    version = version + 1
WHERE id = 1001
  AND stock > 0
  AND version = 7;
```

如果另一个请求先修改了商品，版本号就不再是 `7`，当前更新影响行数为 `0`。应用必须把它当成一次并发失败，选择重新读取后有限重试，或直接告诉用户抢购失败。

> [!tip] 实战优先级
> 能用一条条件 `UPDATE` 安全完成时，通常先用原子更新；业务必须“先查再做多步判断”时考虑悲观锁；冲突较少且业务允许重试时考虑乐观锁。

### 6.8 场景四：转账为什么会死锁

用户 A 向用户 B 转账，同时用户 B 又向用户 A 转账：

| 时间 | 事务 1：A 转给 B | 事务 2：B 转给 A |
| --- | --- | --- |
| ① | 锁住账户 A | 锁住账户 B |
| ② | 等待账户 B | 等待账户 A |
| ③ | 无法继续 | 无法继续 |

```text
事务 1 持有 A，等待 B
事务 2 持有 B，等待 A
→ 形成环形等待
→ 死锁
```

InnoDB 检测到死锁后，通常会回滚其中一个事务，让另一个继续。死锁不是数据库“卡死了”，而是数据库主动牺牲一个事务来拆掉等待环。

最有效的改法之一，是规定所有转账都按账户 ID 从小到大加锁：

```text
无论 A 转 B，还是 B 转 A
→ 都先锁较小的账户 ID
→ 再锁较大的账户 ID
→ 两个事务不会反向各拿一把锁
```

生产代码还应做到：

- 捕获死锁错误，只对适合重试的短事务做有限次数重试；
- 保证转账请求幂等，避免重试造成重复扣款；
- 缩短事务，不在持锁期间调用远程服务；
- 使用合适索引，减少扫描和锁定范围；
- 分批处理大量数据，避免一次事务持有太多锁。

### 6.9 把锁类型放回真实场景

| 业务动作 | 主要机制 | 为什么 |
| --- | --- | --- |
| 商品详情页查看库存 | MVCC 快照读 | 只展示数据，尽量不阻塞写入 |
| 秒杀扣一件库存 | 原子 `UPDATE` + 排他锁 | 必须围绕当前库存安全扣减 |
| 查完库存还要做多步判断 | `SELECT ... FOR UPDATE` | 防止判断到更新之间被别人改掉 |
| 审核记录且暂时不允许修改 | `FOR SHARE` | 多人可审核，冲突修改需等待 |
| 锁定金额范围内的订单 | Record/Gap/Next-Key Lock | 同时保护现有记录和相关插入范围 |
| 两个账户互相转账 | 排他锁 + 统一加锁顺序 | 防止反向持锁形成死锁 |

> [!tip] 第六章只记这一条
> **锁不是为了让数据库变慢，而是让会破坏结果的并发操作排队；索引决定“去哪找数据”，也会影响锁触及多大范围。**

## 七、🚀 实践：观察一次行锁等待

### 7.1 前置准备

- MySQL 8.0 或 8.4；
- 使用 InnoDB 测试表；
- 准备两个独立数据库连接，分别作为事务 A 和事务 B；
- 下面包含建表和写入，只能在个人测试库练习，不要在共享库或生产库直接执行。

### 7.2 准备测试数据

```sql
CREATE TABLE lock_demo_account (
    id BIGINT PRIMARY KEY,
    balance DECIMAL(12, 2) NOT NULL
) ENGINE = InnoDB;

INSERT INTO lock_demo_account(id, balance) VALUES (1, 1000.00);
```

### 7.3 事务 A 锁住记录

在连接 A 中执行：

```sql
START TRANSACTION;

SELECT balance
FROM lock_demo_account
WHERE id = 1
FOR UPDATE;

-- 暂时不要提交，用来观察另一个事务等待。
```

### 7.4 事务 B 尝试修改同一记录

在连接 B 中执行：

```sql
START TRANSACTION;

UPDATE lock_demo_account
SET balance = balance - 100
WHERE id = 1;
```

连接 B 会等待，因为连接 A 持有目标记录的排他锁。

回到连接 A 执行：

```sql
COMMIT;
```

连接 A 释放锁后，连接 B 才能继续。最后在连接 B 中提交：

```sql
COMMIT;
```

这个实验说明：锁不是让所有事务都停止，而是让访问同一冲突资源的事务按照顺序继续。

## 八、🎤 高频面试题

### 8.1 MySQL 默认隔离级别是什么

> InnoDB 默认是 `REPEATABLE READ`。普通一致性读通常复用同一个 Read View；当前读和增删改读取较新的数据并加锁。范围当前读还可能使用 next-key lock 控制范围内插入。

### 8.2 MVCC 能完全代替锁吗

> 不能。MVCC 主要通过 Read View 和 undo 版本链优化普通快照读；写写冲突、当前读和锁定读仍然需要锁。

### 8.3 READ COMMITTED 和 REPEATABLE READ 有什么区别

> `READ COMMITTED` 每次普通一致性读通常创建新的 Read View，更关注最新已提交数据；`REPEATABLE READ` 通常复用第一次一致性读建立的 Read View，更关注同一事务内数据视角稳定。

### 8.4 什么是 next-key lock

> next-key lock 可以理解为记录锁与记录前间隙锁的组合。InnoDB 在范围当前读或范围修改中使用它保护已存在的索引记录及相关插入范围，从而处理常见幻读问题。

### 8.5 如何减少死锁

> 保持一致的资源访问顺序，缩短事务，使用合适索引缩小加锁范围，避免大事务；应用还要捕获死锁异常，对适合重试的短事务进行有限重试并保证幂等。

## 九、📌 快速回顾

```text
隔离级别       = 决定并发事务之间能看到什么
READ COMMITTED = 每次普通查询看最新已提交版本
REPEATABLE READ = 同一事务普通查询通常复用快照
MVCC           = Read View + undo 版本链
快照读         = 普通 SELECT，可能读取历史版本
当前读         = 读取较新数据并结合锁控制冲突
Record Lock    = 锁已有索引记录
Gap Lock       = 锁索引记录之间的间隙
Next-Key Lock  = 记录锁 + 间隙锁
```

最适合面试复述的一句话：

> InnoDB 使用隔离级别规定并发可见性，使用 MVCC 让普通 SELECT 读取合适的历史版本，使用记录锁、间隙锁和 next-key lock 控制当前读与写入冲突；锁实际加在索引记录上，所以索引设计会直接影响加锁范围和并发性能。
