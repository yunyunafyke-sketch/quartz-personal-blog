## 一、💡 一句话理解

> [!tip] 核心结论
> 多个事务同时操作数据时，数据库必须决定“谁能看到哪份数据”和“谁需要等待”。隔离级别负责制定规则，InnoDB 主要通过历史版本和锁来执行这些规则。

先不着急背术语，只记住这条主线：

```text
多个事务同时操作同一批数据
→ 可能产生脏读、不可重复读、幻读或丢失更新
→ 隔离级别规定要防住哪些问题
→ InnoDB 再使用历史版本和锁实现这些规则
```

## 二、🧭 理论：先认识并发、锁和 MVCC

### 2.1 为什么学完事务还要学隔离和锁

事务的原子性只能保证“多条操作一起成功或一起失败”。它并不自动保证多个事务同时执行时不会互相干扰。

假设账户余额是 `1000`，两个用户几乎同时扣款：

```text
事务 A：读到 1000，准备扣 100
事务 B：也读到 1000，准备扣 200
```

如果没有并发控制，两个事务都可能根据同一个旧值计算，造成结果被覆盖。所以学完“事务是什么”以后，还必须学习事务之间如何相处。

```text
事务       = 划定一组操作的开始和结束
隔离级别 = 规定并发事务之间能看到什么
锁           = 让冲突的操作按顺序执行
MVCC         = 让普通查询可以读取合适的历史版本
```

### 2.2 数据库锁是什么

先把锁理解成一个非常简单的规则：

> [!tip] 锁的最小定义
> 当一个事务正在使用或修改某份数据时，数据库会限制其他事务对这份数据执行冲突操作。得不到锁的事务通常需要等待，或者返回失败。

可以把一行数据想成一间只有一块白板的会议室：

```text
事务 A 正在修改白板内容
→ 数据库给这份数据加上合适的锁
→ 事务 B 也想修改同一份数据
→ B 先等待
→ A 提交或回滚，锁被释放
→ B 才能继续
```

这个类比只用来理解“冲突操作需要排队”。真实的 InnoDB 锁有不同类型和范围，后文再逐步展开。

### 2.3 为什么不能所有读取都靠锁

如果普通查询一遇到正在修改的数据就必须等待，读写会经常互相堵住，并发性会很差。

假设余额原来是 `1000`，事务 A 正在把它修改为 `900`，但还没提交。此时事务 B 进行普通查询，有三种可能：

| 做法 | 问题 |
| --- | --- |
| 让 B 一直等 A | 安全，但普通读取容易被写操作堵住 |
| 让 B 直接读未提交的 `900` | 可能读到以后会被回滚的脏数据 |
| 让 B 读取对自己可见的旧版本 `1000` | 既不必等待，也不会看到未提交数据 |

第三种做法就是理解 MVCC 的起点。

### 2.4 MVCC 是什么

MVCC 的全称是 Multi-Version Concurrency Control，即“多版本并发控制”。此时只需要记住：

> [!tip] MVCC 的最小定义
> 同一行数据被修改后，InnoDB 仍能根据修改记录找到较旧的版本。普通查询可以按照当前事务的读取视角，选择自己应该看到的版本。

```text
最新版本：900，正在被事务 A 修改
历史版本：1000，对事务 B 仍然可见

事务 B 执行普通 SELECT
→ 不必去读 A 未提交的 900
→ 也不一定要等 A 结束
→ 可以返回对自己可见的 1000
```

这里先理解目的就够了。历史版本保存在哪里、Read View 怎么判断可见性，会在第五章详细说明。

### 2.5 本篇的学习顺序

```text
先看并发事务会造成什么问题
→ 再看四种隔离级别分别允许什么
→ 再理解 MVCC 如何为普通查询选择版本
→ 然后理解 MVCC 和锁的正式分工
→ 最后深入具体锁类型、加锁范围和死锁
```

> [!warning] 暂时不要死背细节
> 刚开始只要能说出“锁让冲突操作排队，MVCC 让普通查询可以选择合适的历史版本”就够了。

## 三、⚠️ 理论：并发事务会产生什么问题

| 问题 | 现象 |
| --- | --- |
| 脏读 | 读到了其他事务尚未提交的数据，之后对方可能回滚 |
| 不可重复读 | 同一事务两次读取同一行，值发生了变化 |
| 幻读 | 同一事务两次按相同条件查询，结果行数发生了变化 |
| 丢失更新 | 两个事务都根据同一个旧值计算新值，后写入的结果覆盖先写入的结果 |

下面的事务 A 和事务 B 表示两个独立的数据库连接。SQL 只用于解释执行顺序，假设示例表和数据已经存在；如需动手验证，只能在个人测试库中进行。

### 3.1 脏读是怎么产生的

先用生活例子理解：同事正在修改一份共享表格，还没有点击“保存”，你却看到了他的临时数字，并拿这个数字去做决定。后来同事发现写错了，撤销了修改。你刚才看到的数字从来没有正式生效，这就是“读到了脏数据”。

假设账户 A 的余额原来是 `1000` 元：

| 时间 | 事务 A | 事务 B |
| --- | --- | --- |
| ① | 开始事务 |  |
| ② | 把余额从 `1000` 改成 `900`，但是**没有提交** |  |
| ③ |  | 读取余额，竟然读到尚未提交的 `900` |
| ④ | 发现操作有误，执行 `ROLLBACK`，余额恢复为 `1000` |  |
| ⑤ |  | 此时才发现刚才读到的 `900` 从未真正生效 |

对应的执行顺序可以简化为：

```sql
-- 事务 A
START TRANSACTION;
UPDATE account SET balance = 900 WHERE id = 1;
-- 暂时不提交
```

```sql
-- 事务 B：只有允许读取未提交数据时，才可能看到这种结果。
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
START TRANSACTION;
SELECT balance FROM account WHERE id = 1;
-- 读到 900，但事务 A 还没有提交。
```

```sql
-- 事务 A 后来撤销修改。
ROLLBACK;
-- 数据库中的余额重新变成 1000。
```

问题在于：事务 B 可能已经根据不存在的 `900` 拒绝付款、发送通知或执行其他业务操作。

> [!tip] 判断关键词
> 脏读的关键不是“两次读取结果不同”，而是**读到了其他事务尚未提交、以后还可能被回滚的数据**。

### 3.2 不可重复读是怎么产生的

生活中可以理解为：你在同一张商品详情页里先看到价格是 100 元；工作人员正式修改并保存价格后，你刷新页面看到 120 元。同一个商品还在，但同一字段前后两次读到的值不同。

仍然假设账户余额原来是 `1000` 元：

| 时间 | 事务 A | 事务 B |
| --- | --- | --- |
| ① |  | 开始事务，第一次读取余额，得到 `1000` |
| ② | 开始事务，把余额改成 `900` |  |
| ③ | 执行 `COMMIT`，修改正式生效 |  |
| ④ |  | 在同一个事务里再次读取同一账户，得到 `900` |

```sql
-- 事务 B：READ COMMITTED 下，每次普通查询会读取新的已提交版本。
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT balance FROM account WHERE id = 1;
-- 第一次得到 1000。
```

```sql
-- 事务 A 在两次查询之间提交修改。
START TRANSACTION;
UPDATE account SET balance = 900 WHERE id = 1;
COMMIT;
```

```sql
-- 事务 B 仍处于原来的事务中，再查一次同一行。
SELECT balance FROM account WHERE id = 1;
-- 第二次得到 900。
COMMIT;
```

这不是脏读，因为事务 B 第二次读到的 `900` 已经由事务 A 提交。问题是：**事务 B 在同一个事务中重复读取同一行，结果却不能保持一致。**

> [!tip] 判断关键词
> 不可重复读关注的是**同一行数据的内容发生变化**，例如同一个账户的余额从 `1000` 变成 `900`。

### 3.3 幻读是怎么产生的

生活中可以理解为：你第一次统计“教室里穿红衣服的人”，数出 2 人；统计过程中又进来一个穿红衣服的人；你按照相同条件再数一次，变成了 3 人。原来的两个人没有变，但符合条件的结果集合中凭空多出了一行，好像出现了“幻影”。

假设订单表中原来只有 1 条待支付订单：

| 时间 | 事务 A | 事务 B |
| --- | --- | --- |
| ① |  | 开始事务，查询待支付订单，得到 1 条 |
| ② | 插入一条新的待支付订单 |  |
| ③ | 执行 `COMMIT`，新订单正式生效 |  |
| ④ |  | 使用完全相同的条件再次查询，得到 2 条 |

```sql
-- 事务 B 第一次按条件查询。
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT * FROM orders WHERE status = 'PENDING';
-- 第一次返回 1 行。
```

```sql
-- 事务 A 插入一条也符合 status = 'PENDING' 的记录并提交。
START TRANSACTION;
INSERT INTO orders(id, status) VALUES (2, 'PENDING');
COMMIT;
```

```sql
-- 事务 B 使用完全相同的条件再次查询。
SELECT * FROM orders WHERE status = 'PENDING';
-- 第二次返回 2 行。
COMMIT;
```

两次查询条件没有变化，但符合条件的记录集合发生了变化。新插入的记录像“幻影”一样出现在第二次结果中，所以叫幻读。其他事务删除符合条件的记录，也可能让第二次查询少一行。

> [!tip] 判断关键词
> 幻读关注的是**相同查询条件得到的记录集合发生变化**，常见表现是多了一行或少了一行；不可重复读关注的是同一行的字段值发生变化。

### 3.4 丢失更新是怎么产生的

假设账户余额是 `1000` 元，事务 A 支付 `100` 元，事务 B 支付 `200` 元。两个事务都采用“先查询，再由程序计算，最后把结果写回”的方式：

```text
事务 A 读取余额 1000
事务 B 也读取余额 1000

事务 A 计算 1000 - 100 = 900，并写入 900
事务 B 计算 1000 - 200 = 800，并写入 800
```

最终余额是 `800`，但正确结果应该是：

```text
1000 - 100 - 200 = 700
```

事务 B 写入的 `800` 覆盖了事务 A 已经写入的 `900`，导致事务 A 的扣款效果消失，这就是**丢失更新**。

常见解决办法：

- 直接执行原子更新：`UPDATE account SET balance = balance - 100 WHERE id = 1 AND balance >= 100;`
- 在事务中先用 `SELECT ... FOR UPDATE` 锁定目标行，再读取和修改。
- 使用版本号做乐观锁，更新时检查数据有没有被其他事务改过。

> [!warning] 不要混淆
> `UPDATE account SET balance = balance - 100` 由数据库基于当前值直接计算，与应用先读出 `1000`、计算出 `900`，再执行 `UPDATE account SET balance = 900` 不同。后者更容易覆盖其他事务的修改。

四种问题可以这样快速区分：

| 问题 | 最关键的判断点 |
| --- | --- |
| 脏读 | 读到了别人**还没提交**的数据，这个数据之后可能被回滚 |
| 不可重复读 | 同一事务重复读取**同一行**，已经提交的字段值发生了变化 |
| 幻读 | 同一事务使用相同条件重复查询，符合条件的**记录集合**多了或少了 |
| 丢失更新 | 两个事务根据同一个旧值计算，后写入的结果覆盖了先写入的结果 |

> [!tip] 大白话记忆
> **脏读**：偷看了别人还没保存的草稿，别人后来又撤销了。
>
> **不可重复读**：第一次看的是正式版本，别人保存了新版本，第二次再看时，同一条内容变了。
>
> **幻读**：第一次按条件点名有 2 个人，别人又正式加入了一个符合条件的人，第二次用相同条件点名变成 3 个人，像凭空冒出来一个“幻影”。
>
> **丢失更新**：两个人都拿同一个旧版本进行修改，后保存的人覆盖了先保存的人，导致前一个人的修改白做了。

隔离越强，并发事务越不容易互相影响，但等待和锁冲突通常也越多。因此数据库通过**隔离级别**在一致性和并发性能之间取舍。

## 四、🧱 理论：四种隔离级别

InnoDB 支持四种隔离级别，默认是 `REPEATABLE READ`。

先看面试最常用的结论：

| 隔离级别 | 能防止什么 | 仍可能发生什么 | 为什么 |
| --- | --- | --- | --- |
| `READ UNCOMMITTED` | 基本没有防住三种读异常 | 脏读、不可重复读、幻读 | 连其他事务尚未提交的数据都允许读取 |
| `READ COMMITTED` | 脏读 | 不可重复读、幻读 | 只读已提交数据，但每次查询都会读取当时最新的已提交版本 |
| `REPEATABLE READ` | 脏读、不可重复读；InnoDB 还能处理常见幻读问题 | 普通快照读通常不会出现前三种读异常，但当前读要结合锁理解 | 同一事务的普通一致性读通常复用同一快照；范围锁定操作还会使用 next-key lock |
| `SERIALIZABLE` | 脏读、不可重复读、幻读 | 三种经典读异常通常都不会发生 | 通过更严格的锁和等待，让事务尽量像排队一样执行 |

### 4.1 READ UNCOMMITTED：别人没提交也能读

这个级别几乎不限制普通读取。事务 A 把余额从 `1000` 改成 `900`，即使尚未提交，事务 B 也可能读到 `900`。

```text
事务 A：写入 900，但没有提交
事务 B：直接读到 900                 ← 脏读
事务 A：ROLLBACK，余额恢复成 1000
```

既然连未提交数据都能看到，就更无法保证同一行重复读取不变，也无法保证相同条件查询的记录集合不变。因此三个问题都可能发生。

> [!tip] 大白话
> `READ UNCOMMITTED` 相当于别人草稿还没保存，你就能偷看。

### 4.2 READ COMMITTED：解决脏读，但不能解决不可重复读

这个级别规定：**只能读取已经提交的数据。**

如果事务 A 把余额改成 `900` 但没有提交，事务 B 仍然只能读到之前已经提交的 `1000`，所以不会脏读。

```text
事务 A：写入 900，但没有提交
事务 B：只能读到已提交的 1000         ← 防止脏读
```

但是，`READ COMMITTED` 下每条普通查询都会读取执行这一刻最新的已提交版本：

```text
事务 B：第一次查询余额，得到 1000
事务 A：把余额改成 900，并且 COMMIT
事务 B：第二次查询余额，得到 900       ← 不可重复读
```

事务 B 第二次读到的 `900` 是合法的已提交数据，所以不属于脏读；但同一事务两次读取同一行的结果不同，因此属于不可重复读。

同样，如果事务 A 在两次查询之间提交了一条符合条件的新记录，事务 B 第二次查询时就会看到它，所以也可能发生幻读。

> [!tip] 为什么能防脏读，却防不了不可重复读
> 它只承诺“不给你看未提交的数据”，没有承诺“整个事务始终看同一个版本”。

### 4.3 REPEATABLE READ：同一事务通常看同一个快照

这是 InnoDB 的默认隔离级别。对于普通一致性读，事务第一次查询时会建立 Read View，后续普通查询通常继续使用同一个快照。

```text
事务 B：第一次查询余额，得到 1000，并建立快照
事务 A：把余额改成 900，并且 COMMIT
事务 B：第二次普通查询仍然得到 1000   ← 保持可重复读
```

事务 A 已经提交了 `900`，但它是在事务 B 的快照建立之后提交的，所以事务 B 的普通查询暂时看不到它。这样就避免了不可重复读。

如果事务 A 后来插入一条符合条件的新记录，事务 B 的普通快照读通常也看不到这条新记录，因此两次查询的结果集合能够保持一致。

不过要区分两种读取：

- 普通 `SELECT` 是**快照读**，主要使用 MVCC 和 Read View。
- `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 是**当前读或锁定操作**，要读取较新的数据并加锁。

InnoDB 对索引范围执行锁定读或修改时，还可能使用 next-key lock 锁住索引记录及其间隙，阻止其他事务在相关范围插入新记录，从而处理常见的幻读问题。

> [!warning] 面试容易混淆的地方
> 按 SQL 标准的常见隔离级别表格，`REPEATABLE READ` 仍可能出现幻读；但 MySQL InnoDB 结合 MVCC 和 next-key lock，能够处理常见的幻读场景。回答时最好明确说“MySQL InnoDB 的实现”。

### 4.4 SERIALIZABLE：让事务尽量排队执行

这是隔离程度最高的级别。可以把它理解为：多个事务对同一批数据的操作尽量排队，不让它们随意交叉执行。

```text
事务 A：读取或修改目标数据，并持有相关锁
事务 B：也想操作冲突的数据，只能等待
事务 A：COMMIT 或 ROLLBACK，释放锁
事务 B：继续执行
```

在关闭自动提交的事务中，InnoDB 会把普通 `SELECT` 隐式转换为共享锁定读。这样能避免三种经典读异常，但也会带来更多锁等待、降低并发能力，所以普通业务通常不会默认使用。

### 4.5 四个级别到底逐步增加了什么

```text
READ UNCOMMITTED
    什么版本都可能读
        ↓ 增加“只能读已提交数据”
READ COMMITTED
    防止脏读，但每次查询可能看到新版本
        ↓ 增加“同一事务复用快照”
REPEATABLE READ
    普通查询前后结果更稳定
        ↓ 增加更严格的锁和串行等待
SERIALIZABLE
    隔离最强，但并发性能最低
```

> [!tip] 最简单的记忆方法
> `READ COMMITTED` 只保证“读到的是真的”；`REPEATABLE READ` 进一步保证“这次事务里反复读，看到的版本尽量不变”；`SERIALIZABLE` 则让有冲突的事务尽量排队。

> [!info] 丢失更新要单独理解
> 上面的隔离级别对比主要讨论脏读、不可重复读和幻读三种经典读异常。业务代码如果采用“先读旧值、在程序中计算、再把绝对值写回”的方式，仍要注意丢失更新；通常使用原子 `UPDATE`、`SELECT ... FOR UPDATE` 或版本号乐观锁解决。

### 4.6 四种隔离级别的实际场景与选择

先用一句话记住最常比较的两个级别：

```text
READ COMMITTED  = 实时直播
REPEATABLE READ = 某个时间点的截图
```

直播不断更新，但前后看到的内容可能不同；截图可能不是最新的，但分析截图时内容不会突然变化。

| 隔离级别 | 典型定位 | 普通业务是否常用 |
| --- | --- | --- |
| `READ UNCOMMITTED` | 可以接受脏数据的临时观察或实验 | 几乎不用 |
| `READ COMMITTED` | 关注最新已提交结果的高并发短事务 | 常用 |
| `REPEATABLE READ` | 一个事务内需要稳定数据视角 | MySQL 默认，常用 |
| `SERIALIZABLE` | 正确性和严格顺序远比吞吐量重要 | 极少使用 |

#### 4.6.1 READ UNCOMMITTED：只适合允许结果失真的临时场景

它允许读取其他事务尚未提交的数据，查询结果可能随后被回滚。

可以勉强考虑的场景：

- 个人测试环境中演示脏读；
- 临时观察一个大事务进行到了哪里，并且结果只供参考；
- 对准确性完全没有要求的粗略估算。

例如事务 A 正在导入 100 万条数据但尚未提交，事务 B 可能看到已经导入 80 万条；如果事务 A 最终回滚，真实数量又会变成 0。

```text
临时看到：80 万条
导入事务：发生错误并回滚
最终真实结果：0 条
```

余额、支付、订单、库存、权限、报表和审计等业务不能使用它。

> [!tip] 场景关键词
> 可以接受“刚才读到的数据可能从未正式存在”，才可能考虑 `READ UNCOMMITTED`；普通业务基本不用。

#### 4.6.2 READ COMMITTED：适合查询最新状态和高并发短事务

它只读取已经提交的数据，并且每条普通查询都会读取执行当时最新的已提交版本。

适合的场景：

- 客服查询订单当前状态；
- 后台管理页面刷新最新数据；
- 用户查询最新物流进度；
- 高并发、执行时间很短的增删改查接口；
- 业务能够接受同一事务中前后两次查询结果发生变化。

例如客服查询订单：

```text
10:00 第一次查询 → 待支付
10:01 用户支付并提交
10:02 第二次查询 → 已支付
```

这里前后结果不同反而符合需求，因为客服关心的是当前最新状态，而不是保持第一次查询的旧视角。

它不适合一个事务执行多条统计 SQL，并要求所有结果使用同一个数据时间点的场景。

> [!tip] 场景关键词
> “每次刷新都想看到最新提交结果”，优先考虑 `READ COMMITTED`。

#### 4.6.3 REPEATABLE READ：适合需要稳定快照的多次查询

它让同一事务中的普通一致性读通常复用同一个快照，适合多次查询必须保持统一观察口径的场景。

例如生成财务报表需要依次查询：

```text
订单总数
订单总金额
退款总金额
最终收入
```

如果使用 `READ COMMITTED`，其他事务在查询过程中不断提交订单，不同指标可能来自不同时间点：

```text
订单总数   → 基于 10:00 的数据
订单总金额 → 基于 10:01 的数据
退款总金额 → 基于 10:02 的数据
```

每个结果单独看都是真的，但整份报表可能对不上。使用 `REPEATABLE READ` 时，这些普通查询通常基于同一个快照，统计口径能够保持一致。

其他适合的场景：

- 对账时多次读取并比较同一批数据；
- 库存盘点需要固定一个观察时间点；
- 批量计算要求输入来自同一个数据版本；
- 分页导出希望本次看到的数据集合保持稳定；
- 没有明确理由修改隔离级别时，沿用 InnoDB 默认设置。

分页导出示例：

```sql
SELECT * FROM user ORDER BY id LIMIT 0, 100;
SELECT * FROM user ORDER BY id LIMIT 100, 100;
SELECT * FROM user ORDER BY id LIMIT 200, 100;
```

稳定快照可以减少导出期间因数据集合变化产生的统计口径问题，但事务不能保持太久。长事务会占用连接和资源，还会让旧版本及 undo log 长时间无法清理；大量导出还应考虑主键游标分页、只读副本或专门的导出方案。

> [!tip] 场景关键词
> “这次分析必须始终基于同一个时间点”，优先考虑 `REPEATABLE READ`。

#### 4.6.4 SERIALIZABLE：适合低并发但要求严格顺序的特殊流程

它通过更严格的锁和等待，让冲突事务尽量排队执行，正确性直观，但并发性能最低。

可以考虑的场景：

- 数据量小、频率低，但必须严格顺序完成的结算流程；
- 系统维护期间执行关键配置或数据迁移校验；
- 复现并发异常时，临时使用最高隔离级别做对比；
- 业务吞吐量很低，愿意用等待换取简单性。

例如每天执行一次的小规模结算：

```text
结算事务开始
→ 读取待结算记录并持有相关锁
→ 其他冲突事务等待
→ 完成计算并提交
→ 释放锁，其他事务继续
```

它不适合秒杀、抢购、高频支付和大量用户同时修改订单等高并发业务，否则容易出现大量锁等待、超时和死锁。这些业务通常应该用唯一约束、条件更新、合理索引、悲观锁或乐观锁解决具体冲突。

> [!tip] 场景关键词
> “数据量小、并发低、必须严格排队，而且可以接受等待”，才考虑 `SERIALIZABLE`。

#### 4.6.5 最终怎么选择

| 业务目标 | 更适合的选择 | 原因 |
| --- | --- | --- |
| 允许读取尚未提交的临时数据 | `READ UNCOMMITTED` | 准确性最低，普通业务基本不用 |
| 每次查询尽量看到最新提交结果 | `READ COMMITTED` | 每条普通查询获取新的已提交版本 |
| 多次查询需要统一统计口径 | `REPEATABLE READ` | 同一事务的普通一致性读通常复用同一快照 |
| 低并发流程必须严格排队 | `SERIALIZABLE` | 用更多锁和等待换取最高隔离程度 |
| 余额、库存等并发修改 | 不能只靠隔离级别 | 还要使用原子更新、悲观锁或乐观锁 |

面试时可以这样回答：

1. `READ UNCOMMITTED` 会产生脏读，普通业务基本不用。
2. 查询最新状态或高并发短事务，可以考虑 `READ COMMITTED`。
3. 报表、对账和多次查询需要稳定快照，使用 `REPEATABLE READ`。
4. 只有低并发、严格顺序比性能更重要时，才考虑 `SERIALIZABLE`。
5. 隔离级别不能代替业务并发控制，余额、库存和幂等仍要依赖条件更新、锁、版本号与数据库约束。

## 五、🔄 理论：MVCC

MVCC 全称是 Multi-Version Concurrency Control，即**多版本并发控制**。它让同一行数据保留可以追溯的历史版本，使普通查询能够读取适合当前事务的版本，而不必总是等待正在修改数据的事务。

> [!tip] 一句话理解
> 写操作继续修改最新数据；普通查询根据自己的读取视角，从版本链中找到应该看到的版本。这样读写可以在很多情况下同时进行。

### 5.1 MVCC 要解决什么问题

假设账户余额原来是 `1000`，事务 A 正在把它修改为 `900`，但尚未提交。

如果数据库只保留一个版本，事务 B 查询时只能选择：

```text
等待事务 A 结束
或者直接读到事务 A 尚未提交的 900
```

前者会增加阻塞，后者会产生脏读。MVCC 提供第三种选择：

```text
事务 A：继续修改最新版本 900
事务 B：读取修改前仍然对自己可见的历史版本 1000
```

这样，普通读取通常不需要因为写操作而等待，也不会读到不应该看到的未提交数据。

### 5.2 一行数据为什么能有多个版本

InnoDB 会在聚簇索引记录中维护隐藏的事务信息。理解 MVCC 最重要的是下面两个字段：

| 隐藏字段 | 作用 | 白话理解 |
| --- | --- | --- |
| `DB_TRX_ID` | 记录最后一次插入或修改该行的事务 ID | 说明“这个版本是谁改出来的” |
| `DB_ROLL_PTR` | 指向 undo log 中的相关记录 | 说明“上一个版本去哪里找” |

InnoDB 还可能维护隐藏的 `DB_ROW_ID`，用于没有合适主键或唯一非空索引时生成聚簇索引键；它不是判断 MVCC 可见性的核心。

假设余额经过三次修改：

```text
事务 120：余额改为 900       ← 当前聚簇索引记录
             │ DB_ROLL_PTR
             ▼
事务 105：余额原来是 1000    ← undo log 重建出的旧版本
             │ DB_ROLL_PTR
             ▼
事务 90：余额原来是 1200     ← 更旧版本
```

这些版本通过回滚指针串起来，可以理解成一条**版本链**。旧版本不是完整复制多张表，而是利用当前记录和 undo log 中的信息按需重建。

### 5.3 Read View 是什么

只有版本链还不够，数据库还要判断“当前事务应该看哪个版本”。Read View 就是普通一致性读使用的**可见性判断规则和事务快照信息**。

学习和面试时，可以重点理解四类信息：

| 信息 | 作用 |
| --- | --- |
| 当前事务 ID | 判断版本是不是当前事务自己修改的 |
| 活跃事务 ID 集合 | 记录创建 Read View 时仍未提交的事务 |
| 最小活跃事务 ID | 小于它的事务通常在快照创建前已经结束 |
| 下一批事务的边界 ID | 大于等于该边界的事务是在快照创建后才出现的 |

> [!info] 不要死背字段名
> 不同资料会使用 `m_ids`、`min_trx_id`、`max_trx_id`、`creator_trx_id` 等教学名称。面试更重要的是说清楚：Read View 记录了创建快照时有哪些事务仍在活跃，并据此判断某个行版本是否可见。

### 5.4 版本可见性怎么判断

假设事务 B 创建 Read View 时：

```text
当前事务：110
仍然活跃的事务：[110, 120]
最小活跃事务 ID：110
后续事务边界：130
```

查询某个行版本时，可以按下面的思路理解：

1. 如果版本是当前事务自己修改的，当前事务可以看到自己的修改。
2. 如果版本的事务 ID 小于最小活跃事务 ID，说明它通常在 Read View 创建前已经提交，可以看到。
3. 如果版本的事务 ID 大于等于后续事务边界，说明它在 Read View 创建后才出现，不能看到。
4. 如果事务 ID 位于两个边界之间，就检查它是否在活跃事务集合中：仍在活跃则不可见，当时已经提交则可见。

例如最新余额 `900` 由事务 120 修改，而事务 120 创建快照时仍然活跃：

```text
最新版本：余额 900，DB_TRX_ID = 120
→ 120 在活跃事务集合中
→ 对当前 Read View 不可见
→ 沿 DB_ROLL_PTR 查找旧版本

旧版本：余额 1000，DB_TRX_ID = 105
→ 105 小于最小活跃事务 ID 110
→ 对当前 Read View 可见
→ 返回余额 1000
```

### 5.5 一次快照读的完整过程

普通 `SELECT` 的 MVCC 查询过程可以压缩成六步：

```text
执行普通 SELECT
→ 创建或复用 Read View
→ 读取记录的最新版本
→ 根据 DB_TRX_ID 判断版本是否可见
→ 不可见就沿 DB_ROLL_PTR 从 undo log 重建旧版本
→ 重复判断，直到找到可见版本并返回
```

[打开 MVCC 快照读与版本可见性交互图](../../archify/mvcc-read-visibility.html)

图中绿色路径表示最新版本可见，可以直接返回；紫色虚线路径表示最新版本不可见，需要沿 `DB_ROLL_PTR` 追溯 undo log，重建并检查更旧的行版本。

### 5.6 READ COMMITTED 和 REPEATABLE READ 有什么区别

两个隔离级别都可以使用 MVCC，关键区别是 **Read View 的创建和复用时机**：

| 隔离级别 | Read View 的使用方式 | 查询效果 |
| --- | --- | --- |
| `READ COMMITTED` | 每次普通一致性读通常创建新的 Read View | 每次查询都可能看到其他事务刚刚提交的新版本 |
| `REPEATABLE READ` | 第一次普通一致性读创建 Read View，后续通常复用 | 同一事务中的多次普通查询保持稳定视角 |

假设事务 B 第一次读到余额 `1000`，随后事务 A 把余额改成 `900` 并提交：

```text
READ COMMITTED：
第一次 SELECT → 1000
事务 A 提交 900
第二次 SELECT → 新建 Read View，看到 900

REPEATABLE READ：
第一次 SELECT → 1000，并建立 Read View
事务 A 提交 900
第二次 SELECT → 复用 Read View，仍然看到 1000
```

所以 `READ COMMITTED` 更像不断刷新的直播，`REPEATABLE READ` 更像固定时间点的截图。

### 5.7 快照读和当前读不要混淆

MVCC 主要服务于普通一致性读，也就是常说的**快照读**：

```sql
SELECT balance FROM account WHERE id = 1;
```

下面这些操作需要处理当前最新数据，属于当前读或锁定操作：

```sql
SELECT balance FROM account WHERE id = 1 FOR SHARE;
SELECT balance FROM account WHERE id = 1 FOR UPDATE;
UPDATE account SET balance = balance - 100 WHERE id = 1;
DELETE FROM account WHERE id = 1;
```

当前读不能只返回某个历史版本，因为应用接下来可能要修改数据。InnoDB 会读取较新的版本并使用锁控制并发冲突。

| 对比项 | 快照读 | 当前读或锁定操作 |
| --- | --- | --- |
| 常见语句 | 普通 `SELECT` | `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` |
| 主要机制 | Read View、版本链、undo log | 最新数据、行锁及范围锁 |
| 是否可能读取历史版本 | 可以 | 通常要读取较新的当前版本 |
| 主要目标 | 减少普通读写阻塞 | 保证接下来的修改不被并发操作破坏 |

### 5.8 MVCC 不能解决什么

MVCC 很重要，但不能把它理解成“不再需要锁”：

- 写写冲突仍然需要锁处理；
- `SELECT ... FOR UPDATE` 等锁定读仍然会加锁；
- 普通快照读可能看到历史版本，不保证是此刻最新值；
- 长事务会让旧版本长时间不能清理，导致 undo log 膨胀；
- 余额扣减、库存扣减等业务仍要使用原子更新、悲观锁或乐观锁。

> [!tip] 面试表达
> InnoDB 的 MVCC 通过行记录中的 `DB_TRX_ID`、`DB_ROLL_PTR`、undo log 版本链和 Read View 实现。普通 SELECT 先读取最新版本，再根据 Read View 判断该版本是否可见；不可见就沿回滚指针查找旧版本。`READ COMMITTED` 通常每次查询创建新的 Read View，`REPEATABLE READ` 通常复用第一次查询的 Read View。MVCC 主要减少普通读写阻塞，但写写冲突和当前读仍然需要锁。

### 5.9 MVCC 和锁怎么分工

现在已经分别知道了 MVCC 和锁是什么，再来看它们的分工：

| 场景 | 主要机制 | 目标 |
| --- | --- | --- |
| 普通 `SELECT` | MVCC、Read View、undo 版本链 | 读取合适的历史版本，减少普通读写阻塞 |
| `SELECT ... FOR UPDATE` | 排他锁 | 读取较新的数据并阻止其他事务冲突修改 |
| `SELECT ... FOR SHARE` | 共享锁 | 允许其他事务读取，但阻止冲突修改 |
| `UPDATE`、`DELETE` | 当前读、排他锁 | 修改当前数据并保护写入结果 |

```text
只想查看数据
→ 普通 SELECT
→ 尽量通过 MVCC 读取合适版本，避免与写操作互相等待

要根据查询结果继续修改
→ SELECT ... FOR UPDATE、UPDATE 或 DELETE
→ 读取较新数据，并通过锁保护操作顺序
```

> [!warning] 不要混淆
> MVCC 不是锁的替代品。它主要优化普通快照读；写写冲突、当前读和范围修改仍然需要锁。

## 六、🔒 理论：InnoDB 锁

### 6.1 普通 SELECT 和 FOR UPDATE 的区别

```sql
-- 普通一致性读：通常通过 MVCC 读取快照，不锁住返回的记录。
SELECT balance FROM account WHERE id = 1;

-- 锁定读：读取当前数据，并对匹配的索引记录加排他锁。
SELECT balance FROM account WHERE id = 1 FOR UPDATE;
```

如果业务要“先查余额，再根据余额决定是否扣款”，普通 `SELECT` 不足以阻止其他事务同时修改余额。常见做法是：

- 在事务中使用 `SELECT ... FOR UPDATE` 锁定目标行；或
- 直接用一条带条件的原子 `UPDATE`，再检查影响行数。

### 6.2 写操作为什么不能只靠 MVCC

MVCC 可以让普通查询读取历史版本，但修改数据时不能只操作历史版本。例如两个事务都要扣减同一个账户余额，数据库必须决定谁先修改，另一个事务等待还是失败。

```text
普通查询：可以读取适合自己的历史版本
修改数据：必须围绕当前数据协调顺序
```

因此，InnoDB 使用锁处理下面的问题：

- 两个事务同时修改同一行；
- 查询后马上修改，需要阻止数据在中途变化；
- 范围更新期间，需要控制其他事务向范围内插入新记录；
- 外键检查和唯一键检查需要保护相关记录。

### 6.3 共享锁和排他锁

| 锁 | 常见名称 | 作用 | 与其他锁的关系 |
| --- | --- | --- | --- |
| 共享锁 | S Lock | 当前事务读取并保护记录 | 多个共享锁可以同时存在，但会阻止排他锁 |
| 排他锁 | X Lock | 当前事务准备修改记录 | 会阻止其他事务获得冲突的共享锁或排他锁 |

可以类比成一份文档：

```text
共享锁 = 多个人可以同时阅读，但暂时不允许别人修改
排他锁 = 我正在修改，其他人不能同时修改或加冲突锁
```

常见语句：

```sql
-- 给查询到的记录加共享锁。
SELECT * FROM account WHERE id = 1 FOR SHARE;

-- 给查询到的记录加排他锁，适合查询后继续修改。
SELECT * FROM account WHERE id = 1 FOR UPDATE;

-- UPDATE 会对真正修改的记录加排他锁。
UPDATE account SET balance = balance - 100 WHERE id = 1;
```

### 6.4 意向锁是什么

InnoDB 除了行级锁，还会在表级别设置意向锁，用来快速说明“这张表中的某些行已经准备加什么锁”。

| 意向锁 | 含义 |
| --- | --- |
| IS（意向共享锁） | 事务准备在表中的某些行上加共享锁 |
| IX（意向排他锁） | 事务准备在表中的某些行上加排他锁 |

意向锁不是把整张表的数据都锁住。它主要帮助表锁快速判断是否会和已有行锁冲突，不必逐行检查整张表。

> [!tip] 面试够用的回答
> 意向锁是表级锁，用来表示事务准备在表内某些记录上加共享锁或排他锁，主要用于协调表锁和行锁。

### 6.5 记录锁、间隙锁和 next-key lock

| 锁类型 | 锁住什么 | 白话理解 |
| --- | --- | --- |
| Record Lock | 已存在的索引记录 | 锁住目录中的某一项 |
| Gap Lock | 两条索引记录之间的间隙 | 锁住一个可以插入新目录项的空白范围 |
| Next-Key Lock | 记录锁加记录前面的间隙 | 同时保护已有记录和相邻插入范围 |

假设索引中有：

```text
10、20、30
```

可以把锁定范围简化理解为：

```text
Record Lock：锁住 20 这条记录
Gap Lock：锁住 10 和 20 之间的空隙，不允许插入 15
Next-Key Lock：锁住 20 以及它前面的间隙
```

在 InnoDB 默认的 `REPEATABLE READ` 下，范围当前读或范围修改可能使用 next-key lock，阻止其他事务向扫描范围插入新记录，从而处理常见幻读问题。

> [!warning] 范围只是帮助理解
> 实际加锁范围取决于隔离级别、索引、查询条件和执行计划。不能只看 SQL 文本就绝对判断锁住了哪些记录。

### 6.6 InnoDB 行锁为什么和索引有关

InnoDB 的“行锁”实际是加在索引记录上的。查询能否使用合适索引，会直接影响扫描和加锁范围。

```text
精确命中唯一索引
→ 通常只需要锁住目标索引记录

范围查询或没有合适索引
→ 需要扫描更多索引记录
→ 可能锁住更大的范围
```

例如：

```sql
-- id 是主键，通常能够精确定位一条记录。
SELECT * FROM account WHERE id = 1 FOR UPDATE;

-- 如果 status 没有合适索引，可能扫描并锁住更多记录。
SELECT * FROM orders WHERE status = 'PENDING' FOR UPDATE;
```

所以优化锁冲突不能只看事务代码，还要结合 [[MySQL 索引]] 和执行计划。

### 6.7 乐观锁和悲观锁

| 方式 | 思路 | 常见实现 | 适用场景 |
| --- | --- | --- | --- |
| 悲观锁 | 认为冲突很可能发生，先锁住再操作 | `SELECT ... FOR UPDATE` | 冲突较多、操作必须串行 |
| 乐观锁 | 认为冲突较少，提交时检查是否被修改 | 版本号或条件更新 | 冲突较少、希望减少等待 |

版本号乐观锁示例：

```sql
UPDATE product
SET stock = stock - 1,
    version = version + 1
WHERE id = 1001
  AND stock > 0
  AND version = 7;
```

如果影响行数为 `0`，说明库存不足或版本已经变化，应用不能假装更新成功，应重新读取后重试或返回失败。

### 6.8 死锁是怎么产生的

死锁是两个事务分别持有对方需要的锁，并且互相等待：

```text
事务 A：锁住账户 1，等待账户 2
事务 B：锁住账户 2，等待账户 1
```

InnoDB 检测到死锁后，会选择回滚其中一个事务，让另一个继续执行。应用需要捕获死锁异常，并对适合重试的短事务进行有限次数重试。

减少死锁的常见方法：

- 多个事务按照相同顺序访问资源，例如始终先锁较小的账户 ID；
- 缩短事务时间，不在事务中调用耗时远程接口；
- 为查询条件建立合适索引，缩小扫描和加锁范围；
- 一次只处理必要的数据，避免大事务；
- 对死锁失败进行有限重试，并保证业务幂等。

## 七、🚀 实践：观察一次行锁等待

### 7.1 前置准备

- MySQL 8.0 或 8.4；
- 使用 InnoDB 测试表；
- 准备两个独立数据库连接，分别作为事务 A 和事务 B；
- 下面包含建表和写入，只能在个人测试库练习，不要在共享库或生产库直接执行。

### 7.2 准备测试数据

```sql
CREATE TABLE lock_demo_account (
    id BIGINT PRIMARY KEY,
    balance DECIMAL(12, 2) NOT NULL
) ENGINE = InnoDB;

INSERT INTO lock_demo_account(id, balance) VALUES (1, 1000.00);
```

### 7.3 事务 A 锁住记录

在连接 A 中执行：

```sql
START TRANSACTION;

SELECT balance
FROM lock_demo_account
WHERE id = 1
FOR UPDATE;

-- 暂时不要提交，用来观察另一个事务等待。
```

### 7.4 事务 B 尝试修改同一记录

在连接 B 中执行：

```sql
START TRANSACTION;

UPDATE lock_demo_account
SET balance = balance - 100
WHERE id = 1;
```

连接 B 会等待，因为连接 A 持有目标记录的排他锁。

回到连接 A 执行：

```sql
COMMIT;
```

连接 A 释放锁后，连接 B 才能继续。最后在连接 B 中提交：

```sql
COMMIT;
```

这个实验说明：锁不是让所有事务都停止，而是让访问同一冲突资源的事务按照顺序继续。

## 八、🎤 高频面试题

### 8.1 MySQL 默认隔离级别是什么

> InnoDB 默认是 `REPEATABLE READ`。普通一致性读通常复用同一个 Read View；当前读和增删改读取较新的数据并加锁。范围当前读还可能使用 next-key lock 控制范围内插入。

### 8.2 MVCC 能完全代替锁吗

> 不能。MVCC 主要通过 Read View 和 undo 版本链优化普通快照读；写写冲突、当前读和锁定读仍然需要锁。

### 8.3 READ COMMITTED 和 REPEATABLE READ 有什么区别

> `READ COMMITTED` 每次普通一致性读通常创建新的 Read View，更关注最新已提交数据；`REPEATABLE READ` 通常复用第一次一致性读建立的 Read View，更关注同一事务内数据视角稳定。

### 8.4 什么是 next-key lock

> next-key lock 可以理解为记录锁与记录前间隙锁的组合。InnoDB 在范围当前读或范围修改中使用它保护已存在的索引记录及相关插入范围，从而处理常见幻读问题。

### 8.5 如何减少死锁

> 保持一致的资源访问顺序，缩短事务，使用合适索引缩小加锁范围，避免大事务；应用还要捕获死锁异常，对适合重试的短事务进行有限重试并保证幂等。

## 九、📌 快速回顾

```text
隔离级别       = 决定并发事务之间能看到什么
READ COMMITTED = 每次普通查询看最新已提交版本
REPEATABLE READ = 同一事务普通查询通常复用快照
MVCC           = Read View + undo 版本链
快照读         = 普通 SELECT，可能读取历史版本
当前读         = 读取较新数据并结合锁控制冲突
Record Lock    = 锁已有索引记录
Gap Lock       = 锁索引记录之间的间隙
Next-Key Lock  = 记录锁 + 间隙锁
```

最适合面试复述的一句话：

> InnoDB 使用隔离级别规定并发可见性，使用 MVCC 让普通 SELECT 读取合适的历史版本，使用记录锁、间隙锁和 next-key lock 控制当前读与写入冲突；锁实际加在索引记录上，所以索引设计会直接影响加锁范围和并发性能。
