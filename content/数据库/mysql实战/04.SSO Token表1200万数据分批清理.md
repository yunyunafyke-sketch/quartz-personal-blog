## 一、清理方案

**表内约 1200 万条数据，按 `expiry_time` 清理过期超过 7 天的 Token，手动分批执行。已有 `IX_EXPIRY_TIME` 索引，不用重复建。**

> `expiry_time < NOW() - INTERVAL 7 DAY` 表示“过期时间距今超过 7 天”，不是“创建于 7 天前”，也不是“所有已过期数据”。

### 1. 执行前准备

使用独立连接，开启客户端自动提交，保证每批删除独立提交。每次等上一条执行完成，再执行下一条。

先查看最早过期的 10 条记录：

```sql
SELECT id, expiry_time
FROM t_abs_sso_valid_token
WHERE expiry_time < NOW() - INTERVAL 7 DAY
ORDER BY expiry_time, id
LIMIT 10;
```

### 2. 先小批量试跑

```sql
DELETE FROM t_abs_sso_valid_token
WHERE expiry_time < NOW() - INTERVAL 7 DAY
LIMIT 1000;
```

确认耗时和业务负载正常后，可先增加到 1 万条，再尝试 5 万条。

### 3. 稳定后按每批 5 万条执行

```sql
DELETE FROM t_abs_sso_valid_token
WHERE expiry_time < NOW() - INTERVAL 7 DAY
LIMIT 50000;
```

重复执行，查看客户端显示的影响行数，**直到影响行数为 0，就停止**。

如果全部 1200 万条都符合条件，每批 5 万条约需 **240 批**；实际批数取决于符合条件的数据量。

### 4. 慢或超时怎么办？

| 情况 | 处理方式 |
| --- | --- |
| 每批 5 万条耗时长、业务变慢 | 降低到 1 万或 1000 条，观察数据库负载 |
| 1000 条仍慢 | 降到 100 条试跑，同时排查原因 |
| 报 `Lock wait timeout` | 先查阻塞事务，不能只靠减小批量解决 |
| 客户端超时 | 先确认服务端原语句是否仍在执行，再重试 |

不要因为执行慢而继续增大批量；先确认是否存在锁等待、索引未用上或磁盘压力。

**执行顺序：先由 ID 1 扫描数据，再交给 ID 0 执行删除。**

### 2. 能确认的结论

- **使用了 `IX_EXPIRY_TIME` 索引。**表名后括号里的索引名就是本次选择的访问路径。
- **不能看到 `TABLE SCAN` 就认定扫了整张表。**这种格式与 OceanBase 执行计划一致，其 `TABLE SCAN` 可以表示索引扫描；是否扫描完整索引或只扫描一段范围，还需要看 `range`、`range_cond` 等信息。
- **本批设置了最多 5 万条的限制。**但 `EST. ROWS = 50000` 是估算输出行数，不是实际扫描行数，也不是已经成功删除的行数。
- **当前计划没有显示 `SORT` 排序算子。**如果这是带 `ORDER BY` 的 SQL 对应的计划，就没有看到额外排序，不能认定去掉 `ORDER BY` 一定更快。如果原 SQL 本来就不带排序，则不能据此判断带排序的版本会怎样。
- **`COST` 是优化器的估算成本。**不能把 `358626` 直接当成实际执行耗时，也不能据此认定这批删除一定快或一定慢。

### 3. 还需要确认什么？

**截图没有原 SQL，也没有展示 `range`、`range_cond`，所以还不能确认过期时间条件是否正确限定了扫描范围。**

`filter(nil)` 可能是因为条件已用于限定索引扫描范围，无需再做额外过滤；也可能原 SQL 没有相应条件，不能只凭这一项下结论。

先核对原 SQL 保留了以下条件：

```sql
WHERE expiry_time < NOW() - INTERVAL 7 DAY
```

如果查看完整计划，应进一步确认 `range` / `range_cond` 的边界与这个条件一致。

**本次结论：计划用上了过期时间索引，限制了每批最多 5 万条，未显示额外排序；但不能仅凭计划保证执行快、没有锁等待或不影响业务。**是否适合持续按 5 万条删除，还要结合实际耗时、影响行数、锁等待和数据库负载判断。

## 三、为什么删除语句不加 ORDER BY？

**这次只要求清理符合条件的过期数据，不要求先删哪条，因此删除语句可以省略 `ORDER BY`。**

原来的 `ORDER BY expiry_time, id` 表示：先删过期时间最早的记录，过期时间相同再按 ID 排序。

| 写法 | 含义 | 性能影响 |
| --- | --- | --- |
| 不加 `ORDER BY` | 删除找到的符合条件的记录，最多删除 `LIMIT` 指定的条数，不保证顺序 | 无需满足指定排序要求 |
| 加 `ORDER BY expiry_time, id` | 按过期时间、ID 决定本批删除哪些记录 | 如果索引不能提供顺序，需要额外排序，可能变慢 |

**`LIMIT 50000` 不代表只处理 5 万条数据。**如果需要额外排序，可能要扫描大量符合条件的记录，才能确定排在前面的 5 万条。

不过，**加 `ORDER BY` 不一定慢，去掉也不保证一定更快**。这张表有 `expiry_time` 索引，可能利用索引顺序避免额外排序；原生 MySQL InnoDB 的二级索引还包含主键 `id`。具体要看 `EXPLAIN DELETE ...` 的执行计划：MySQL 关注是否出现 `Using filesort`，OceanBase 关注是否出现 `SORT` 等排序算子。

删除示例省略排序；执行前的查询保留排序，是为了查看最早过期的 10 条记录。

## 四、每批删 5 万条，会发生什么？

**可以每批删 5 万条，但单次压力更大。是否合适，要看每批耗时、锁等待和数据库负载，不能只看表里有 1200 万条。**

| 环节 | 会发生什么 | 可能的影响 |
| --- | --- | --- |
| 查找数据 | 找出符合条件的最多 5 万条记录；执行计划用上 `IX_EXPIRY_TIME` 索引时，可以减少扫描量 | 不代表每批都要扫描完整的 1200 万条 |
| 加锁删除 | 对涉及的记录和索引记录加锁；根据隔离级别和扫描范围，还可能涉及间隙锁 | 修改相同记录的业务可能等待，不等于直接锁整张表 |
| 写日志 | 生成 undo、redo；开启 binlog 时还会记录 binlog | 增加磁盘写入，有主从复制时可能增加复制延迟 |
| 提交事务 | 开启自动提交时，这一批作为一个事务提交，并释放事务持有的锁 | 批次越大，通常持锁时间越长 |
| 后台清理 | InnoDB 后续通过 purge 清理旧记录 | 删完后表文件通常不会立即变小，空间可供后续复用 |

> 上表涉及 InnoDB 锁、undo/redo、binlog、purge 的细节，以原生 MySQL InnoDB 为前提。第二部分截图的格式与 OceanBase 执行计划一致；如果实际使用 OceanBase，不能把这些内部实现直接套用，应以实际数据库版本为准。

**`LIMIT 50000` 限制的是删除行数，不保证只扫描、只锁 5 万条。**

对 SSO Token 表，主要关注清理期间登录、Token 查询或更新是否变慢。普通查询通常可以通过 MVCC 读取，但仍可能受磁盘负载影响。

**每批独立提交，才能控制事务大小。**连续执行多条却一直不提交，仍会积累成一个大事务；批量是否合适，要结合实际耗时、锁等待和业务负载判断。
