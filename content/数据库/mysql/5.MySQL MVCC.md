## 一、💡 从隔离级别接着往下想：数据库怎么兑现读取规则

> [!tip] 先抓住两篇文章的关系
> [[4.MySQL 隔离级别]] 讲的是“一个事务应该看到什么”；本篇讲的是“InnoDB 怎样找出允许它看到的数据版本”。MVCC（Multi-Version Concurrency Control，多版本并发控制）是实现 RC、RR 普通一致性读的重要机制。

### 1.1 先接住上一篇的结论：RC 和 RR 读出来有什么不同

继续使用上一篇的账户例子：余额最初是 `1000`，事务 A 负责扣款，事务 B 负责查询。**B 的两次查询在同一个事务内，都是普通 SELECT，B 自己不修改数据。**

| 顺序 | 事务 A：扣款 | 事务 B 使用 RC（读已提交） | 事务 B 使用 RR（可重复读） |
| --- | --- | --- | --- |
| ① | 尚未扣款 | 第一次查到 `1000` | 第一次查到 `1000`，建立快照 |
| ② | 将余额改成 `900`，尚未提交 | 此时再查，仍是 `1000` | 此时再查，仍是 `1000` |
| ③ | 提交扣款 | | |
| ④ | | 再查得到 `900` | 再查仍是 `1000` |

RC、RR 两列表示两种独立情形。先不背实现，回忆它们对应的知识点：

- **防脏读**：第②步都不读取 A 尚未提交的 `900`。
- **不可重复读**：第④步 RC 可以看到新提交的 `900`，所以同一事务前后结果可能变化。
- **可重复读**：第④步 RR 继续看到 `1000`，保持原来的读取视角。

上一篇告诉我们这些结果符合各自的隔离规则。接下来才是本篇的问题：**当前余额已经被改成了 900，数据库到底从哪里拿到 1000？又怎么知道这次该返回哪一个？**

### 1.2 为什么需要“多个版本”，而不是只保存最新值

先看 A 尚未提交时。B 不能读取未提交的 `900`，否则可能脏读。让 B 等待 A 结束是一种并发控制思路，但会增加读写之间的等待。

InnoDB 的普通一致性读提供了另一条路：**A 继续修改，B 读取对自己可见的旧版本 1000。** 这里的“一致性读”也常叫“快照读”，就是按照某个读取视角选择版本，后文会解释这个视角如何实现。

再看 A 提交以后。RC 的下一次普通查询可以读取 `900`；RR 的原事务仍可能需要读取 `1000`。所以，“已经提交”还不足以决定返回哪个版本，还要看当前查询沿用哪个读取视角。

这里的“读取视角”就是后文要讲的 **Read View：用于判断哪些数据版本对当前查询可见的依据**。先沿着时间顺序理解：

| 顺序 | 事务 A：扣款 | 事务 B：查询 |
| --- | --- | --- |
| ① | 尚未扣款 | 第一次普通查询，看到 `1000` |
| ② | 将余额改成 `900`，并提交 | |
| ③ | | 在同一个事务内再次普通查询 |

第③步，A 明明已经提交，为什么 B 还可能看到 `1000`？关键在于 B 使用哪一个视图：

- **事务 B 使用 RC**：第③步建立新的 Read View。A 在这个新视图建立之前已经提交，因此 `900` 对新视图可见，查询返回 `900`。
- **事务 B 使用 RR**：第③步继续沿用第①步建立的 Read View。A 的修改是在旧视图建立之后发生并提交的，因此 `900` 对旧视图不可见，查询仍返回 `1000`。

这里仍假设 B 自己没有修改数据，两次读取都是同一事务中的普通一致性读。

> [!tip] “已经提交”和“对我可见”是两回事
> “已经提交”描述的是写事务现在的状态；“对我可见”还取决于当前查询使用的 Read View。**已经提交，不等于对所有查询立即可见；RR 的旧快照仍可能看不到后来提交的修改。**

由此自然得到两个实现需求：

| 从隔离规则推导出的需求 | InnoDB 的对应机制 | 接下来要回答的问题 |
| --- | --- | --- |
| 当前值变了，仍要能找到旧值 | 当前记录与 undo log 形成的逻辑版本链 | `1000` 怎样还原出来？ |
| 不同查询可能有不同的可见范围 | Read View（读取视图） | 哪些事务写出的版本允许我看？ |
| RC 后续读取可以看新提交，RR 通常保持原视角 | Read View 的建立与复用时机 | 这次该换视图，还是沿用原视图？ |

**先记住：版本链提供候选版本，Read View 筛选可见版本，RC/RR 决定何时建立或复用视图。** 后面的隐藏字段、事务 ID 都是在为这三个职责服务。

### 1.3 隔离级别、MVCC、锁分别处在哪一层

隔离级别是事务对外提供的行为规则；MVCC 和锁是实现并发控制的机制，不能把四种隔离级别理解为四套 MVCC。

| 隔离级别 | 普通查询的关键行为 | 与本篇的关系 |
| --- | --- | --- |
| RU：读未提交 | 可能读到其他事务未提交的修改 | 不套用本篇 RC/RR 的快照可见性规则 |
| RC：读已提交 | 每次普通一致性读使用新快照 | 用 MVCC 解释为何不脏读、却可能前后不同 |
| RR：可重复读 | 同一事务的普通一致性读通常复用首次快照 | 用 MVCC 解释为何别人提交了，我仍看到旧值 |
| SERIALIZABLE：可串行化 | 施加更严格的并发约束；关闭自动提交时，普通 SELECT 隐式成为共享锁定读 | 需要结合锁理解，见 [[6.MySQL 锁]] |

即使在 RC、RR 下，`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 也不能照搬普通快照读的分析方式。先学会本篇的普通读取，再到第六章区分当前读与快照读。

本篇以 **MySQL 8.4 InnoDB 的 RC、RR 普通一致性读**为主。读取规则可对照 [官方一致性读说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)；前置笔记是 [[3.MySQL 事务]]、[[4.MySQL 隔离级别]]。

现在按下面的顺序读，就能从现象走到原理：

```text
隔离级别要求我看到什么？
→ 需要保留哪些旧版本？（第二章：版本链）
→ 怎样判定哪个版本可见？（第三章：Read View）
→ 实际查询怎样挑出结果？（第四章：逐版判断）
→ RC/RR 为什么挑出不同结果？（第五章：视图生命周期）
```

## 二、🔗 版本链：数据库怎样找回旧余额

### 2.1 当前记录上的两个关键字段

回到开头的疑问：余额已改成 `900`，查询还需要拿到 `1000`。数据库既要知道“这一版是谁修改的”，也要知道“沿哪里找修改前的内容”，于是需要下面两个字段。

InnoDB 的聚簇索引记录中包含事务信息。理解版本链，重点看这两个隐藏字段：

| 字段 | 作用 | 白话理解 |
| --- | --- | --- |
| `DB_TRX_ID` | 最后插入或修改该记录的事务 ID | 这一版是谁写出来的 |
| `DB_ROLL_PTR` | 指向相关 undo log 记录 | 从哪里还原修改前的内容 |

`DB_ROW_ID` 主要与没有合适主键或唯一非空索引时的聚簇索引生成有关，不是判断版本可见性的核心。

### 2.2 undo log 保存的是还原旧版本所需的信息

账户余额经历了几次修改，可以用下面的逻辑图理解：

```text
当前记录：余额 900，DB_TRX_ID = 120（支付尚未提交）
    │ DB_ROLL_PTR
    ▼
旧版本：余额 1000，DB_TRX_ID = 105
    │ 继续根据 undo 信息向前还原
    ▼
更旧版本：余额 1200，DB_TRX_ID = 90
```

这就是版本链。图中的旧版本是根据 undo 信息还原出来的，不意味着每次更新都把完整数据行或整张表复制一份。

undo log 既用于事务回滚，也为一致性读提供重建旧版本的信息；两种用途的保留期限并不相同。用于一致性读的更新 undo，可能在写事务提交后仍需保留。[官方多版本说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)

> [!tip] 先分清两个职责
> 版本链负责“旧数据怎样找回来”，它本身不能决定当前查询应该返回哪一版。

## 三、👀 Read View：查询有资格看哪一版

### 3.1 它记录事务状态，不复制查询结果

上一章解决了“找得到旧值”，这一章解决“有资格看哪一个值”。例如，A 未提交的 `900` 不应被 B 读到；A 提交后，B 的新视图可能允许读取 `900`，原来的旧视图却可能仍然不允许。判断依据就放在 Read View 中。

Read View 可以理解为建立读取视角时拍下的一张“事务状态合影”。它用当时的活跃事务和事务 ID 边界，判断一个行版本是否可见。

最核心的规则是：

- 当前事务自己之前的修改可见。
- 其他事务在快照建立前已经提交的修改可见。
- 其他事务在快照建立时尚未提交，或者在快照建立后才产生的修改，对这个快照不可见。

所以，某个事务**现在已经提交**，不代表它的修改对一个**更早建立的快照**也可见。

### 3.2 四份关键的信息

下面使用常见教学名称，并列出 MySQL 8.4 源码中的对应名称：

| 教学名称 | 源码名称 | 含义 |
| --- | --- | --- |
| `creator_trx_id` | `m_creator_trx_id` | 创建视图的事务 ID，用于识别自己的修改 |
| `m_ids` | `m_ids` | 建立视图时其他活跃读写事务的 ID 集合 |
| `min_trx_id` | `m_up_limit_id` | `m_ids` 中的最小 ID；集合为空时取下面的上界 |
| `max_trx_id` | `m_low_limit_id` | 建立视图时取到的事务 ID 分配上界；大于等于它的版本不可见 |

注意：源码中的 `up`、`low` 命名与数值大小的直觉容易混淆。学习时可以先记 `min`、`max` 的含义。

事务 ID 不是事务提交的时间排名：事务 100 可以比事务 105 更晚提交，所以只比较 ID 大小还不够，需要结合活跃集合判断。纯只读事务也不一定分配普通读写事务 ID，不能把表中的集合理解为所有已执行 `BEGIN` 的连接。

### 3.3 一版数据的可见性怎么判断

取出某个版本的 `DB_TRX_ID`，记为 `trx_id`：

```text
① trx_id == creator_trx_id
   → 当前事务自己的修改，可见

② trx_id < min_trx_id
   → 位于最早活跃事务之前，可见

③ trx_id >= max_trx_id
   → 达到或超过快照建立时的分配上界，不可见

④ min_trx_id <= trx_id < max_trx_id
   → 检查它是否在 m_ids 中
      在：快照建立时仍然活跃，不可见
      不在：其已提交的修改对快照可见
```

`m_ids` 是建立视图时留下的状态，不会因为某个事务随后提交，就自动从旧视图中删除该事务 ID。

以上为教学顺序，字段与判断逻辑可对照官方源码中的 [ReadView 定义与可见性判断](https://github.com/mysql/mysql-server/blob/8.4/storage/innobase/include/read0types.h) 和 [ReadView 初始化](https://github.com/mysql/mysql-server/blob/8.4/storage/innobase/read/read0read.cc)。

## 四、🔄 串起来：一次查询怎样沿版本链找到结果

### 4.1 先准备一个具体的 Read View

下面是独立的演算例子。假设查询事务已经分配了事务 ID `108`，建立 Read View 时：

```text
creator_trx_id = 108
m_ids          = [100, 107]  ← 其他活跃读写事务，不包含创建者
min_trx_id     = 100
max_trx_id     = 110
```

某行数据最初由事务 105 写入余额 `1000` 并提交。事务 107 将它改成 `900`，在建立快照时尚未提交。

快照建立后，107 提交；随后事务 112 把余额改成 `800` 并提交。此时查询事务 108 继续使用原来的 Read View 读取这行数据，逻辑版本链为：

```text
最新版本：trx_id = 112，余额 800
    ↓
上一版本：trx_id = 107，余额 900
    ↓
更旧版本：trx_id = 105，余额 1000
```

这里事务 112 在事务 107 提交后才修改同一行，符合写写冲突需要通过锁协调的顺序。

### 4.2 从最新版本开始逐个检查

| 检查顺序 | 版本 | 判断 | 处理 |
| --- | --- | --- | --- |
| ① | 112：余额 `800` | `112 >= 110`，快照建立后产生 | 不可见，向前找 |
| ② | 107：余额 `900` | 在 `[100, 110)` 中，且在 `m_ids` 中 | 不可见，继续向前找 |
| ③ | 105：余额 `1000` | 在 `[100, 110)` 中，不在 `m_ids` 中 | 可见，返回 `1000` |

虽然 107 和 112 现在都已提交，但它们不符合这个旧视图的可见性规则。因此，这次查询得到的仍然是 `1000`。

### 4.3 完整读取过程

```text
执行普通一致性读
→ 建立或复用 Read View
→ 检查当前记录的版本
→ 可见：使用该版本判断记录是否应返回
→ 不可见：通过 undo 信息还原上一版，继续判断
→ 找到适合的版本，或者确定该行对当前快照不存在
```

“不可见”不一定意味着总能找到一个旧版本。如果该行是快照建立之后才插入的，当前快照可能根本看不到这行。删除也要结合可见版本上的删除标记判断，不能把“找到可见版本”机械理解成“一定返回一行”。

## 五、🧭 RC 和 RR：核心差别在于什么时候建立读取视角

两者都通过 Read View 判断可见性，主要区别在于普通一致性读什么时候获取新的视图。

### 5.1 RC：每次普通一致性读获取新视图

```text
事务 B：第一次查询，建立视图 V1 → 余额 1000
事务 A：将余额改为 900，并提交
事务 B：第二次查询，获取新视图 V2 → 余额 900
```

A 在 V1 建立时尚未提交，对 V1 不可见；在 V2 建立前已经提交，对 V2 可见。变化来自**读取视角更新**，不是版本链的判断规则发生了变化。

### 5.2 RR：同一事务通常复用首次一致性读建立的视图

```text
事务 B：第一次查询，建立视图 V1 → 余额 1000
事务 A：将余额改为 900，并提交
事务 B：第二次查询，继续使用 V1 → 仍然是 1000
```

普通 `START TRANSACTION` 通常只表示事务开始，快照在第一次普通一致性读时建立。RR 下如需在开始时建立一致性快照，可使用 `START TRANSACTION WITH CONSISTENT SNAPSHOT`。

| 对比项 | RC | RR |
| --- | --- | --- |
| 普通一致性读的视图 | 每次读取获取新视图 | 同一事务通常复用首次视图 |
| 其他事务刚提交的修改 | 后续读取可见 | 对原快照可能仍不可见 |
| 自己之前的修改 | 可见 | 可见 |

这些规则针对同一事务中的普通一致性读，参见 [官方一致性读说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)。

### 5.3 客服刷新和财务报表怎样对应这两种策略

客服刷新订单通常会发起新请求、执行新事务。因此，即使使用 RR，新事务也可以读取新提交的数据，不能因为“页面要最新”就断定必须用 RC。

财务报表如果要求订单数、支付金额、退款金额基于同一快照，可以在**同一 RR 事务**内完成这些普通查询。若每条查询都自动提交，各自属于不同事务，就不能保证它们共享视图。

业务上如何选择隔离级别，详见 [[4.MySQL 隔离级别]]；本篇重点是理解上述现象背后的视图生命周期。

### 5.4 再接回三种读取异常：MVCC 分别做了什么

到这里，再看上一篇的三个问题，就能把“现象”和“机制”对上：

| 上一篇的知识点 | 本篇的机制解释 |
| --- | --- |
| RC、RR 为什么能避免脏读？ | 其他事务未提交的版本不可见，普通一致性读可沿版本链寻找可见旧版本 |
| RC 为什么仍可能不可重复读？ | 后一次读取建立新视图，可能允许读取其他事务刚提交的新版本 |
| RR 为什么能让普通重复读取稳定？ | 复用原视图，其他事务后来提交的版本不会因此变成对原视图可见 |
| RC 为什么可能查出新增订单，RR 原快照却看不到？ | 新插入的行也要接受可见性判断；RC 的新视图可能看见，RR 的原视图仍将它排除 |

具体看幻读：B 第一次普通查询待支付订单，得到 1 条；A 随后插入另一条待支付订单并提交。B 再查时，RC 可以得到 2 条；RR 复用原视图时仍得到原来的 1 条。这里假设 B 没有修改相关数据，且两次查询都在同一事务中。

**RR 中不是 A 插入失败了，而是新订单对 B 的原快照不可见。** 新行没有一个更早、可见的行版本，查询就不会返回它。只有需要限制别人向相关范围插入时，才要进一步讨论范围锁定读和 next-key lock，见 [[6.MySQL 锁]]。

> [!warning] 把读取方式一起记住
> 本节解释的是普通一致性读。事务自己的修改可见，锁定读与修改语句又使用不同的读取规则，因此不能推出“RR 事务里无论怎样读写，结果都永远不变”。

## 六、🛠️ MVCC 的使用边界与代价

### 6.1 快照读与当前读：展示余额和扣款需要不同的保证

| 操作 | 典型语句 | 主要读取方式 |
| --- | --- | --- |
| 展示余额 | 普通 `SELECT`（RC/RR） | 按 Read View 读取可见版本 |
| 锁定余额后再修改 | `SELECT ... FOR UPDATE` | 读取当前数据，并协调冲突锁 |
| 扣款、删除记录 | `UPDATE`、`DELETE` | 基于当前数据执行修改，并处理锁冲突 |

后两类常被统称为“当前读”。这里的“当前”不表示可以直接读走其他事务未提交的值：遇到冲突时，操作可能需要等待，再处理符合条件的记录。

锁定读取需要放在合适的事务边界中使用。具体锁类型、索引范围以及等待行为见 [[6.MySQL 锁]]。

### 6.2 两个人都看见最后一件库存，不代表都能购买

MVCC 可以让两个事务都读到对自己可见的库存 `1`，但它不会自动替业务完成抢购判定。

常见做法是把库存检查与扣减放进同一条条件更新：

```sql
UPDATE product
SET stock = stock - 1
WHERE id = 1001
  AND stock > 0;
```

在商品 ID 唯一且记录存在的前提下，影响行数为 `1` 表示本次扣减成功；为 `0` 表示当前没有可扣减的匹配记录。订单与扣库存还要放在合适的事务中提交，不能只凭一次快照查询决定购买成功。

### 6.3 长时间持有旧视图，会拖住历史版本清理

旧版本不能无限保留，也不能在写事务刚提交时立即全部删除。InnoDB 的 purge 会在相关历史信息不再被活跃视图等机制需要时，逐步清理它们。

如果一个 RR 报表事务长期持有旧 Read View，期间其他事务持续修改数据，某些更新 undo 就必须继续保留，可能增加存储占用和旧版本还原成本。

因此，即使只执行查询，也应及时结束事务。分批、分事务导出可以缩短单次事务，但跨批次是否还需要同一快照，要另行设计。

### 6.4 “非锁定一致性读”不等于“任何时候都不会等待”

普通一致性读通常不依赖行锁来阻塞其他事务修改，但仍会涉及元数据锁、内部同步和磁盘访问。例如，与表结构变更发生冲突时，查询也可能等待。

更准确的理解是：**MVCC 减少了普通读取与写入之间因行数据冲突产生的等待，它不能消除所有等待，也不能代替写入时的锁。**

## 七、🎤 高频面试题

### 7.1 MVCC 是怎样实现的

> InnoDB 利用记录中的事务 ID、回滚指针以及 undo 信息形成逻辑版本链，再用 Read View 判断版本是否可见。普通一致性读从当前版本开始检查，不可见就还原更旧的版本，直到找到合适版本或确定该行对快照不存在。

### 7.2 为什么事务已经提交，RR 还是读不到它的修改

> 可见性取决于快照建立时的状态。如果该事务在 Read View 建立时尚未提交，它的 ID 会保留在旧视图的活跃集合中；随后提交不会改变旧视图的判断结果。

### 7.3 RC 和 RR 的 Read View 有什么区别

> RC 每次普通一致性读获取新的视图，RR 通常复用同一事务首次一致性读建立的视图。两者使用类似的版本判断机制，区别主要在视图的建立与复用时机。

### 7.4 Read View 是数据库的一份完整副本吗

> 不是。它主要保存用于判断版本可见性的事务信息；需要读取旧内容时，InnoDB 再通过当前记录与 undo 信息还原对应版本。

### 7.5 MVCC 能完全代替锁吗

> 不能。MVCC 主要优化普通读取与写入的并发，写写冲突和锁定操作仍然需要锁；业务上还要通过条件更新或版本检查等方式保护并发修改。

### 7.6 旧版本为什么不能在写事务提交后马上清理

> 写事务提交后，其他事务持有的旧 Read View 仍可能需要修改前的版本。只要相关视图还需要这些历史信息，就不能立即清理对应 undo；长事务因此可能增加历史版本保留成本。

## 八、📌 快速回顾与后续阅读

```text
版本链：旧版本从哪里来？         → 当前记录 + undo 信息
Read View：我能看到哪一版？      → 事务 ID 边界 + 活跃集合 + 自己的修改
查询：怎么找出合适版本？         → 从新到旧，逐个判断
RC/RR：为什么读取结果不同？      → 新建视图与复用视图的时机不同
使用边界：能否直接据此安全修改？ → 还要条件更新、锁及事务配合
历史清理：什么时候能删旧信息？   → 不再被相关视图等机制需要之后
```

继续阅读 [[6.MySQL 锁]]，理解锁定读取、写写冲突、范围锁与死锁。
