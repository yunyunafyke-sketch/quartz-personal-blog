## 一、💡 一句话理解

> [!tip] 核心结论
> `aboss-sso` 没有一套覆盖所有入口的全局异常处理器。它主要在 Facade 层用 `AbossBaseOperateTemplate` 把异常转换成失败的 `ResultModel`；事务方法还会主动标记回滚。Web 直连接口、外部网关和鉴权 Pipeline 则各自采用不同的异常出口。

最核心的链路是：

```text
Executor / Gateway / Pipeline Handler 发现错误
                    ↓
       抛出 BizRuntimeException 或其他异常
                    ↓
             由入口边界决定怎么返回
                    ↓
RPC Facade → ResultModel      外部网关 → JSON
鉴权 Pipeline → AuthDTO      Web 直连 → Spring MVC
```

因此，理解本项目异常处理时不能只问“抛了什么异常”，还必须继续问：

> **这次请求从哪个入口进来，最外层由谁接住异常？**

## 二、🧭 理论：异常处理在解决什么问题

### 2.1 异常只是内部信号，不是最终响应

业务代码抛异常，表示当前流程不能继续。例如：

```java
// 业务校验失败：使用业务异常携带错误编码和可读信息
throw new BizRuntimeException(
        ErrorCode.PARAMETER_ERROR.getErrCode(),
        "账户不存在!"
);
```

这个异常首先在 Java 调用栈中向外传播。它本身并不等于 HTTP 响应，也不等于 RPC 返回值。

系统边界还要完成一次“翻译”：

| 内部结果 | 对外形式 | 本项目中的例子 |
| --- | --- | --- |
| 业务规则不满足 | 失败状态、业务提示 | `ResultModel.status=F` |
| 未知程序异常 | 统一系统错误 | `未知系统异常` |
| 外部网关调用失败 | 约定的 JSON | `ExternalErrorResponse` |
| 认证或鉴权不通过 | 专用失败对象 | `AuthDTO.success=false` |
| Web 异常未被项目捕获 | 交给 Spring MVC | `/login-by-code` 等直连接口 |

### 2.2 业务异常与系统异常

本项目主要把异常分成两类：

| 类型 | 白话解释 | 对外策略 |
| --- | --- | --- |
| `BizRuntimeException` | 业务已经预料到的失败，例如参数错误、账户不存在、第三方返回失败 | 通常保留可读错误信息 |
| 其他 `Exception` | 代码错误、空指针、数据库异常等未明确分类的问题 | 隐藏内部细节，统一返回“未知系统异常” |

这种区分的目的，是既让调用方知道可处理的业务原因，又避免把堆栈、SQL、服务器地址等内部信息暴露出去。

### 2.3 异常传播、转换与吞掉

三个术语容易混淆：

- **传播**：当前方法不处理，异常继续交给上一层。
- **转换**：捕获底层异常，改成统一业务异常或失败响应。
- **吞掉**：捕获异常后既不抛出，也没有返回明确失败结果，流程可能继续运行。

本项目三种情况都存在。前两种是正常机制；第三种需要特别谨慎，因为它可能掩盖真正的故障。

## 三、⚙️ 理论：本项目的异常处理链路

### 3.1 异常通常在哪里产生

异常主要来自以下位置：

| 位置 | 常见原因 | 典型行为 |
| --- | --- | --- |
| Facade 参数校验 | 必填字段为空、格式错误 | 抛 `BizRuntimeException` |
| Executor | 业务规则不满足 | 抛 `BizRuntimeException` |
| Pipeline Handler | IDaaS、ACL 等步骤失败 | 转成业务异常，或返回失败对象 |
| Infrastructure Gateway | 数据不存在、外部服务失败 | 抛 `BizRuntimeException` |
| 数据库、Redis、序列化 | 非预期技术故障 | 抛普通运行时异常 |

例如 `LoginFacadeImpl` 在参数校验失败时抛出业务异常：

```java
// ValidationTool 返回校验结果；不通过时终止本次业务流程
Failed result = (Failed) validationTool.validate(passwordLoginCmd);
if (!result.isPass()) {
    throw new BizRuntimeException(
            ErrorCode.PARAMETER_ERROR.getErrCode(),
            result.getMessage()
    );
}
```

### 3.2 Facade 的统一模板是主要异常边界

大多数 RPC Facade 不直接写重复的 `try/catch`，而是把校验、执行和收尾操作交给：

```text
aboss-sso-app/.../template/AbossBaseOperateTemplate.java
```

模板按以下顺序执行：

```text
callback.check()
        ↓
callback.execute()
        ↓
callback.afterExecute()
        ↓
设置 status=S
```

任意一步抛出异常，都会直接跳到对应的 `catch`，后面的步骤不再执行。

普通模板的核心逻辑可以简化为：

```java
public void operate(AbossBaseOperateCallback callback,
                    ResultModelSupport<?> result) {
    try {
        // 1. 校验输入；失败时可以抛业务异常
        callback.check();

        // 2. 执行业务；Executor、Gateway 的异常会继续向这里传播
        callback.execute();

        // 3. 正常执行后的扩展动作
        callback.afterExecute();

        // 4. 三步全部完成才标记成功
        result.setStatus(Status.S.getValue());
    } catch (BizRuntimeException e) {
        // 业务异常：记录完整堆栈，对调用方保留业务提示
        log.error("Business exception [resultCode= {} ]",
                e.getErrorCode(), e);
        result.setStatus(Status.F.getValue());
        result.setMessage(new Message(e.getMessage()));
    } catch (Exception e) {
        // 未知异常：日志保留真实原因，对外只返回统一描述
        log.error("System exception [resultCode= {} ]",
                ErrorCode.UNKNOW_SYSTEM_ERROR.getErrCode(), e);
        result.setStatus(Status.F.getValue());
        result.setMessage(new Message(
                ErrorCode.UNKNOW_SYSTEM_ERROR.getErrDesc()
        ));
    }
}
```

> [!info] 为什么调用方收不到 Java 异常
> 模板已经捕获异常，并把它改写成了一个正常返回的 `ResultModel`。从 RPC 框架和外层 AOP 看，Facade 方法完成了正常返回，只是返回对象内部的 `status` 是失败。

### 3.3 事务模板为什么主动调用 `setRollbackOnly()`

写操作使用 `operateWithTransAction()`。它标注了：

```java
@Transactional(rollbackFor = Exception.class)
```

但模板会在方法内部捕获异常。异常没有继续抛出事务代理时，事务代理看到的是“方法正常结束”，不能单靠 `rollbackFor` 判断失败。

因此两个 `catch` 都会执行：

```java
// 取得当前事务状态，并明确告诉 Spring：本次事务只能回滚
TransactionAspectSupport.currentTransactionStatus()
        .setRollbackOnly();
```

完整因果关系是：

```text
数据库写入过程中发生异常
          ↓
模板在方法内部 catch 住异常
          ↓
异常不再向事务代理传播
          ↓
主动 setRollbackOnly()
          ↓
方法返回失败 ResultModel，事务最终回滚
```

Spring 官方文档明确说明：事务代码可以在事务上下文中调用 `setRollbackOnly()`，主动把当前事务标记为只能回滚。

### 3.4 登录 Pipeline 遇到异常为什么会停止

登录执行器使用普通 `for` 循环依次调用 Handler：

```java
for (LoginContextHandler<? super LoginPipelineContext> handler : pipeline) {
    // Handler 抛出异常时，循环立即退出，不会进入下一个 Handler
    handler.handle(loginPipelineContext);
}
```

因此，IDaaS 登录或用户信息查询失败后，后续查询本地账户、生成 SSO JWT、单设备登录和写 Cookie 都不会继续执行。

部分 Handler 会把所有底层异常统一转换为业务异常。例如 `UserInfoPipelineHandler` 把 IDaaS 查询失败统一转换为 `THIRD_ERROR`。

### 3.5 RPC Facade 最终怎样返回失败

以密码 RPC 登录为例：

```text
LoginController.loginByRPCPassword()
            ↓
LoginFacadeImpl.loginByPassword()
            ↓
AbossBaseOperateTemplate.operate()
            ↓
PasswordLoginExecutor.execute()
            ↓
某个 Pipeline Handler 抛异常
            ↓
operate() 捕获并填写 ResultModel
            ↓
Controller 正常返回失败 ResultModel
```

预期响应的语义类似：

```json
{
  "status": "F",
  "message": {
    "message": "参数错误或具体业务原因"
  },
  "data": null
}
```

具体 JSON 字段仍以公共 `ResultModel` 依赖的实际序列化结果为准。

### 3.6 Web 直连登录绕过了统一模板

下面两个接口直接调用 Web Pipeline Executor：

```text
POST /platform/api/aboss/sso/login-by-code
POST /platform/api/aboss/sso/login-by-password
```

它们没有经过 `AbossBaseOperateTemplate`。源码中也没有找到项目自定义的 `@ControllerAdvice` 或 `@ExceptionHandler`。

所以 Handler 抛出的异常会继续离开 Controller，交给 Spring MVC 的异常解析链和 Spring Boot 默认错误处理机制。实际 HTTP 状态和响应体还可能受到部署网关或公共依赖配置影响，但从当前项目源码看，它与 RPC Facade 的失败 `ResultModel` 不是同一套出口。

### 3.7 外部网关自己组装错误 JSON

实现 `ReceiveService` 的外部接口会在 `invoke()` 中自行捕获异常，并返回 `ExternalErrorResponse`：

```java
try {
    // 执行外部登录流程
    externalLoginToken = externalOauth2LoginCmdExe.execute(command);
} catch (Exception e) {
    // 记录异常，并返回合作网关约定的 JSON 字符串
    log.error("第三方 oauth2 登录异常", e);
    return JSON.toJSONString(
            new ExternalErrorResponse()
                    .setErrorCode("400")
                    .setErrorMessage(e.getMessage())
    );
}
```

这里的 `400` 或 `500` 是响应 JSON 中的业务字段，不一定等于真实 HTTP 状态码，因为方法本身返回的是字符串。

### 3.8 认证与鉴权使用失败对象短路

鉴权 Pipeline 不只依靠异常。每个 Handler 会返回 `AuthDTO`，Executor 检查：

```java
authDTO = handler.handle(authenticationPipelineContext);
if (!authDTO.isSuccess()) {
    // 当前步骤判定失败，直接结束，不再调用后续 Handler
    return authDTO;
}
```

这是“返回值短路”，与登录 Pipeline 的“异常中断”不同。

### 3.9 AOP 日志看到的结果可能和直觉不同

`LogAopConfig` 的日志写在 `joinPoint.proceed()` 之后。

- 如果异常直接离开 Facade，`proceed()` 后面的成功日志不会执行。
- 如果异常已被 `AbossBaseOperateTemplate` 转成失败 `ResultModel`，Facade 会正常返回，AOP 仍会打印入参、返回值和耗时。

所以看到 Facade AOP 的返回日志，只能说明 Java 方法正常返回，不能说明业务成功。还必须检查返回对象中的 `status`。

## 四、🚀 实践：从异常产生到验证

### 4.1 前置准备

本笔记依据的项目源码为：

```text
/Volumes/data/ideaWorkSpace/aboss-sso
```

根 `pom.xml` 声明的 Spring Boot 版本为 `2.1.3.RELEASE`。验证时需要能够启动 `start` 模块，并能查看：

```text
./logs/aboss-sso/common-default.log
./logs/aboss-sso/common-error.log
```

日志绝对位置的判断方法见 [[日志文件在哪里]]。

### 4.2 可以拿来干什么

#### 4.2.1 根据返回形式判断请求走了哪条异常链

| 观察到的现象 | 优先检查的入口 |
| --- | --- |
| HTTP 200，但 `ResultModel.status=F` | Facade 模板已捕获异常 |
| HTTP 500 或 Spring Boot 默认错误体 | Web 直连 Executor，异常未被项目捕获 |
| 返回字符串 JSON，里面有 `errorCode=400/500` | 外部 `ReceiveService` 自行组装错误 |
| `AuthDTO.success=false` | 认证或鉴权 Pipeline 主动短路 |

#### 4.2.2 根据日志定位异常层次

检索下面的固定日志前缀：

```text
Business exception [resultCode=
System exception [resultCode=
第三方oauth2登录异常
authentication , request
Access ControlAspect around error
```

输入是调用方看到的错误响应；处理过程是先按响应结构确定入口，再用固定日志前缀找到捕获点；结果是把排查范围缩小到 Facade 模板、外部网关、鉴权 Pipeline 或 AOP。

### 4.3 完整实践：验证业务异常、事务回滚和日志

#### 4.3.1 验证普通 Facade 业务异常

调用 RPC 密码登录对应的 HTTP 转发接口，并故意缺少必要参数：

```bash
curl -i \
  -X POST 'http://localhost:8080/platform/api/aboss/sso/login-byRPC-password' \
  -H 'Content-Type: application/json' \
  -d '{}'
```

预期过程：

```text
ValidationTool 校验失败
  → LoginFacadeImpl 抛 BizRuntimeException
  → AbossBaseOperateTemplate 捕获
  → ResultModel.status 设为 F
  → 返回业务校验信息
```

同时应在错误日志中看到 `Business exception` 和堆栈。

#### 4.3.2 对比 Web 直连接口

使用同样的空参数调用直连密码登录接口：

```bash
curl -i \
  -X POST 'http://localhost:8080/platform/api/aboss/sso/login-by-password' \
  -H 'Content-Type: application/json' \
  -d '{}'
```

该接口绕过 Facade 模板。若 Pipeline 中出现未捕获异常，响应应由 Spring MVC、Spring Boot 或上层网关处理，不应假定它与上一请求具有相同的 `ResultModel` 结构。

#### 4.3.3 验证事务异常确实回滚

选择一个使用 `operateWithTransAction()` 的写接口，在测试环境构造“前一条数据库写入成功、后一操作抛异常”的场景：

1. 调用前查询目标数据并记录状态。
2. 发起写请求，使执行过程在中途抛出业务异常。
3. 确认响应为失败 `ResultModel`。
4. 再次查询数据库，确认前面已经执行的写入没有提交。
5. 在日志中确认出现 `Business exception` 或 `System exception`。

> [!warning] 数据库安全
> 这项验证只能在测试环境使用可回收数据进行。执行任何写入 SQL 前，需要先展示完整 SQL、目标库表和预计影响范围，并取得明确的“确认执行”。

#### 4.3.4 关键报错排查

| 现象 | 可能原因 | 排查动作 |
| --- | --- | --- |
| 失败结果没有错误码 | 使用了普通 `operate()`，业务异常分支只设置 message | 对照普通模板与事务模板 |
| 异常后数据仍被提交 | 写操作误用了 `operate()`，或没有处于 Spring 事务代理中 | 检查调用的模板方法和代理边界 |
| AOP 有返回日志但业务失败 | 异常已被模板转成失败对象 | 查看 `ResultModel.status` |
| Web 登录返回 500 | 直连 Executor，未经过统一模板 | 检查 `/login-by-code`、`/login-by-password` |
| 鉴权日志先报 ACL 异常，随后又空指针 | 捕获异常后仍使用空的 ACL 结果 | 检查 `AuthenticationPipelineHandler` |
| Access 检查报错后业务仍执行 | `AccessAspect` 捕获自身异常后继续 `proceed()` | 判断是否符合安全策略 |

## 五、⚠️ 当前实现的边界与风险

### 5.1 返回错误码不一致

普通 `operate()` 捕获 `BizRuntimeException` 时只设置错误信息，没有设置 `Message.code`；`operateWithTransAction()` 会写入 `e.getErrorCode()`。

这会导致同一种业务异常，因为是否使用事务模板而产生不同返回结构。

### 5.2 存在两套 ErrorCode

项目同时存在：

```text
aboss-sso-client/.../dto/data/ErrorCode.java
aboss-sso-infrastructure/.../constant/ErrorCode.java
```

未知异常编码还分别出现：

```text
UNKNOWN_SYSTEM_ERROR
UNKNOW_SYSTEM_ERROR
```

调用方按错误码编写判断逻辑时，容易出现兼容问题。

### 5.3 AuthenticationPipelineHandler 可能产生二次异常

普通账户鉴权调用 ACL 失败时，代码会记录异常，但没有立即返回失败对象。之后仍执行：

```java
resourcesPermissionResDTO.getHasPermission()
```

如果结果仍为 `null`，会再产生一次 `NullPointerException`，掩盖最初的 ACL 故障。

### 5.4 AccessAspect 在自身异常时继续放行

`AccessAspect` 捕获访问控制查询异常后，只记录日志，随后仍调用：

```java
return joinPoint.proceed();
```

也就是说：明确查到未授权时拒绝；但访问控制机制自身故障时继续执行目标方法。这属于 **fail-open（故障时放行）** 行为，应由业务和安全要求明确确认。

### 5.5 日志和响应可能泄露敏感信息

当前代码存在以下风险：

- `UserInfoPipelineHandler` 在异常日志中输出完整 IDaaS access token；
- 部分外部接口记录完整请求对象，其中可能包含用户名、密码或 Token；
- 部分接口把 `e.getMessage()` 原样返回给外部调用方。

建议排查时只记录脱敏标识、TraceId、错误码和必要上下文，不记录密码、授权码、完整 Token 或密钥。

### 5.6 日志 AOP 不是异常处理器

`LogAopConfig` 的职责是记录 Facade 和外部实现的入参、返回值与耗时。它没有统一捕获、转换异常，也不能代替 Facade 模板或 Spring MVC 的异常处理机制。

## 六、📌 总结

- 项目最主要的异常边界是 `AbossBaseOperateTemplate`，不是全局 `ControllerAdvice`。
- `BizRuntimeException` 表达可预期业务失败，普通 `Exception` 被统一隐藏为系统异常。
- 事务模板捕获异常后必须主动 `setRollbackOnly()`，否则事务代理会把方法视为正常结束。
- 登录 Pipeline 依靠异常中断；鉴权 Pipeline 主要依靠失败 `AuthDTO` 短路。
- Web 直连、RPC Facade、外部网关的异常响应格式并不统一。
- 运维排查时，先确认入口，再看最外层由谁捕获，最后结合 ERROR 日志和 TraceId 定位原始异常。
- 当前实现需要重点关注错误码不一致、鉴权二次空指针、Access 故障时放行和敏感日志问题。

快速记忆句：

> **异常从里往外抛，入口负责翻译；事务异常被接住后，还要主动标记回滚。**
