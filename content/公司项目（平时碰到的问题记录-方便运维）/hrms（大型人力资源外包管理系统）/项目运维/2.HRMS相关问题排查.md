## 1. 人员手机号检验规则

创建外包人员时，`phone` 字段会经过以下校验：

1. **必填校验**：手机号不能为空；为空时返回“手机号不能为空”。
2. **格式校验**：必须是 11 位中国大陆手机号，格式为 `^1[3-9]\\d{9}$`：以 `1` 开头，第二位为 `3` 至 `9`，其余为 9 位数字；不符合时返回“手机号格式错误”。
3. **唯一性校验**：保存时由数据库唯一索引 `uk_contact_number` 兜底限制，手机号重复时返回“手机号已存在”。

校验位置

- 请求字段的必填与格式：`CreateStaffCmd.phone`。
- 请求参数校验：`OutsourcedStaffWebValidator.validateCreateStaff` 调用统一参数校验。
- 手机号唯一性：新增员工插入数据库时捕获唯一索引冲突并转换为业务提示。

## 2. 人员批量导入提示“批次号不存在有效记录”

点击“批量保存员工”时，系统会按批次号查询导入明细中状态为 `1` 的记录；查询结果为空时，即提示“批量导入员工信息批次号不存在有效记录”。

常见触发情况：

1. 该批次没有成功写入导入明细，例如文件导入未完成或未插入任何记录。
2. 导入明细已被全部删除或清空。
3. 导入的所有员工均校验失败，明细状态均为 `0`。
4. 原本有效的明细在后续保存处理中因手机号与已有员工冲突等原因被标记为失败。

导入明细可能因机构或岗位不存在、无机构权限、手机号重复、证件类型或号码不合法、码值校验失败、线客必填项缺失，以及员工状态不允许关联当前项目等原因而变为失败。应先在批次明细页查看各条记录的失败原因，修正后重新导入。

校验代码：`OutsourcedStaffBatchSaveHandler.getValidBatchRecords`，查询条件为 `batch_id = 当前批次号` 且 `status = 1`。

## 3. 人员批量导入提示“无此机构权限”

报错原因：本次导入传入的 `permissionOrgCode` 权限范围不包含待新增人员的归属部门/团队。

### 3.1 `permissionOrgCode` 可以管理哪些机构

| `permissionOrgCode` 所属机构 | 可管理范围        |
| ------------------------ | ------------ |
| 总公司 `210000000000`       | 不限制机构范围      |
| 一级机构                     | 本机构及下属二、三级机构 |
| 二级机构                     | 本机构及下属三级机构   |
| 三级机构                     | 本机构及其上级二级机构  |

### 3.2 如何查看机构级别

在组织中心按 `permissionOrgCode` 查询机构详情，查看 `branchOrgLevel`：

| `branchOrgLevel` | 机构级别 |
| --- | --- |
| `0` | 总公司（一级机构） |
| `1` | 分公司（二级机构） |
| `2` | 中心支公司（三级机构） |

如果 `permissionOrgCode` 是团队编码，系统会向上找到最近的经营组织，再按该经营组织的级别计算权限。

### 3.3 示例

`permissionOrgCode` 属于 A 支公司，只能管理 A 支公司及其下属机构；Excel 中待新增人员填写的是 B 支公司的电融团队，因此超出权限范围，提示“无此机构权限”。

排查时只需对比：

1. 导入请求中的 `permissionOrgCode`。
2. Excel 中待新增人员的“人员归属部门/团队编码”（`branchOrgCode`）。

如果一个批次的人员全部因此校验失败，保存时还会提示“批次号不存在有效记录”。

### 4.1 分页接口如何查询并返回审批单信息

分页接口 `hrms/staff/query-staff-page` 不支持通过请求参数直接查询 `requestId` 或 `flowInstanceId`。仅当人员处于审批相关状态，且申请单关联数据完整时，服务端才会在响应中自动补充这两个字段。

#### 请求条件

请求中需传入有权限的机构编码，并在 `staffStatusList` 筛选审批相关状态：

```json
{
  "current": 1,
  "pageSize": 20,
  "permissionOrgCode": "你的机构权限编码",
  "staffStatusList": ["-3", "-2", "2", "3"]
}
```

| 状态值 | 人员状态 |
| --- | --- |
| `-3` | 入场审批中 |
| `-2` | 审批通过待入场 |
| `2` | 离场审批中 |
| `3` | 审批通过待离场 |

#### 关联数据要求

人员、申请记录和申请单需满足以下关联及状态条件：

```text
outsourced_staff_onoffboard_application_record.account_id
    = 人员 staffId

outsourced_staff_onoffboard_application_record.application_batch_id
    = outsourced_staff_onoffboard_application.id
```

- 申请单 `status` 为 `approving`、`approved` 或 `fail`；
- `application.id` 不等于 `application.flow_instance_id`；
- `flow_instance_id` 已成功写入。

满足条件后，接口自动返回：

```json
{
  "requestId": "申请单 ID（application.id）",
  "flowInstanceId": "流程实例 ID（application.flow_instance_id）"
}
```

#### 字段为 `null` 的常见原因

当人员状态为 `-1`、`0`、`1`，或申请单、申请记录不存在，或流程实例 ID 尚未写入时，`requestId` 和 `flowInstanceId` 均会返回 `null`。



### 4.2 审批单无法检索时的数据修复与重试

当离场申请状态为成功，但页面无法找到审批单时，可将该申请及关联记录恢复为失败状态，再在页面发起重试。该操作会修改 HRMS 业务库数据，应先在目标环境核对人员、申请单和记录的关联关系，并在事务中执行。

#### 处理步骤

1. 通过 `staff_id` 查询离场申请单，确认需要处理的申请单 `id` 和当前状态。

   ```sql
   SELECT id, staff_id, status
   FROM outsourced_staff_onoffboard_application
   WHERE staff_id = '<staff_id>';
   ```

2. 将确认无误的申请单状态由 `success` 改为 `fail`。本次示例申请单 ID 为 `7503021854042873856`。

   ```sql
   UPDATE outsourced_staff_onoffboard_application
   SET status = 'fail'
   WHERE id = '7503021854042873856'
     AND status = 'success';
   ```

3. 通过人员 `staff_id`（对应记录表的 `account_id`）查询申请记录，确认其与申请单的关联字段及当前状态。

   ```sql
   SELECT id, account_id, application_batch_id, status
   FROM outsourced_staff_onoffboard_application_record
   WHERE account_id = '<staff_id>';
   ```

4. 将关联申请记录的状态改为 `2`（失败）。申请记录通过 `account_id` 关联人员 `staffId`，通过 `application_batch_id` 关联申请单 ID；执行前需先确认两项关联关系。

   ```sql
   UPDATE outsourced_staff_onoffboard_application_record
   SET status = 2
   WHERE account_id = '<staff_id>'
     AND application_batch_id = '7503021854042873856';
   ```

5. 回到 HRMS 页面重新查询审批单，确认申请单已可检索后点击“重试”。





## 5. 外部账号返聘提示“账户不存在”

外部账号返聘时，SSO 会先在本地账户表中查询待返聘账号；查询不到记录时返回“账户不存在!”。

### 5.1 触发条件

查询条件由请求参数决定：

| 请求参数情况 | 实际查询条件 | 会报“账户不存在”的情况 |
| --- | --- | --- |
| 传入 `accId` | `accountId + externalSource` | 对应账号不存在，或账号的外部来源与传入的 `externalSource` 不一致 |
| 未传 `accId`，传入 `externalId` | `externalId + externalSource` | 对应账号不存在，或账号的外部来源与传入的 `externalSource` 不一致 |

`accId` 的优先级高于 `externalId`：两个字段同时传入时，系统只按 `accId + externalSource` 查询。

如果 `accId` 和 `externalId` 都未传，提示为“accId 或 externalId 不能同时为空”，不属于“账户不存在”。

### 5.2 HRMS 入场失败后点击“重试”的实际传参（返聘分支）

HRMS 人员的 `account_id` 非空时，入场重试会进入“返聘已有外部账号”分支。调用账号中心返聘接口时传入：

| 参数 | HRMS 取值 |
| --- | --- |
| `accId` | 外包人员表 `outsourced_staff.account_id` |
| `accountStartDt` | 入场申请日期，格式为 `yyyy-MM-dd` |
| `accountEndDt` | 固定为 `9999-12-31` |
| `phoneNo` | 外包人员的历史手机号 `history_contact_number` |
| `externalSource` | 固定为 `P010068`（HRMS 外包账号来源） |

该调用**不传** `externalId`、证件号码、项目 ID 或协议 ID。因此，入场重试报“账户不存在”时，应优先核对 `outsourced_staff.account_id` 对应的 SSO 账号是否存在，且其外部来源是否为 `P010068`。仅将内部账号 ID 写入 `account_id`，会导致 HRMS 调用外部账号返聘接口并出现此问题。

### 5.3 排查步骤

1. 核对返聘请求中的 `accId`；若使用旧字段，则核对 `externalId` 是否正确。
2. 核对 `externalSource` 是否与该账户入库时的外部来源完全一致。
3. 在 SSO 账户表中按上述组合条件查询，确认账号是否已创建或同步；未入库的账号不能通过返聘接口恢复。
4. 账号能查到后，如仍返聘失败，查看账号中心的返回信息，确认其是否为外部账号、当前是否已离职，以及返聘手机号是否被在职账号占用。

这里是在确认账号中心是否允许“恢复这一个已有账号”，不是 HRMS 再次查询本地人员表。HRMS 仅将 `account_id`、`history_contact_number`、申请日期等参数传给账号中心，并把账号中心的失败信息返回；账号类型、是否已离职、手机号是否与有效账号冲突，均由账号中心的返聘逻辑判定。当前 HRMS 代码未包含这些账号中心校验规则的实现，因此应以账号中心接口响应或其账户表数据作为最终依据。

对应实现：`ExternalAccountRehiredCmdExe.init`。
