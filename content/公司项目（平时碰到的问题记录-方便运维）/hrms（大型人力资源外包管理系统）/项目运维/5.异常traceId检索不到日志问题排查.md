# 异常 traceId 检索不到日志问题排查

## 一、问题现象

访问“内转人员查询”接口 `query-internal-outsourced-staff-page` 发生异常时，页面提示“响应错误，请稍后重试”，并展示 traceId，例如：

```text
0ac5e490178892320877746437481
```

使用该 traceId 在日志平台检索，却没有找到对应的异常日志。

## 二、结论

当前现象更可能是“异常日志写入位置或日志格式与检索方式不匹配”，而不是异常完全没有记录。项目中至少存在以下三个问题。

### 2.1 标准输出日志未包含 traceId

`bootstrap/src/main/resources/log4j2.xml` 中，`STDOUT-APPENDER` 的输出格式为：

```xml
%d{yyyy-MM-dd HH:mm:ss.SSS},%t,%r,%c{2},%-5p  - %m%n%throwable
```

该格式未输出 `%X{SOFA-TraceId}`。如果云上日志平台采集的是容器标准输出，即使应用已经输出了异常堆栈，日志文本中也没有 traceId，因此不能通过页面上的 traceId 搜到日志。

### 2.2 业务异常不会写入 common-error.log

业务代码包 `com.aliyun.fsi.insurance` 配置了独立日志器，且 `additivity="false"`，只绑定：

- `STDOUT-APPENDER`
- `APP-DEFAULT-APPENDER`

没有绑定 `ERROR-APPENDER`。因此该包下的 `log.error(...)` 不会继续向根日志器传递，也不会写入 `common-error.log`，而会写到：

```text
./logs/aboss-property-hrms/app-default.log
```

如果日志平台只采集 `common-error.log`，则自然查不到该异常。

### 2.3 页面 traceId 与 SOFA-TraceId 可能不是同一个值

滚动文件日志使用 `%X{SOFA-TraceId}` 输出 SOFA Tracer 写入 MDC 的链路标识；页面 toast 中的 traceId 可能由网关生成或由上游服务透传。

若网关的 trace header 没有正确透传、名称与 SOFA Tracer 不兼容，或应用侧重新生成了链路标识，则页面的 traceId 和服务日志中的 `SOFA-TraceId` 会不一致。

## 三、接口异常处理链路

本次页面对应的 Controller 调用链为：

```text
POST /query-internal-outsourced-staff-page
  → OutsourcedStaffController
  → OutsourcedStaffWebImpl
  → AbossOperateTemplateBuilder
  → 领域服务 / 仓储
```

`AbossOperateTemplateBuilder` 会捕获业务异常和普通异常，并调用：

```java
log.error("业务异常 [code={}]", e.getErrorCode(), e);
log.error("系统异常", e);
```

因此，只要请求已进入该模板并在其回调中抛出异常，应用进程理论上会记录异常堆栈。

但 Controller 最终只返回 `ResultModel` 的 `getData()`：

```java
return outsourcedStaffWeb.queryInternalOutsourcedStaffPage(cmd).getData();
```

模板已包装的失败错误码和错误信息未被保留给调用方，容易表现为前端的通用“响应错误”。

若异常发生在进入 Controller 之前，例如网关路由、鉴权、请求体解析、网络超时，则不会经过该模板，也不会有这里的业务异常日志。

## 四、建议排查顺序

1. 先按发生时间和接口路径 `query-internal-outsourced-staff-page` 检索标准输出或 `app-default.log`，确认请求是否已进入 HRMS 服务。
2. 在浏览器 Network 中查看失败请求的 Request Headers 和 Response Headers，确认页面 traceId 的来源及其 header 名称。
3. 查看同一时段 `app-default.log` 中的 `%X{SOFA-TraceId}`，与页面 traceId 对照。
4. 若应用日志没有该接口访问或异常记录，继续查网关、鉴权服务和上游调用链。
5. 确认云上日志采集范围：是采集标准输出、`app-default.log`，还是仅采集 `common-error.log`。

## 五、修复建议

### 5.1 在标准输出中打印链路标识

调整 `STDOUT-APPENDER` 的日志格式，至少加入：

```xml
[%X{SOFA-TraceId} %X{SOFA-SpanId}]
```

示例：

```xml
<PatternLayout pattern="%d{yyyy-MM-dd HH:mm:ss.SSS},%t,%r,%-5p,[%X{SOFA-TraceId} %X{SOFA-SpanId}] %c{2} - %m%n%throwable" charset="UTF-8"/>
```

这样，无论日志平台采集标准输出还是文件，都可直接用 traceId 检索。

### 5.2 将业务错误同时写入错误日志

为 `com.aliyun.fsi.insurance` 日志器增加：

```xml
<AppenderRef ref="ERROR-APPENDER"/>
```

使业务代码的 `ERROR` 级别日志也进入 `common-error.log`，避免错误分散在日常业务日志中。

### 5.3 统一网关与应用的 traceId 传递

确认网关透传的 trace header 与 SOFA Tracer 的接收规范一致。目标是让页面展示的 traceId、应用日志 `%X{SOFA-TraceId}` 及上下游服务链路 ID 相同。

### 5.4 保留统一失败响应

评估 Controller 不再直接丢弃 `ResultModel` 的可行性，确保失败时前端能获得标准错误码、错误信息和可用于定位的 traceId，减少通用“响应错误”掩盖真实故障的情况。

## 六、涉及代码位置

- `bootstrap/src/main/resources/log4j2.xml`
- `service/src/main/java/com/aliyun/fsi/insurance/hrms/service/template/AbossOperateTemplateBuilder.java`
- `bootstrap/src/main/java/com/aliyun/fsi/insurance/hrms/controller/staff/OutsourcedStaffController.java`
- `service/src/main/java/com/aliyun/fsi/insurance/hrms/service/impl/OutsourcedStaffWebImpl.java`
