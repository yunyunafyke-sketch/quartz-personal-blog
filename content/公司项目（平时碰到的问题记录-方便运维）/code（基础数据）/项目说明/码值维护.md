## MQ 消息体

```json
{
  "codeType": "example_code_type",
  "action": "ADMITTANCE",
  "releaseUnitId": 123456789,
  "codeTableId": 987654321
}
```

| 字段 | 含义 | 使用说明 |
| --- | --- | --- |
| `codeType` | 码表类型编码 | 消费者必填校验字段，也是查询、入库和刷新缓存的业务主键 |
| `action` | 同步动作 | 取 `SyncActionEnum` 对应的 code：`ADMITTANCE`、`CANCEL`、`PASS`、`DELETE` |
| `releaseUnitId` | 发布/审批单元 ID | 准入、取消准入、上线时用于向数据标准平台查询本次审批数据 |
| `codeTableId` | 数据标准平台码表 ID | 准入、取消准入、上线时与 `codeType`、`releaseUnitId` 一起查询码表和码值 |

上面以准入消息为例。发送取消准入、上线或删除消息时，将 `action` 分别替换为 `CANCEL`、`PASS`、`DELETE`。删除分支的代码只使用 `codeType`，不会使用 `releaseUnitId` 和 `codeTableId`；但消费者入口当前只校验 `codeType` 和 `action`，不会提前校验另外两个 ID。

## 消费入口

`DataStandardEventConsumer` 订阅数据标准平台的码表变更消息。消息至少需要包含 `codeType`，并且 `action` 必须是以下四种之一：

- `ADMITTANCE`：准入
- `CANCEL`：取消准入
- `PASS`：上线
- `DELETE`：删除

消费者使用单线程处理消息。校验通过后交给 `BasicCodeChangeExe` 执行；校验失败会记录告警并直接提交消息。执行期间即使出现异常，当前实现也会捕获异常、记录错误并提交消息，因此 MQ 不会自动重试，需要结合日志和数据结果人工确认。

## 数据标准平台接口调用对照

| 动作 | 查询内容 | 调用接口 | 主要请求参数 | 接口返回 |
| --- | --- | --- | --- | --- |
| 准入 `ADMITTANCE` | 当前码表 | `CodeTableFacade#queryByCodeType` | `SyncCodeTableRequest`：`codeType`、`releaseUnitId`、`codeTableId` | `DataplatformResult<SyncCodeTableDTO>` |
| 准入 `ADMITTANCE` | 本次审批码值，分页查询 | `CodeValueFacade#queryCodeValuePageSync` | `CodeValuePageRequest`：`codeType`、`releaseUnitId`、`codeTableId`、`pageIndex`、`pageSize` | `DataplatformResult<DataplatformPaginationInfo<List<SyncCodeValueDTO>>>` |
| 取消准入 `CANCEL` | 回滚码表 | `CodeTableFacade#codeTableRollbackSync` | `SyncCodeTableRequest`：`codeType`、`releaseUnitId`、`codeTableId` | `DataplatformResult<SyncCodeTableDTO>` |
| 取消准入 `CANCEL` | 回滚码值，分页查询 | `CodeValueFacade#codeValueRollbackSync` | `CodeValuePageRequest`：`codeType`、`releaseUnitId`、`codeTableId`、`pageIndex`、`pageSize` | `DataplatformResult<DataplatformPaginationInfo<List<SyncCodeValueDTO>>>` |
| 上线 `PASS` | 当前码表 | `CodeTableFacade#queryByCodeType` | 与准入查询码表相同 | `DataplatformResult<SyncCodeTableDTO>` |
| 上线 `PASS` | 本次审批码值，分页查询 | `CodeValueFacade#queryCodeValuePageSync` | 与准入查询码值相同 | `DataplatformResult<DataplatformPaginationInfo<List<SyncCodeValueDTO>>>` |
| 删除 `DELETE` | 不查询数据标准平台 | 无 | 只使用消息中的 `codeType` 处理本地数据库 | 无上游接口返回 |

上述接口是 `DataStandardGatewayImpl` 调用的数据标准平台 RPC。分页查询会从第 1 页开始，使用配置项 `spring.sofamq.data.standard.page-size` 作为每页大小，直到取完平台返回的全部页。

### 上游接口返回如何处理

- 码表接口：读取 `DataplatformResult` 中的 `success`、`errorMessage` 和 `data`。成功时把 `SyncCodeTableDTO` 转换为本系统的 `BasicType`；响应对象为 `null` 或 `success = false` 时抛出第三方调用异常；`data = null` 时返回 `null`，后续业务处理会因缺少码表数据而失败并进入消费者异常捕获。
- 码值接口：从 `DataplatformPaginationInfo` 中读取当前页码值列表、`pageTotal` 和 `pageCount`，把 `SyncCodeValueDTO` 列表转换为 `BasicCode` 列表。响应对象为 `null` 或 `success = false` 时抛出第三方调用异常；分页数据为空时按空列表处理。
- 删除动作：不调用上游接口，因此没有数据标准平台返回值；本地更新方法的影响行数没有继续向上返回。

### 消费者最终返回

该流程是 MQ 消费，不是 HTTP 接口，没有返回给调用方的业务响应体。监听器最终统一向 MQ 返回 `Action.CommitMessage`，表示提交当前消息：

- 消息校验失败：记录告警后返回 `CommitMessage`。
- 业务处理成功：返回 `CommitMessage`。
- RPC、数据库或解析处理异常：捕获并记录错误后仍返回 `CommitMessage`。

因此，`CommitMessage` 只代表这条 MQ 消息已被消费端提交，不代表码表和码值一定同步成功；异常场景不会依靠这条消息自动重试。

## 四种动作分别做什么

### 1. 准入（ADMITTANCE）

准入的目标是把本次审批对应的数据同步到测试侧，供正式上线前验证：

1. 调用 `CodeTableFacade#queryByCodeType`，使用消息中的 `codeType`、`releaseUnitId`、`codeTableId` 查询数据标准平台的当前码表信息。
2. 按 `typeCode` 将码表信息写入 `t_abs_basic_type`：不存在则新增，存在则沿用原 `typeId` 更新。
3. 调用 `CodeValueFacade#queryCodeValuePageSync`，分页查询本次审批对应的码值。
4. 将码值写入非生产表 `t_abs_non_prod_code`：
   - 该码表在非生产表中没有数据时，按每批 1000 条批量新增；
   - 已有数据时，按 `typeCode + basicCode` 匹配，匹配到则沿用原 `codeId` 更新，未匹配到则新增。

准入不会把码值写入生产码值表 `t_abs_basic_code`。

### 2. 取消准入（CANCEL）

> [!tip] 大白话解释
> 可以把非生产码值表想成一张测试用的 Excel。准入时把新内容写进这张表；取消准入时，系统向数据标准平台要回旧内容，再把平台返回的旧内容逐条写回来。平台返回了哪一条，就恢复哪一条；平台没有返回的内容，本系统不会主动删除，仍然保持原样。简单说就是：**取消准入 = 把平台给的旧数据写回测试库，不等于删除本次准入的全部数据。**

**一句话理解：取消准入不会删除已经同步到测试侧的数据，而是请数据标准平台算出“取消后应该恢复成什么内容”，然后把平台返回的内容重新写入测试侧。**

具体处理如下：

1. 调用 `CodeTableFacade#codeTableRollbackSync`，传入 `codeType`、`releaseUnitId`、`codeTableId`，查询取消本次准入后的码表版本。
2. 将返回的码表写入 `t_abs_basic_type`：本地没有就新增，已有就更新。
3. 调用 `CodeValueFacade#codeValueRollbackSync`，使用相同的三个业务参数分页查询取消后的码值列表。
4. 将平台返回的每个码值写入 `t_abs_non_prod_code`：
   - 本地存在相同的 `typeCode + basicCode`：更新这条记录；
   - 本地不存在：新增一条记录。

例如，准入后测试表中有以下数据：

| 码值 | 测试表当前内容 | 平台回滚接口返回 | CANCEL 后结果 |
| --- | --- | --- | --- |
| `A` | 新名称 | 旧名称 | 更新回旧名称 |
| `B` | 已存在 | 已存在 | 按回滚结果更新 |
| `C` | 本次准入新增 | 未返回 | **仍然保留，不会被删除** |

所以从当前代码实现看，`CANCEL` 更准确地说是“将平台返回的回滚数据增量合并到非生产表”，并不是先清空测试数据后再完整恢复。

需要特别注意：代码不会比较并删除差异数据，也不会把平台未返回的本地码值置为无效。因此能否完整撤销本次准入，取决于回滚接口是否把需要恢复或失效的码值都返回出来；仅从本系统代码看，未返回的数据不会发生变化。

### 3. 上线（PASS）

上线的目标是把审批通过的数据同步到正式码值表：

1. 调用 `CodeTableFacade#queryByCodeType` 查询数据标准平台的当前码表信息，并新增或更新 `t_abs_basic_type`。
2. 调用 `CodeValueFacade#queryCodeValuePageSync`，分页查询本次审批对应的码值。
3. 将码值写入生产表 `t_abs_basic_code`：
   - 当前没有有效码值时，按每批 1000 条批量新增；
   - 已有有效码值时，按 `typeCode + basicCode` 匹配，匹配到则沿用原 `codeId` 更新，未匹配到则新增。
4. 如果 `codeType = area_cd`，还会同步行政区待更新表 `t_abs_area_update`：按行政区 `code` 新增或更新，并把 `updatedStatus` 设置为有效，供后续行政区更新流程处理。

上线采用增量新增/更新，不会先做全量清空；本次平台结果中未返回的既有码值不会被自动删除。

### 4. 删除（DELETE）

删除采用逻辑删除，只处理正式侧数据：

该动作不调用数据标准平台的码表或码值查询接口，只根据消息中的 `codeType` 操作本地数据库。

1. 按 `codeType` 查询 `t_abs_basic_type`；存在时将 `is_valid` 更新为 `0`。
2. 查询 `t_abs_basic_code` 中该类型的有效码值；存在时逐条将 `is_valid` 更新为 `0`。

它不会物理删除数据库记录，也不会删除 `t_abs_non_prod_code` 中的测试码值。若码表不存在，或码表存在但没有有效的正式码值，对应步骤会直接结束。

## 公共收尾：刷新码值缓存

四种合法动作执行完成后，都会清除 `abossCode` 下当前 `codeType` 对应的码值缓存，再从 `t_abs_basic_code` 查询有效码值并重新写入缓存。

需要注意：当前收尾逻辑只刷新码值缓存，没有在这里清理 `abossType` 码表缓存；准入和取消准入虽然修改的是非生产码值，但仍会按同样规则刷新正式码值缓存。

## 快速对照

| 动作 | 码表 `t_abs_basic_type` | 非生产码值 `t_abs_non_prod_code` | 生产码值 `t_abs_basic_code` | 其他处理 |
| --- | --- | --- | --- | --- |
| 准入 | 新增或更新当前版本 | 新增或更新 | 不修改 | 刷新生产码值缓存 |
| 取消准入 | 新增或更新回滚版本 | 新增或更新回滚数据 | 不修改 | 刷新生产码值缓存 |
| 上线 | 新增或更新当前版本 | 不修改 | 新增或更新 | `area_cd` 同步 `t_abs_area_update`；刷新缓存 |
| 删除 | `is_valid = 0` | 不修改 | 有效码值逐条置 `is_valid = 0` | 刷新缓存 |
