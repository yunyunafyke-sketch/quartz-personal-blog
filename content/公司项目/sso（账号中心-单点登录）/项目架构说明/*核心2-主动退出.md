# SSO主动退出

本文基于 `aboss-sso` 工作区代码整理，未执行压测，也未修改代码或数据库。

**目的：** 用户主动退出后，让尚未自然过期的 JWT 在后续认证中被拒绝，同时结束对应的 IDaaS 登录状态。

[打开交互式时序图](../../../../archify/sso-logout-sequence.html)

## 1. 主动退出按顺序做了什么

`LogoutCmdExe.execute()` 按以下顺序执行：

1. 校验 JWT；过期或非法时直接结束。
2. 查询数据库中的有效 Token 记录。
3. 将 JWT 写入 Redis 失效名单，原因标记为 `MANUAL_LOGOUT`。
4. 删除数据库中的有效 Token 记录。
5. 调用 IDaaS 退出接口，作废对应的 IDaaS Token。

例如 JWT 原定 18:00 过期，用户在 14:00 退出。JWT 字符串本身没有改变，但后续请求会命中 Redis 失效记录，因此被拒绝，不必等到 18:00。

**仅删除数据库中的 Token 记录，不足以让这条认证链路拒绝旧 JWT，因为认证时不查这张表。真正承担提前拦截职责的是 Redis 失效记录。**

## 2. 与重复登录限制的区别

| 对比项 | 主动退出 | 重复登录限制 |
| --- | --- | --- |
| 触发时机 | 用户发起退出 | 新登录命中限制策略 |
| 处理范围 | 本次传入的 Token | 当前账号在策略覆盖应用中的旧有效 Token |
| 失效原因 | `MANUAL_LOGOUT` | `ONLY_SINGLE` |
| 共同动作 | 写 Redis 失效名单，删除数据库旧记录 | 写 Redis 失效名单，删除数据库旧记录 |
| 后续动作 | 调用 IDaaS 退出 | 保存本次新 Token 记录 |

退出和重复登录限制负责“写入失效状态”，认证负责“读取失效状态并拦截”。新登录不等于用户主动退出，两个入口的后续动作不同。

## 3. 失效记录的有效期

退出时 Redis 失效记录的 TTL 按数据库 Token 记录的剩余有效期计算。若该记录早于 JWT 过期，失效名单也可能先过期，使旧 JWT 存在重新通过认证的风险。此处是当前代码的条件性风险，尚未结合线上配置验证。详细来源及建议见 [SSO登录](<*核心1-登录.md>) 的“有效期一致性”。
