本文说明业务请求经过 SSO 认证后，用户身份如何经网关传递到业务系统，以及 HTTP 与 SOFARPC 两种转发方式的区别。

> 核心职责：SSO 校验身份并返回认证结果；网关决定是否转发，并向业务系统传递身份；业务系统读取身份，供业务代码使用。
>
> 核实范围：SSO 部分已对照当前 `aboss-sso` 仓库；网关部分依据 `AuthDTO` 的接口约定说明；`aboss-code` 的身份读取、ThreadLocal 存取和异步任务清理已对照本地对应仓库核实。

## 1. 完整请求链路

```text
用户携带 Token 发起业务请求
  ↓
网关调用 SSO 认证或鉴权接口
  ↓
SSO：选择 Token → 校验 JWT → 检查 Redis 失效记录 → 提取身份
  ↓
认证接口：组装用户身份
鉴权接口：在认证基础上校验资源访问权限，并补充权限码
  ↓
SSO 返回 AuthDTO
  ├─ success=false：由网关按失败响应约定处理
  └─ success=true：principal.authData 保存用户身份 JSON 字符串
       ↓
网关按目标服务的转发协议传递 principal
  ├─ HTTP：写入请求 Header
  └─ SOFARPC：写入 RPC request baggage
       ↓
业务系统读取 authData，解析为 AuthUserInfoDTO
       ↓
业务代码使用账户 ID、姓名、角色等身份信息
```

认证结果中的 `authData` 是用户身份 JSON 字符串，原始 Token 则用于 SSO 校验登录状态，两者用途不同。

## 2. SSO 如何完成认证与鉴权

### 2.1 认证和鉴权的区别

当前 HTTP 入口位于 `AuthRPCController`，公共前缀为 `/platform/api/aboss/sso`。

| 类型 | HTTP 接口 | 处理职责 |
| --- | --- | --- |
| 认证 | `POST /platform/api/aboss/sso/certification` | 校验登录身份，返回用户信息 |
| 鉴权 | `POST /platform/api/aboss/sso/authentication` | 在认证基础上，校验当前用户是否有访问目标资源路径的权限 |

`PipelineRouteConfig` 配置的处理顺序为：

```text
认证：InitPipelineHandler → CertificationPipelineHandler
鉴权：InitPipelineHandler → CertificationPipelineHandler → AuthenticationPipelineHandler
```

管道中任一处理器返回 `success=false`，执行器就停止后续处理。

### 2.2 Token 校验

`InitPipelineHandler` 按以下顺序处理：

1. 根据 `cic-auth-method` 选择 Token：值为 `header` 时使用 `cic-htoken`，否则使用 `cic-ctoken`。这些值来自认证请求的上下文。
2. 调用 `jwtUtils.parserJWT()` 校验并解析 JWT。
3. 查询 Redis 中该 Token 的失效记录，命中则拒绝请求。
4. 从 JWT 提取账户 ID、账户角色、账户类型、工号、姓名等信息，写入管道上下文。

Token 为空、过期、解析失败、命中失效记录或缺少账户 ID 时，代码会返回 `success=false`，并将 `failResponseStatus` 设为 `401`。

### 2.3 资源权限校验

`AuthenticationPipelineHandler` 负责资源权限处理：

- 普通账户：调用 ACL，按账户 ID 和资源路径查询访问权限；无权限时返回失败，`failResponseStatus=403`。
- 超管账户：按资源路径向 ACL 查询权限码，再组装身份结果；该分支仍会调用 ACL。
- 校验通过后：将权限码写入上下文，重新组装 `AuthUserInfoDTO`。

这里的 `401`、`403` 是认证结果中的失败状态字段；网关如何转换成客户端最终响应，需要结合网关实现确认。

## 3. principal 和 authData 分别是什么

`AuthDTO` 中的定义为：

```java
private Map<String, String> principal;
```

`principal` 是 SSO 返回给网关的待透传键值对。`real-server` 指最终处理业务请求的后端服务，例如 `aboss-code`。

| 字段 | 含义 |
| --- | --- |
| `success` | 是否允许请求继续转发 |
| `principal.authData` | 序列化后的用户身份 JSON 字符串 |
| `principal.Referer` | 从认证上下文取得的来源信息 |
| `failResponseStatus` | 失败时供网关使用的 HTTP 状态码 |
| `failResponseHeader` | 失败时供网关使用的响应头 |
| `failResponseBody` | 失败时供网关使用的响应体 |

认证处理器中的组装逻辑如下：

```java
AuthUserInfoDTO authUserInfoDTO =
        AuthConvertor.INSTANCE.toAuthUserInfoDTO(certificationPipelineContext);

Map<String, String> maps = Maps.newHashMap();
maps.put(SSOConstant.AUTH_DATA, JSON.toJSONString(authUserInfoDTO));
maps.put(SSOConstant.REFERER, certificationPipelineContext.getReferer());

return new AuthDTO().setSuccess(true).setPrincipal(maps);
```

这段代码完成身份转换、序列化和结果返回。把这些键值对放入后端请求的动作由网关完成。

## 4. 网关如何区分 HTTP 与 SOFARPC

### 4.1 根据目标路由选择协议

`principal` 字段本身没有协议判断能力。按照接口约定，网关应根据目标服务的路由或转发配置，决定使用 HTTP 还是 SOFARPC。

以下仅为概念示例，并非当前环境的真实路由：

| 请求路径                | 目标接口         | 转发协议    | 身份承载位置          |
| ------------------- | ------------ | ------- | --------------- |
| `/api/order/detail` | 订单服务 HTTP 接口 | HTTP    | 请求 Header       |
| `/api/code/query`   | 字典服务 RPC 方法  | SOFARPC | request baggage |

需要分别看清三段调用：用户到网关、网关到 SSO、网关到业务系统。用户通过 HTTP 请求网关，并不代表网关转发到业务系统时也使用 HTTP。

### 4.2 转发逻辑示意

以下为伪代码，说明接口约定，不代表仓库中的实际网关实现：

```text
认证结果 = 调用 SSO

如果 success 为 false：
    按 failResponseStatus / Header / Body 处理失败响应
    停止转发

如果目标路由使用 HTTP：
    将 principal 的键值对写入后端 HTTP 请求 Header

如果目标路由使用 SOFARPC：
    将 principal 的键值对写入后端 RPC 请求 baggage

转发到业务系统
```

当前核实到的 SSO 代码负责返回 `principal`。具体的协议选择、Header/baggage 写入位置，需要继续查网关的路由配置和认证结果处理代码。

## 5. 业务系统如何读取身份

### 5.1 HTTP 接口

从请求 Header 中读取 `authData`，再解析用户身份。读取示意：

```java
String authData = request.getHeader("authData");
```

当前 `AuthRPCController` 的两个 HTTP 入口会对身份中的 `personName` 进行 URL 编码，再重新序列化 `authData`。排查中文姓名显示问题时，应同时核对实际入口和下游解码逻辑；该处理仅针对姓名字段，并非对整段 JSON 编码。

### 5.2 SOFARPC 接口：身份信息如何传到业务代码

**request baggage 就是 RPC 请求中的附加信息，作用类似 HTTP 请求的 Header。** 在这条链路里，网关把用户身份 `authData` 放进去，业务服务收到请求后再取出来。

以“张三查询字典”为例，顺着一次请求来看。

**第一步：业务参数告诉服务要查什么。**

假设字典接口接收一个字典编码：

```java
queryDictionary("gender")
```

`gender` 表示要查哪个字典，但这个参数没有说明当前用户是谁。为了让服务拿到用户身份，又不必给每个业务方法增加用户参数，网关会把身份放到 RPC 请求的 baggage 中。

**第二步：网关把身份附在同一次 RPC 请求上。**

SSO 认证通过后，会在 `principal.authData` 中返回用户身份 JSON 字符串。按照透传约定，网关将它写入 baggage，再调用字典服务。因此，业务服务收到的请求可以理解为：

```text
一次 RPC 请求
├─ 业务参数：dictCode = gender
└─ 附加信息 baggage
   └─ authData = 张三的用户身份 JSON 字符串
```

`baggage` 是承载附加信息的位置，`authData` 是其中一个键，键对应的值才是用户身份。这里的字典接口和用户仅为说明示例，网关具体写入代码需在网关工程核实。

**第三步：业务服务取出身份，供业务代码使用。**

原笔记记录的读取方式是：

```java
RpcInvokeContext.getContext().getRequestBaggage("authData");
```

这行代码的意思是：“从当前 RPC 请求的附加信息中，取出名为 `authData` 的值。”取到的仍是 JSON 字符串，需要解析成 `AuthUserInfoDTO` 才能作为用户对象使用。

原笔记中，`aboss-code` 将这套处理封装在切面里：带 `@UserInfo` 的方法执行前，`UserInfoAspect` 通过 `SofaRpcContext.userInfo()` 读取并解析身份，再保存到 `ThreadLocalUtils`。随后，业务代码就可以通过 `UserInfoUtil.accountId()`、`disPlayName()`、`isAdmin()` 获取账户 ID、姓名和角色信息。这条调用链已在本地 `aboss-code` 仓库核实；线程上下文的清理情况见下一小节。

这里出现的两个存放位置，分别用于不同阶段：**baggage 把身份随请求带到业务服务；ThreadLocal 则把解析后的身份留在服务端当前线程中，方便业务代码读取。** ThreadLocal 本身不负责跨服务传输。

### 5.3 ThreadLocal：用户信息存在哪里，什么时候清理

**ThreadLocal 可以理解为“当前线程自己的存储空间”。** code 服务把用户信息存进去后，同一线程执行的后续代码就能读取，不用层层传递用户参数。它不能跨服务共享，也不会自动把信息传到线程池的另一个线程。

本节已核对本地 `/Volumes/data/ideaWorkSpace/aboss-code` 源码。`ThreadLocalUtils` 实际使用的是普通 `ThreadLocal<Map<String, Object>>`，不是 `TransmittableThreadLocal`；切面注释中的“ttl”不能作为使用了 TTL 的依据。

#### 为什么线程池中必须注意清理

线程池会反复使用同一个线程。一次请求结束，并不代表执行它的线程被销毁，ThreadLocal 中的数据也不会因为请求结束自动删除。

例如，线程先处理张三的请求，存入了张三的身份；随后这个线程被分配给另一个请求。如果旧身份没有清理，而新请求又没有写入新身份，业务代码就可能读到张三的信息。旧对象也可能一直被线程持有。

因此，应在本次请求或任务结束时清理上下文，并放在 `finally` 中，确保正常返回和抛异常都会执行。

#### code 服务确实有线程池，异步任务已经做了清理

```java
    
/**  
 * 相当于告诉 Spring：  
 * 遇到标有 @Async 的方法调用，要按异步任务处理。  
 */  
@EnableAsync  
@Configuration  
public class AsyncConfig implements AsyncConfigurer {  
  
    /**  
     * 创建线程池  
     * @return  
     */  
    @Override  
    @Bean("taskExecutor")  
    public Executor getAsyncExecutor() {  
  
        /**  
         * java原生线程池  
         * new ThreadPoolExecutor(  
         *         2,                              // corePoolSize：核心线程数  
         *         4,                              // maximumPoolSize：最大线程数  
         *         30,                             // keepAliveTime：非核心线程的空闲存活时间  
         *         TimeUnit.SECONDS,               // 时间单位  
         *         new ArrayBlockingQueue<>(10),   // workQueue：最多等待 10 个任务  
         *         threadFactory,                  // ThreadFactory：创建线程的规则  
         *         new ThreadPoolExecutor.AbortPolicy() // 拒绝策略  
         * );  
         */  
        /**         * Spring 封装的 ThreadPoolTaskExecutor  
         *   提供设置线程名称、包装任务、应用关闭时处理任务等功能  
         *        ↓ 内部创建和使用  
         * Java：ThreadPoolExecutor  
         *   负责线程复用、任务排队、线程数量控制和拒绝任务  
         */  
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();  
        // 核心线程数 - 根据CPU核心数和任务类型调整  
        executor.setCorePoolSize(5);  
        // 最大线程数  
        executor.setMaxPoolSize(10);  
        // 队列容量  
        executor.setQueueCapacity(100);  
        // 线程前缀（给线程起名字,创建出来的线程会使用类似这样的名字： Async-Executor-1 Async-Executor-2 ）  
        executor.setThreadNamePrefix("Async-Executor-");  
        // 拒绝策略  
        //DiscardPolicy ：直接丟弃任务  
        //CallerRunsPolicy ： 使用调用者线程直接执行被拒绝的任务  
        //AbortPolicy ：默认的拒绝策略，抛出 RejectedExecutionException 异常  
        //DiscardOldestPolicy：丢弃处于任务队列头部的任务，添加被拒绝的任务  
        executor.setRejectedExecutionHandler(new java.util.concurrent.ThreadPoolExecutor.CallerRunsPolicy());  
        // 等待所有任务完成再关闭  
        /**  
         * 比如 code 服务正在重启，此时线程池中：  
         * 任务 A：正在导出文件  
         * 任务 B：正在刷新缓存  
         * 任务 C：还在队列里等待  
         *  
         * 设置为 true 后，线程池关闭时会：  
         * - 不主动中断正在执行的 A、B。  
         * - 继续执行队列里等待的 C。  
         * - 不再接收新任务，已有任务完成后线程池结束。  
         */  
        executor.setWaitForTasksToCompleteOnShutdown(true);  
        // 只要里面有线程在工作，关闭应用的时候，最多等线程池执行30秒（适合用于重启时还有任务）  
        executor.setAwaitTerminationSeconds(30);  
        //是给线程池配置一个任务包装器：以后任务交给这个线程池执行时，都先经过 ContextCopyingDecorator 的处理，用来传递上下文  
        /**  
         前端点击“导出”  
         ↓         请求经过网关认证  
         网关将用户身份 authData 放入 RPC baggage  
         ↓         请求到达 code 服务  
         服务框架安排线程 A 执行接口  
         ↓  
         UserInfoAspect 从 RPC baggage 读取用户信息  
         解析成 AuthUserInfoDTO，存入线程 A 的 ThreadLocal  
         ↓         执行 exportCodes()，校验请求参数  
         ↓  
         通过 Spring 代理调用异步导出方法  
         BasicCodesExportExe.execute()  
         该方法标注 @Async("taskExecutor")  
         ↓         Spring 找到名为 taskExecutor 的线程池  
         ↓  
         ContextCopyingDecorator 在线程 A 中复制用户上下文  
         并将导出任务包装成：         “设置用户上下文 → 执行导出 → finally 清理上下文”  
         ↓         把包装后的任务提交给线程池  
         │  
         ├── 线程 A：继续执行接口代码  
         │       ↓  
         │   设置返回结果：  
         │   data = true，status = 成功状态  
         │       ↓  
         │   返回给前端  
         │   表示任务已受理，不代表文件已生成  
         │   当前接口没有返回导出任务 ID  
         │         └── 线程 B：从线程池取得任务并执行  
            ↓  
            将复制的用户上下文放入线程 B 的 ThreadLocal  
            这样导出代码就能读取当前用户 ID  
            ↓            新增一条导出记录到 t_abs_opertaion_history  
            包含操作 ID、创建人、操作类型等  
            初始状态：-1，解析中  
            ↓  
            查询码表和码值数据  
            ↓  
            生成并上传导出文件  
            │  
            ├── 成功：更新同一条导出记录  
            │   状态 = 1，成功  
            │   保存 fileId、fileName  
            │            └── 处理异常：更新同一条导出记录  
            状态 = 0，操作失败  
            错误说明 = 文件生成失败  
            ↓  
            finally 清理线程 B 的 ThreadLocal  
            ↓            本次任务结束  
            线程 B 留在线程池中，等待其他任务  
  
  
         前端后续查询导出记录：exportCodesHistory()  
         ↓         后端读取数据库中的最新记录并返回  
         ↓  
         前端根据状态更新页面  
         ├── -1：处理中  
         ├──  1：成功，记录中已有文件 ID  
         └──  0：失败，展示错误信息  
         */  
        executor.setTaskDecorator(new ContextCopyingDecorator());  
        executor.initialize();  
        return executor;  
    }  
}
```

`AsyncConfig.getAsyncExecutor()` 创建了名为 `taskExecutor` 的线程池。当前代码直接设置核心线程数为 5、最大线程数为 10、队列容量为 100，并配置了 `ContextCopyingDecorator`。使用 `@Async("taskExecutor")` 的方法会使用这个执行器。

注意：配置文件中还有 `thread.pool.*` 属性，但上述方法使用的是直接写入的数值，没有读取这些属性。这个异步线程池也不能等同于接收 RPC 请求的执行线程池；当前检查没有确认 RPC 服务端的实际线程池参数。

普通 ThreadLocal 不会自动跨线程传递，所以 `ContextCopyingDecorator.decorate()` 做了以下处理：

```text
提交任务的线程：复制当前用户上下文
    ↓
执行异步任务的线程：将复制的上下文放入自己的 ThreadLocal
    ↓
执行任务
    ↓
finally：清理执行任务线程的 ThreadLocal
```

对应的关键代码为：

```java
try {
    ThreadLocalUtils.set(copiedContext);
    runnable.run();
} finally {
    ThreadLocalUtils.remove();
}
```

这里的 `remove()` 最终调用 `threadLocal.remove()`，删除当前线程绑定的上下文。复制 Map 是浅拷贝，里面的用户对象本身没有被深拷贝。

#### RPC 请求入口的清理，目前没有找到

`UserInfoAspect.before()` 在带 `@UserInfo` 的方法执行前读取 baggage，并把用户身份写入 ThreadLocal。但这个切面只有 `@Before`，没有配套的结束清理逻辑。

检索当前仓库后，找到的 `ThreadLocalUtils.remove()` 调用位于上述异步任务装饰器中。**异步工作线程清理自己的 ThreadLocal，不会顺便清掉提交任务的请求线程中的 ThreadLocal。** 因此不能据此认定整个请求的上下文都已经清理。

当前代码还有一个需要注意的条件：切面只有在读取到非空用户信息时才写入；如果本次没有读到身份，就直接跳过。这意味着在线程复用且旧身份未清理的情况下，旧值可能继续留存。这里指出的是代码层面的风险，并不表示已经确认线上发生了身份串用。

建议在统一的请求边界管理用户上下文：进入时明确初始化，退出时在 `finally` 中清理；如果存在嵌套调用，则需要处理原上下文的恢复，避免内层调用提前清掉外层仍需使用的数据。本次仅记录检查结果，未修改业务代码。

另外，当前异步线程池使用 `CallerRunsPolicy`：线程池饱和时，任务可能直接在提交线程执行。这时装饰器里的 `remove()` 会清掉提交线程的上下文，后续代码若还需要用户身份，就可能取不到。因此装饰器也需要考虑执行前保存、执行后恢复原上下文的情况。

源码定位（相对于 `aboss-code` 仓库）：

- `aboss-code-infrastructure/src/main/java/com/aliyun/fsi/insurance/code/infra/config/AsyncConfig.java`：线程池及装饰器配置。
- 同目录 `ContextCopyingDecorator.java`：跨线程复制及 `finally` 清理。
- 同目录 `UserInfoAspect.java`：RPC 用户信息写入，当前没有配套结束清理。
- `aboss-code-infrastructure/src/main/java/com/aliyun/fsi/insurance/code/infra/util/ThreadLocalUtils.java`：普通 ThreadLocal 的存取与删除。

## 6. 排查时从哪里看

| 现象 | 优先检查 |
| --- | --- |
| SSO 返回认证失败、失败状态为 401 | Token 选择方式、Token 是否为空或过期、Redis 失效记录、账户 ID |
