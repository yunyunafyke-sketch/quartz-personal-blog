```text
访问业务系统
→ 检查 Cookie 中是否有“本系统自己的登录态”
  → 有：验证有效性，进入系统
  → 没有：跳转门户登录页
→ 用户在门户完成登录
→ 门户带着临时 code 回调业务系统
→ 业务系统后端用 code 换 token
→ 根据 token 获取门户用户信息
→ 用门户用户唯一标识匹配本系统账号
  → 有账号：创建本系统自己的登录态，写入 Cookie，跳转首页
  → 没账号：拒绝登录或提示联系管理员
```



## IDaaS、账号中心与外部系统的职责

外部系统接入我们的单点登录时，通常会使用我们提供的两个接口：

1. **使用授权码 `code` 换取 `token`**：外部系统服务端提交登录回调收到的临时 `code`，由接口校验并换取访问令牌。
2. **使用 `token` 获取用户信息**：外部系统携带 `token` 调用接口，取得账号中心中的用户标识及所需资料。

这两个接口是外部系统接入单点登录的协议入口，但接口本身不一定承载完整的认证能力。认证和授权码相关能力通常由 IDaaS 提供；我们的服务将这些能力按统一接口暴露给外部系统，并可能负责客户端校验、请求转发、用户映射或结果封装。具体边界要以接口实现为准：例如检查 `code` 和 `token` 是由哪一侧签发、保存、校验和过期处理，就能判断相应职责落在哪一侧。

完整登录过程由几方共同完成：

- **IDaaS**：负责身份认证，以及相关登录会话、授权码或令牌能力（以实际集成方式为准）。
- **我们的账号中心服务**：提供外部系统调用的接口，并根据实现承担客户端接入、与 IDaaS 交互、用户信息查询或映射等工作。
- **外部业务系统**：接收授权码，调用接口获取令牌和用户信息，再将用户匹配到本系统账号，并创建、维护自己的登录态。

因此，外部系统虽然调用了我们提供的接口，但用户认证能力仍可能由 IDaaS 支撑；我们的服务承担的是对外接入和集成职责。外部系统获取到用户信息后，还需要建立自己的会话，不能把账号中心的 `token` 直接等同于外部系统本地登录态。
