## 帐号

**统一身份与账号管理平台 · 统一管理企业账号、登录认证和安全策略**　【2024.7－至今】

**背景：** 为公司多个业务应用提供统一登录、账号生命周期管理及安全策略配置，对接组织系统、权限系统和身份平台（IDaaS）。系统分为管理态与运行态，分别负责账号及策略配置、登录认证与策略执行。

**职责：** 参与后端开发与日常维护，重点负责单设备登录、空闲超时、登录白名单及登录侧联动，参与账号生命周期管理、二次认证调整和账号导出优化

**难点：**

- **高并发认证鉴权与账号查询。** 面向多系统使用接口时会通过api网关绑定认证接口，每次使用他们自己的接口时流量会经过帐号系统，需要支撑高并发认证与鉴权请求，以及对外 RPC 接口的高频账号状态查询，通过查询与索引优化，降低数据库访问开销，支撑高并发调用。
    
- **不同应用与人员的登录策略差异。** 针对重复登录限制、差异化空闲时长及特殊账号放行等需求，通过策略配置、应用及人员关联、白名单统一管理，由运行态匹配并执行，减少规则调整对代码修改的依赖；涉及多张策略表的配置变更，通过本地事务保证原子性。
    
- **多种登录方式的公共逻辑复用。** 将密码登陆与 OAuth2 登录中的用户查询、Token 签发、会话控制等公共步骤抽取为可复用处理器，组合成 4 条登录流程，减少重复实现，便于统一调整公共登录逻辑。
    
- **跨系统账号状态与缓存同步。** 面向离职、返聘等场景，处理本地账号与 IDaaS 的停用、归档、恢复及手机号占用问题。账号变更后通知下游并清理缓存，提供全量及指定账号刷新入口。

- **统一单点登录接入，三方系统使用单点登陆能力。** 封装 IDaaS 第三方登录能力，提供授权码换 Token、Token 获取用户信息的统一接口，降低外部系统接入成本。
    
**结果：** 完成单设备登录、空闲超时和登录白名单三类策略管理及相关登录侧联动，支持 4 条登录流程、账号生命周期管理和缓存刷新，RPC 接口的高频账号状态查询。平台调用覆盖100个应用、10万个账号，日均服务请求量4亿次。 认证接口QPS1300-2000， 响应时间0.7-0.9ms，系统cpu水位：20%以内，内存水位：55%以内，配置为16pod，4c8g。







## 码表

【统一码表管理平台】【为多个业务系统提供统一的字典查询和编码转换服务】 【2024.7 - 至今】

背景：多个业务系统都会用到基础字典、行政区和业务编码。如果各自维护，同一个编码容易出现不同解释，数据更新也需要逐个系统处理。这个项目把这些公共数据集中管理，对接上游数据标准平台，为各业务系统提供统一查询，同时保留历史版本，满足旧数据回查的需要。

职责：独立负责码表查询、变更同步、关联关系和行政区管理等后端开发， 实现查询接口、数据存储和缓存更新，并完成批量导入、校验及操作记录等

难点：

上游数据变了，本地也要跟得上。 码表有准入、上线、取消等不同状态，不能收到通知就直接覆盖。我负责按状态拆分处理流程，分别维护生产和非生产码值；通过 MQ 接收变更，再从上游拉取数据，同时提供按时间段将上游信息同步到系统的定时任务，补充单靠消息同步可能遗漏的数据。

查询要快，返回的数据也要及时更新。 码表会被多个业务系统反复查询，因此按码表类型缓存整组码值，减少重复查库；数据变更后清理并重新加载缓存，再配合定时刷新，兼顾查询效率和更新及时性。

结果：为公司所有业务系统提供统一码表服务，日调用量达2亿，通过 Redis 缓存实现热点数据缓存，降低数据库压力并提升系统并发处理能力，接口耗时控制在20ms内，配置8pod，4c8g



## 消息中心

**消息中心 · 面向业务系统提供统一的站内信与钉钉消息发送能力**　【2024.7 - 至今】

**背景：** 业务系统需要通过不同渠道发送消息，各渠道的参数格式、发送流程和结果反馈各不相同。项目将消息校验、组装、持久化、异步投递和渠道发送收拢到统一服务中，并通过消息任务记录和失败重试处理发送异常。具体成本、吞吐量等背景指标，仓库里没有记录。

**职责：** 独立负责消息中心核心功能，从统一发送入口到渠道发送、任务落库和失败重试全链路落地；负责站内信与钉钉渠道接入，梳理消息任务状态流转。

**难点：**

- **让消息在异步链路中可追踪：** 先将消息保存为待发送任务，再向 MQ 投递任务 ID。消费者根据 ID 获取任务并执行发送，避免把完整消息内容放在 MQ 消息里，也让数据库成为任务状态和失败原因的查询依据。

- **处理“已落库但投递或发送失败”的情况：** 发送失败时更新任务状态、失败原因和重试次数；定时任务按最大重试次数查询待重试消息并重新发送。通过任务记录衔接 MQ 消费与补偿流程，减少一次调用失败就丢失处理线索的情况。

- **适配不同渠道的发送与结果反馈：** 站内信和钉钉分别由独立渠道服务处理；钉钉链路还涉及 access token、异步发送结果查询。


**结果：** 代码实现了统一发送入口、站内信与钉钉渠道适配、任务持久化、MQ 异步投递及失败重试。消息中心每日产生300万



机构接收者与实际账户并非一一对应，若直接按机构写入消息，用户侧查询和状态管理都不方便。实现上先将机构编码解析为账户 ID，再按每个账户生成独立消息明细，使后续未读统计、已读和收藏都能以当前登录用户为边界。相比只保存一条机构级消息，这种方式更方便个人维度的查询和操作，但会增加消息明细数量，因此发送时采用**每 1000 条分批入库**。  
另一个难点是不同业务系统的消息内容各异：系统支持模板发送和非模板发送。模板发送时校验模板有效性及参数匹配，并允许请求覆盖模板内容或跳转链接；非模板方式则直接按接收人生成消息记录。每次发送生成批次号，并记录来源应用、请求流水号、收件人、状态等信息，便于关联同一批发送记录。

**实现方式：** 业务通过 RPC 发送接口提交模板、消息内容和接收对象；服务校验接收人类型、空收件人及链接格式，机构接收人会解析为账户。随后为每位收件人建立一条初始未读的消息明细并批量写入。用户侧根据当前登录账户进行分页查询，提供未读数、最多 5 条未读消息、批量已读、全部已读、收藏和按应用分组统计等能力。查询实现可按配置走 Elasticsearch 或数据库，并将应用 ID 转换为应用名称；应用名称查询失败时以应用 ID 兜底。


**结果：** 已形成覆盖“消息发送—收件人解析—个人消息查询—阅读与收藏管理”的站内信能力，并支持模板消息与直接发送。**性能和稳定性指标建议用线上数据补充**，例如发送量、入库耗时、查询 P95、批量发送成功率或故障率；当前代码本身无法确认这些量化结果。
